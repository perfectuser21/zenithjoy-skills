# 安卓朋友圈发布（com.tencent.mm 原生朋友圈，非视频号）

> **本 skill 的职责边界：只管"把已经写好、已经审核批准的内容发到手机上"，不管内容怎么来的。**
> 文案生成（AI 写文案）+ 质检/审核是完全独立的服务器端流程（`generateMomentDraft()` +
> `/api/wechat/moment-drafts` 审核台 API），跟手机操作没有任何关系，也不是"这个 skill 的一部分"——
> 两者甚至可以不同一天发生（今天审核通过、明天再发）。别把"往手机屏幕里填字"这个机械动作
> 误当成"制作"，那只是发布流程里"把内容搬上屏幕"这一步。

> **熟化阶段：EXPLORE→VALIDATE** · 连续零新坑 1/3（小龙虾ANGYVB4311010223✅ 0917 首通） · 上次更新 0917
> 本次姿态：严格照下表执行，任何偏差=发现→回流手册（协议见 android-publish「运行阶段协议」）。

前提：微信已登录，且要发布的文案+图片已经**在服务器端审核通过**（走完 `generateMomentDraft` →
`/api/wechat/moment-drafts` 审核台 → approve 这一整套，不在本 skill 职责内）。坐标为 1200x2664
（小龙虾 HONOR MAA-AN00）实测。**朋友圈是全通讯录广播、不可撤回**，比发视频号/发抖音私密作品风险
更高——发布前务必按 android-publish「内容安全铁律」+ 本文「坑」核对。

## 素材下发

同 android-publish 规范：真实发布任务从发布包 media[].url 下载，文件名相机风格 `IMG_<yyyymmdd>_<hhmmss>.jpg`，
push 到 `/sdcard/DCIM/Camera/` 后广播 `MEDIA_SCANNER_SCAN_FILE`。**绝不用手机相册里的既有真实照片当素材**
（那是本人私人照片）。蹚路阶段用 ffmpeg 生成暖色调渐变图代替真实照片：
```bash
ffmpeg -y -f lavfi -i "gradients=size=1080x1080:duration=1:nb_colors=4:c0=0xFF8C69:c1=0xFFB88C:c2=0x6E9DC9:c3=0x2C3E63" \
  -frames:v 1 moment.png && ffmpeg -y -i moment.png -q:v 3 moment.jpg
```

## ⚠️ 坐标判定协议（每一步定坐标都按此顺序，不允许死记坐标）

**铁律：坐标永远现场判定，绝不硬编码**——本文档表格里写的坐标只是「这次实测在这台设备这个分辨率下的参考值」，
换机型/换分辨率/微信改版都可能失效，跟 android-publish 底座「不绑机型」原则一致。语义步骤（找哪个文字/
图标、按什么顺序）才是真正固化的东西，坐标每次都要重新定位。

**定位一个控件按此顺序自动切换，不因某一层失败就中断流程**：

1. **优先 `uiautomator dump`**：按 text/content-desc 精确匹配控件，取 bounds 算中心点。最快最准，能用就用。
2. **dump 返回空节点（只有一个 bounds=[0,0][0,0] 的占位 node）→ 自动切视觉判定**：截图，把图交给视觉模型，
   让模型在**这次实际截图**里现场判断目标控件的像素位置——不是套用历史记录的坐标数字，是每次重新看图判断，
   这样天然跟设备无关。
3. **视觉判定的两种打法**（模型自己选，优先级看情况）：
   - 已知控件有明显色值特征（如微信绿按钮 `RGB(88,190,106)`、点赞后的红心）→ 用 PIL/图像处理扫描该颜色
     像素范围取中心点，比纯目测精确（0917 实测：肉眼估算连续 2 次算错坐标，颜色扫描 1 次就中）。
   - 无明显色值特征（纯文字/图标按钮）→ 视觉模型直接看图读取文字位置估算坐标，读完立刻截图核验点没点对，
     错了重新读图，不硬着头皮往下走。
4. **不确定切回 dump 是否恢复** → 下一步依然先试 dump（万一已恢复），失败再回到视觉判定，不假设它永久失效。

**0917 实测背景**：微信会在会话内累积触发后，对 `uiautomator dump` 持续返回空树（截图画面正常，dump 只有
一个占位空节点），`force-stop` 重启微信进程也不恢复；前 45 分钟约 50 次 dump 正常，之后（约第 2 次发朋友圈
选图起）全部转空，持续到会话结束；对照系统桌面 dump 正常（排除 ADB/USB 连接故障）；交替测试 3 轮（微信/
桌面/微信/桌面…）耗时稳定在 2-3 秒，非超时/连接抖动。触发阈值未知（n=1）。完整分析见 memory Learning
「微信安卓端反自动化实测」。

## 坑（0917 实录）

1. **「拍照分享」长按 ≠ 快捷发图，是隐藏的纯文字发布入口**：长按会弹出提示"长按拍照按钮发文字，为内部体验功能"，
   进去后是无法带图片的纯文字合成页（`SnsUploadUI` 但走文字分支）。**要图文发布必须单击**，弹出菜单后走
   「从手机相册选择」。
2. **底部导航栏 / 时间线内条目坐标不能靠比例估算**：聊天列表和「发现」页视觉上都是等分四宫格/列表，
   但两次按肉眼比例估算坐标都点歪了（点进了别的聊天/别的动态）。**一律先 `uiautomator dump`，
   按 text/content-desc 拿 bounds 算中心点**，符合 android-publish 底座「无障碍树语义查询优先」的规定，
   本页面尤其不能省这一步——这台机器微信里是真实客户聊天记录，点歪了有读到无关会话内容的风险。
3. **相册选择器的 content-desc 自带时间戳**（如 `图片9, 2026-09-17 07:29`），可直接拿 `adb push` 时的
   `date +%Y%m%d_%H%M%S` 时间去匹配定位刚推送的素材，比数缩略图格子位置可靠得多。
4. **可见范围（分组）选择器可达性尚未探测**——本轮 MVP 全部按默认「公开」发布，真机验证"谁可以看"能否
   被 ADB 精确操作分组选择，留给下一轮 VALIDATE。
5. 微信是敏感 App：全程截图/dump 驱动，每步验前台（`dumpsys window | grep mCurrentFocus`），别盲点——
   本轮两次误触都发生在"图省事直接按坐标点"的时候。
