# 验收报告模板

写到工作区 `report.md`。结构和顺序不可变——第一屏必须让不懂技术的老板 30 秒看懂全貌。

```markdown
# <skill名> <版本> · 验收报告

归属：<Area> › <Line> › <Ability>（<确认/系统建议待确认>）
提交人 <名> · 来源 <平台> · <日期> · 评估模式 <quick/full>

## 一、总览（第一屏）

**裁决：<通过 / 部分通过——附条件 / 不通过>**

| 功能线 | 依赖缺失 | 缺陷 | 实测成本 | 评估耗时 |
|-------|---------|------|---------|---------|
| N 条 | n 处 | xH·yM·zL | $0.00 | 分钟 |

### 功能地图

<function-map.md 的表格原样放这里>

## 二、梳理向导记录

<N> 题：作者答 <n> / 评估员替判 <m>（替判项列表，作者需复核）
→ 生成断言合同 <k> 条（附 contract-assertions.md 全文或链接）

## 三、逐线评估结论

quick 模式：每线给 静态可执行性判定（可执行/降级未定义/主路径不可执行）
full 模式：线 × 宿主模型矩阵，每格 通过/HF 命中率/分数，附独立vs批量模式差异

## 四、缺陷清单

按 H → M → L 排，每条：编号 · 描述 · 原文位置 · 修复建议
H 级缺陷单独加粗提示：建议回 skill-creator 走修复迭代

## 五、生产选型建议（full 模式）

按价位分档：哪档模型能直接用 / 哪档要外挂后置检查器（给出正则方向）/ 哪种运行形态最安全

## 六、方法局限声明

<按 grading-protocol.md 方法自检清单如实写>

## 七、下一步

- 作者：<最短修复路径，按缺陷优先级排>
- 复评：<修复后重交，quick 免费随时可跑>
```

## 语言纪律

- 报告读者是交 skill 的同事和老板，不是工程师：每个术语首次出现给一句话解释（如"硬失败 HF = 一票否决项"）。
- 缺陷描述引用被测 skill 原文，别只写结论。
- 成本和耗时写实测值，不写估计值；quick 模式成本写 $0。
