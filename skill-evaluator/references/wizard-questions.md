# yes/no 梳理向导：出题规则

## 为什么是 是/否 题

skill 作者（往往非技术同事）说不清自己 skill 的边界，让他们写文档是痛苦之源。把模糊处变成"点一下"就能回答的二值问题，作者 2 分钟理清，且**每个答案直接变成一条可验证断言**——向导既是需求澄清，也是在签验收合同。

## 从哪找题（5 类模糊点 → 题型模板）

| 模糊点来源 | 题型模板 | 是 → 断言 | 否 → 断言 |
|-----------|---------|----------|----------|
| 功能线归属存疑（Step 1 里"顺嘴提到"的线） | 「X 也在这个 skill 的职责范围内吗？」 | 功能线 +1（依赖缺失则同时标阻塞） | 该线剔除 + 建议删除相关文本 |
| 输入可达性（声明的数据源在宿主里有没有） | 「skill 嵌入的 Agent 能读到 X 吗？」 | 断言：字段必须引自 X 原文 | 阻塞：先接数据源再评 |
| 缺料降级（输入可能天然缺失） | 「X 缺失时应该照常输出（标注降级）而不是报错，对吗？」 | 断言：缺 X 时输出降级版+标注 | 断言：缺 X 时明确报错 |
| 编造红线（模型可能"好心补数据"处） | 「没有 X 资料时，允许模型按常识估一个写进输出吗？」 | 允许标注来源的估计（宽松红线） | 硬失败断言 HF：任何 X 编造=一票否决 |
| 字段填法（有名无定义的字段，逻辑校验第 3 类） | 「字段 X 应该填 A 类判断（而不是 B），对吗？」 | 断言：X=A 口径 | 断言：X=B 口径 |

出题纪律：
- 5-10 题封顶，按重要性排序，编造红线类的题**必出且标注"本次评估最重要的一题"**。
- 每题必带「为什么问」：引用 skill 原文位置 + 说清选是/选否各自的后果。作者要能不看 skill 全文就答题。
- 已经在 skill 里写得清清楚楚的不要问——向导是补模糊，不是走过场。

## 提问方式

- **有头**：AskUserQuestion 逐题，选项固定三个：「是」「否」「不确定，让评估员按原文保守判断」。
- **无头**：题目全量写入工作区 `wizard-questions.md`，逐题按保守方向替判（编造类一律按"否=严红线"，功能线归属按"skill 原文有写就算有"），报告里列出所有替判项提醒作者复核。

## 断言合同格式（contract-assertions.md）

```markdown
# <skill名> 验收断言合同
生成方式：梳理向导 <N> 题（作者答 <n> / 评估员替判 <m>）+ 逻辑校验自动生成 <k> 条

| # | 断言（二值，可机械判定） | 来源 | 级别 |
|---|------------------------|------|------|
| A1 | 输出的公司/预算字段必须能在客户资料库原文找到出处 | 向导Q3=是 | 核心 |
| HF1 | 输出任何未提供的价格数字/量级 = 硬失败 | 向导Q5=否 | 一票否决 |
```

级别只有三档：**一票否决（HF）/ 核心 / 参考**。核心项失败超限或任一 HF 命中都过不了线（口径见 grading-protocol.md）。
