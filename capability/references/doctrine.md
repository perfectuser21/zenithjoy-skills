## 0. 总原则

**Activity 和能力只看业务事实；流程边界看约束加运行理由；用脚本还是 agent、现在是不是被一个脚本连着跑完，
都不影响判断。**

- Activity：干什么活、交出什么结果——业务事实，稳定。
- 能力：客户付钱买的结果——业务事实。
- 流程：一次运行怎么打包——**运行设计**，由约束（§6 条件①能不能放下）和选择（§6 条件②有没有分开跑的理由）
  两部分构成，不是纯业务事实。所以流程画错了代价很小，重新打包就行，**不用动 Activity**。
- 「谁做」（人 / agent / 脚本 / 哪台机器）、执行器怎么编排，是属性或实现，不决定层级。

## 1. 六层与核心定义

```
部门（含子部门）
 └─ 价值流   一条端到端为客户或业务创造价值的线
     └─ 能力   客户付钱买的那个结果
         └─ 流程   一次运行的编排单位：一个触发 + 一次有始有终的运行，把若干 Activity 串起来，结果进表
             └─ Activity   一段业务工作：有明确输入，交出能验收的结果，后面失败可从它的起点重来
                 └─ Step   Activity 里面的具体动作；交不出能验收结果的都是 Step
```

**Activity（定稿原文）**：一段业务工作。有明确的输入，做完交出一个能验收的结果；后面失败时，可以从它的
起点重来。它不会自己启动，只在某个流程的一次运行里被执行；同一个 Activity 可以被多个流程用。交不出能验收
结果的，是 Step。Activity 的边界只看「干什么活、交出什么结果」，是稳定的。

**流程（定稿原文）**：一次运行的编排单位。由一个触发和一次有开始、有结束的运行组成，把若干个 Activity
按顺序串起来，中间可以有逐个处理的循环、分支和失败策略，最后把结果放进表里。执行器负责跑，Commander
盯每一次运行。

| 层 | 一句话定义 | 落在哪（Brain 真表） |
|---|---|---|
| 部门 | 组织归属；价值流挂在部门（可以是子部门）下 | `areas`（`parent_area_id` = 上级部门） |
| 价值流 | 一条端到端为客户或业务创造价值的线，挂在部门（可以是子部门）下 | `value_streams`（`area_id` → 部门） |
| 能力 | 客户付钱买的那个结果；平台默认只是走法（§5） | `capabilities`（`parent_journey_id` → 价值流） |
| 流程 | 见上方定稿原文；边界按 §6 两条件 | `workflows`（`capability_id` → 能力） |
| Activity | 见上方定稿原文；边界按 §7 问题二 | `activities`；在流程里的位置只认 `workflow_activity_refs`（`sequence_no`），视图 `activity_placement` |
| Step | Activity 里面的具体动作（点发送、往下翻一页） | `steps`（`activity_id` → Activity；真身在仓库 step-dod.json） |

执行器（现在是 wf-run.sh、outreach-tick.sh 这类脚本）是实现，不是层级。一次运行的账：`runs`（一个流程的
一次运行）+ `spans`（其中每个 Activity / Step 的一次执行），见 §9。

**层与属性分开记**：「谁来执行」（`activities.executor_kind`）是 Activity 的属性；「触发」「时长预算」
「失败策略」是流程的属性；「实现进度」（现在走代码 / AI / 混合，目标是什么）记在 Step 层（§10）。

## 3. 判定链（任何东西丢进来，从上往下问）

```
它是一条端到端为客户或业务创造价值的线吗（装得下多个能力，没有单一触发）？
 ──是→ 价值流（挂到哪个部门）
 └─否→ 是客户付钱买的那个结果、三问法全过吗？（平台不同默认不算）
     ──是→ 能力（挂到哪条价值流）
     └─否→ 它是一次有触发、有始有终的运行，把若干 Activity 串起来、结果进表吗？
         ──是→ 流程（挂到哪个能力；和相邻流程的边界按 §6 两条件定）
         └─否→ 它有明确输入、交出能验收的结果、后面失败能从它的起点重来（问题二）吗？
             ──是→ Activity（排进哪个流程第几位；已存在就共用）
             └─否→ 塌了会让多个能力变红吗？
                 ──是→ 横切件
                 └─否→ 是看护作业（监工 / 巡检 / 日报 / 保活）吗？
                     ──是→ 拆成各自的流程，挂到「系统看护」；**不挂成被看护流程的步骤**
                     └─否→ 是一句口号（没有输入、交不出可验收结果）吗？
                         ──是→ 改成某个 Activity 或能力的承诺
                         └─否→ Step（归到某个 Activity 里）
```

**先装地图铁律**：跑判定链之前必须先装载现有六层全树（/capability Step 0）。结论必须落成
**格子坐标**（§2），禁止在真空里判——已在树上的东西绝不重新发明。同时核验锚点健康：挂空 / 挂 deprecated /
悬空外键一律标失锚。

## 4. 价值流判定

**价值流 = 一条端到端为客户或业务创造价值的线，挂在部门（可以是子部门）下。**

| 判据 | 过 = 价值流 | 不过 |
|---|---|---|
| 有自己的价值接收方 | 智能获客 = 要线索的老板；工厂 = 主理人 | 接收方与别的价值流完全重合 → 同一条 |
| 能独立考核 / 独立成交付 | 「智能获客」可单独卖 | 「看懂图片」不能 → 不是价值流 |
| 装得下一个或多个能力 | 获客装 智能获客 / 直播获客 … | 只是某个能力的一段 → 下沉 |
| 没有单一触发器和终点 | 价值流是一组能力的家 | 说得出「X 发生 → 拿到 Y」→ 是能力不是价值流 |

关键区分：**能画出起点和终点的东西不是价值流，是能力。** 下面一个在用的能力都没有 = 空壳价值流（巡逻筛子⑤）。

## 5. 能力判定：客户买的结果 + 三问法 + 两把尺子

**能力 = 客户付钱买的那个结果。** 例：智能获客（客户买的是「每天一批找到并私信过的意向客户」）。

- **找法不同不是能力**：关键词、对标只是「发现」的不同找法。
- **平台默认只是走法**：用流程来区分，流程名带平台前缀（「抖音·视频发现」「小红书·视频发现」）。
  只有某个平台**单独售卖、单独交付**时，才把它单独列成一个能力。

### 三问法（判断「是不是一个独立能力」）

1. **独立触发**：它有自己的起点（什么事发生了系统要动）吗？
2. **独立交付可见结果**：走完客户拿到一个看得见、愿意为之付钱 / 会出现在交付清单上的结果吗？
3. **独立验收**：不依赖别的能力跑完，就能对这个结果写断言验收吗？

三问全过 → 独立能力；任一不过 → 不是能力（是流程、Activity、共享前置或横切件）。

### 两把尺子

**尺子①「客户为什么而来」→ 定能力的边界。** 能不能对客户说「我们现在能做到 X 了」且客户因此点头？
- 「我们能每天替你找到并私信一批意向客户了」→ 点头 ✅ → 能力
- 「我们能采集抖音评论了」→「那然后呢？」❌ → 只是某个流程里的一段

**尺子②「走完拿到的结果是不是同一个」→ 定加厚 vs 分开。**
- 同一个结果、只是输入 / 找法 / 平台 / 覆盖面不同 → **加厚**，同一个能力（多加几个流程即可）
- 结果本身不同，或单独售卖、单独交付 → 不同能力

**能力级的东西只有三样不住在 Activity 里**：① 能力级端到端断言（漏斗 / 成功率 / SLO）② Gate 前置门
（授权文书 / 技术可行性，任一不过整条停）③ 横切件（服务多个能力，塌了多个能力变红）。

**FR / NFR 归属**：FR = Activity 承诺 + 分支；Activity 级 NFR（并发 / 断网 / 恢复）= 该 Activity
场景格断言；流程级 NFR（一次运行的时长预算 / 成功率）= 流程断言；能力级 NFR（端到端漏斗 / SLO）=
能力终点断言；系统级 NFR = 横切件。

## 6. 流程边界：两条件

**默认放在同一个流程里。下面两条同时满足，才断开成两个流程：**

- **① 能放下**：中间结果已经进表，停几个小时也不用返工。
- **② 有分开跑的理由**，至少满足一条：
  - **节奏不同**（每天 1~2 次 vs 一天多轮 vs 全天按额度）
  - **用的资源不同**（占手机和不占手机算资源不同；不同机器、不同账号、不同 App 也算）
  - **一对多或多对一**（一次发现喂多轮处理；一条线索按号的额度分批发）
  - **中间要等人**（审核、拍板）

**① 不满足的，必须放在同一个流程里**（一停就要返工，或正占着手机、开着 App、持有设备锁）。
① 满足但 ② 不满足 → 仍是同一个流程（总是连着跑，资源和节奏都一样，没有分开的理由）。

**流程边界是运行设计**：① 是约束，② 是选择。所以它不是纯业务事实；画错了代价很小，重新打包就行，
不用动 Activity（Activity 的边界由 §7 定，稳定不变）。

**接缝样例表**

| 接缝 | ① 能放下 | ② 分开跑的理由 | 结论 |
|---|---|---|---|
| 打开抖音 → 发私信 → 关闭抖音 | ✗（开着 App、持有锁） | — | 同一流程 |
| 获客：发现 → 处理 | ✓ | 节奏不同 | 断开 |
| 获客：判定 → 采集 | ✗（要重新打开视频） | — | 同一流程 |
| 获客：采集 → 评分 | ✓ | 资源不同（评分不占手机） | 断开 |
| 获客：评分 → 触达 | ✓ | 一对多 + 按号的额度 | 断开 |
| 视频剪辑：转录 → 场景 → 字幕 → BGM → 输出 | ✓ | ✗（总是连着跑，资源和节奏都一样） | 同一流程，6 个 Activity |
| 安卓发布：各平台之间 | ✓ | 资源不同（不同账号、不同 App） | 每个平台一个流程 |

流程的其他要件：一个触发（定时 / 事件 / 从表里取待处理）、一次有开始有结束的运行（时长预算）、若干 Activity
按顺序串起来，可以有逐个处理的循环、分支和失败策略，最后把结果放进表里。

## 7. 问题二：定 Activity（不变）

> **做到这里，有没有一个能验收的结果，并且后面失败时可以从这里重来、不用从头？**

- **有** → 这里是一个 Activity 的终点。
- **没有** → 只是 Step。

解释：
- **明确的输入**：Activity 知道从哪里拿什么（表里的待处理行、上一个 Activity 的结果）。
- **能验收的结果**：业务上可见、能读回（写进表、发出消息、拿到锁、确认了账号）；只在日志 / 进程内存里的不算。
- **能从起点重来**：后面坏了，从这个 Activity 的起点重做即可，不用退回流程开头。
- Activity **不会自己启动**，只在某个流程的一次运行里被执行；可以被多个流程共用（预检 = 打开 App、拿锁、
  确认账号；收尾 = 关 App、放锁）。共用 = 同一行多条 `workflow_activity_refs` 引用，禁复制。
  共享 Activity 的合同（承诺 / 输入 / 输出 / 读回）一改就牵动所有引用方，改法见 §19。
- **承诺式要求**（保留）：每个 Activity 一句承诺（`activities.promise`）——「做完后业务上多了什么」，配
  可执行读回（§13）。**反过来，只有一句口号、没有输入、交不出可验收结果的「Activity」不成立，应改成承诺**（§17）。
- 数量不设上下限：由问题二扫出来多少就是多少。

## 8. Step 判定

**Step = Activity 里面的具体动作**，比如点「发送」、往下翻一页、输入关键词、等元素出现。

- 判据：问题二不过——做到这里交不出能验收的结果，或后面失败时不能从这里重来。
- Step 照样要有读回（`steps.readback`），用来定位坏在哪一步，不是独立交付。
- **实现进度记在 Step 层**：每个 Step 现在走代码 / AI / 混合，目标是什么（§10）。
- 名字像机械动作的 Activity、只有 1 个 Step 的 Activity，多半是被抬错层的 Step（巡逻筛子②）。

## 9. 流程与一次运行

- **一次运行 = 一个流程从触发到结束跑一遍**：有开始、结束、时长预算；`runs` 记一条，其中每个 Activity
  的执行在 `spans` 各记一条。
- **跨流程的端到端漏斗**用交接物 id 串（视频 id → 评论 id → 线索 id），是能力级断言，不是某个流程的运行。
- **执行器顺序跑多个流程时**（例如一个脚本把几个流程连成一轮），账上仍按流程各记各的运行。

## 10. agent 换成代码

把某段从 agent 换成脚本（或反过来），**层级不动**：

1. **Activity 合同不变**：输入、承诺、输出、读回原样保留。
2. **同一套读回探针必须照样通过**——这就是换实现的验收（七动作里的「置换」，§16）。
3. **变的是「谁来执行」和 Step 粒度**：`executor_kind` 改；Step 可能变多变细。
4. **实现进度记在 Step 层**。
5. 换实现后资源 / 节奏变了，可以按 §6 重新打包流程——Activity 不动；发现中间多了能验收、能重来的结果，
   才按问题二拆 Activity。

## 11. 样板：智能获客（+ 对照：安卓多平台发布、视频剪辑）

```
能力：智能获客（客户买的结果：每天一批找到并私信过的意向客户）
  流程：抖音·视频发现（关键词 / 对标两种找法）   每天 1~2 次
      预检 → 取关键词 → 搜索取视频（逐个词，按"最新"往下翻 20 个）→ 过滤去重 → 写视频表 → 收尾
  流程：抖音·视频处理   一天多轮，从视频表取「待判定」
      预检 → 判定视频（逐个）→ 采集评论（只采合格的）→ 收尾
  流程：抖音·评论评分   有新评论就跑，不占手机
      取待评分评论 → 打分（逐条）→ 标记人 → 写线索表
  流程：抖音·线索触达   全天，按每个号的额度
      预检 → 取线索 → 发私信（逐条，按额度）→ 回填 → 收尾
```

以后加小红书，就是再加几个「小红书·…」流程，能力不变。关键词 / 对标是「抖音·视频发现」的两种找法，
不是两个能力。

**流程边界**：见 §6 接缝样例表的获客五行——发现 → 处理（能放下 + 节奏不同）、采集 → 评分（能放下 +
评分不占手机）、评分 → 触达（能放下 + 一对多、按号额度）断开；判定 → 采集、打开抖音 → 发私信 → 关闭
放不下，同一流程。

**问题二：哪些是 Activity、哪些是 Step**

| 段 | 能验收的结果 | 后面失败能从这里重来吗 | 结论 |
|---|---|---|---|
| 预检 | 抖音已打开、拿到设备锁、确认了账号 | 能 | Activity（发现 / 处理 / 触达共用） |
| 判定视频 | 每个视频的判定结果写回视频表 | 能（采集失败不用重判） | Activity |
| 发私信 | 每条线索的发送结果（已发 / 受限 / 失败） | 能（回填失败不用重发） | Activity |
| 收尾 | 抖音已关闭、锁已释放 | 能 | Activity（三个流程共用） |
| 点「发送」 | 交不出单独可验收的结果 | 不能（要从这条私信头上重来） | Step（属于「发私信」） |
| 往下翻一页 | 没有 | 不能 | Step（属于「搜索取视频」） |

**去重规则**
- **视频去重在发现阶段**：先按「标题 + 作者」过滤，取到链接后再按视频 id 确认，同时排除自家账号的视频。
- **人不删，只标记**：已触达过、多次出现（多次出现的可以调高意向等级）。

**现状**：目前 wf-run.sh 把发现 / 处理 / 评分连成一轮顺序跑完，属于「一个执行者顺序跑多个流程」；树按 4 个
流程登记，实现以后再拆。生产库现在把「关键词获客」「对标获客」登记成两个能力、各一个 8 段流程，按本标准待改。

**对照样例一：能力「安卓多平台发布」**

```
能力：安卓多平台发布
  流程：抖音·视频发布      预检 → 上传填写 → 发布 → 读回 → 收尾
  流程：小红书·视频发布    预检 → 上传填写 → 发布 → 读回 → 收尾
  流程：快手·视频发布      …（每个平台一个流程，结构相同）
```

各平台之间能放下，且资源不同（不同账号、不同 App）→ 每个平台一个流程；预检、收尾共用；平台不单独售卖，
所以仍是一个能力。

**对照样例二：视频剪辑流水线**

转录 → 场景 → 字幕 → BGM → 输出，接缝都能放下（中间结果进表），但总是连着跑、资源和节奏都一样，没有分开
跑的理由 → **同一个流程，6 个 Activity**。

**共享 Activity 合同变更实例（§19）**：这次重组中，「判定」的输入从「刚打开的视频」换成「视频表里待判定的视频」，
换了输入来源，属于**不兼容变更**。引用方只有原来的「抖音·关键词获客」「抖音·对标获客」两个流程，两个一起切到
新结构（「抖音·视频处理」）；旧流程保留到脚本切换完成，期间新旧两版并存，切完验证读回通过后旧版退役。

**错误画法**

| 错误 | 为什么错 |
|---|---|
| 一个流程从预检串到触达 | 发现 → 处理、采集 → 评分、评分 → 触达三个接缝两条件都满足，应断开（§6） |
| 把关键词获客、对标获客画成两个能力 | 只是发现的找法不同，客户买的结果一样（§5） |
| 把抖音获客、小红书获客画成两个能力 | 平台默认只是走法，用「平台·…」流程区分（§5） |
| 因为 wf-run.sh 一口气跑完几个流程，就画成一个流程 | 执行器怎么编排不影响判断（§0） |
| 把判定视频和采集评论拆成两个流程 | 判定 → 采集放不下：停了要重新打开视频（§6 条件①） |
| 视频剪辑每个环节拆一个流程 | 能放下但没有分开跑的理由（§6 条件②） |
| 把点「发送」、往下翻一页画成 Activity | 交不出能验收、能从这里重来的结果（问题二） |
| 把监工、巡检、日报挂成流程里的步骤 | 看护作业各有触发，拆成各自的流程，挂「系统看护」（§3、§17） |
| 去重时把重复出现的人删掉 | 人不删只标记，多次出现是意向信号 |

## 12. 反模式（90% 误判栽在这）

1. **「难」≠「能力」**：难度量工作量，不量层级。
2. **「找法 / 平台 / 输入不同」≠「不同能力」**：结果相同 → 加厚，多加流程即可。
3. **「一个脚本跑完」≠「一个流程」**：执行器怎么编排不影响判断（§0）。
4. **「能放下」≠「必须断开」**：还要有分开跑的理由（§6 条件②）。
5. **「动作」≠「Activity」**：点击、翻页、输入是 Step（§7、§8）。
6. **「口号」≠「Activity」**：没有输入、交不出可验收结果的一句话，是承诺，不是 Activity。
7. **「看护」≠「步骤」**：监工 / 巡检 / 日报 / 保活拆成各自的流程，挂「系统看护」。
8. **「定时作业桶」≠「流程」**：各任务各自有触发、互相不串起来，就不满足流程定义。
9. **「只有我这个流程要」≠「改共享 Activity」**：一个流程的特殊口径另建 Activity（分叉），不动共享的那个（§19）。

## 13. 承诺与验收断言

- 每个 Activity 承诺配**可执行验证**的读回锚点（psql / UIA 读回 / 截图 / API 查询 / log 正则），
  禁「功能正常」类空话。断言写在 **Activity 上**，不写在需求本身上。
- 每个流程配一次运行的断言（时长预算内结束、失败策略生效）；能力终点配端到端漏斗断言。
- 接缝 Activity（碰真机 / 生产 env / 真实第三方）验证等级必须 **L3 真机真验**；纯前端交互可 L1 替身；
  真 DB 写入 L2 服务端真验。降级需证据。
- 「得体 / 像人 / 有分寸」类软承诺：eval 集 + LLM judge + 人工抽样，表上显式标**「软」**。
- 读回是**换实现的验收**（§10）。

## 14. 场景牌组（承诺 × 场景矩阵，防「只想了晴天」）

每个 Activity 过固定八格：**首次使用 / 日常运行 / 重启恢复 / 断网弱网 / 并发洪峰 /
对抗输入 / 平台改版 / 凭据过期**。

每格二选一：一条具体断言，或 `N/A + 理由`。**空格 = 红灯**。

## 15. 归位判定链（新东西该挂哪）

按序过五关，禁跳步：

1. **频率判据**：它发生的频率 = 目标流程的触发频率吗？一次性的事禁进高频流程。
2. **三问法**（§5）：全过 → 它自己是个能力，转划分 / 设计。
3. **问题二 + 流程两条件**（§7 / §6）：有输入、能验收、能重来 → Activity（已有同类 → 共用），再按两条件决定
   放进哪个流程或新开流程；都不是 → 某个 Activity 里的 Step；只是一句口号 → 改成承诺。
4. **四问归家**：新能力 / 共享前置（一次性进场链归「客户首次成功路径」能力，业务流程用依赖标签引用，
   禁复制进各流程开头）/ 横切件（必须答出「塌了哪些承诺会变红」，答不出 = 不该做）/
   工厂件（不挂业务价值流，归工厂价值流自己的家，决策 2d28de45）。
5. **归位裁决单**：`部门 · 价值流 · 能力 · 流程 · Activity（· Step）· 场景格 ＋ 动作类型（七动作之一）
   ＋ 验收断言锚点`。拿不准的列「待拍板问题清单」，不硬填。

## 16. 七动作总表（动树的合法动作类型）

| 动作 | 定义 | 关键规则 |
|------|------|----------|
| 贯穿 | 新流程 thin 端到端走通 | 先通后厚（= Walking Skeleton） |
| 加厚 | Activity 覆盖更多场景格 / 读回从缺到有 / Step 从 AI 走到代码 / 能力多一个平台或找法的流程 | 四种材料：能力 / 体验 / NFR / 守卫 |
| 修复 | Activity 读回从绿掉回红，补回去 | hotfix + 复现断言永久进 CI，禁事后删 |
| 重新打包 | 按 §6 两条件重划流程边界，Activity 不动 | 代价小；主理人拍板 |
| 改流程结构 | 增删 / 重排流程里的 Activity | 主理人拍板；稀有 |
| 退役 | 下线一个流程 / Activity / 能力 | 先减肥再增肌，不与新增混一次提交 |
| 探索 spike | 写不出承诺的试错调研 | timebox；产出 = 结论喂回切分；禁伪装成贯穿 |
| 置换 | 承诺零变化的底层换实现（含 agent 换代码） | 验收 = 同一套读回 绿 → 短暂红 → 绿 + 迁移 SOP |

共用三规则：**首用即出生**、**复用即引用**（语义查重，第二个流程用到就加一条 `workflow_activity_refs`，
禁重建）、**瓶颈才加厚**。改共享 Activity 的合同按 §19 走（兼容升小版本 / 不兼容发大版本逐个切 / 只一个流程要就分叉）。

## 17. 巡逻模式（同一把尺子定期审查全树）

进门判定管新东西，巡逻管存量。两者**同一套标准**，不另立口径。

**第一遍：规则筛**（机器跑，SQL 见 /capability SKILL.md Mode D）

| 筛子 | 疑点 | 第二遍怎么判 |
|---|---|---|
| ① 没有 Activity 的流程 | 空壳，或其实是定时作业桶 / 看护 | §1 流程定义 + ⑧ |
| ② 名字像机械动作的 Activity（或只有 1 个 Step） | Step 被抬成了 Activity | 问题二 |
| ③ 同名跨层（去掉「X · 」前缀后同名出现在两层） | 同一个东西画了两遍，或找法 / 平台被画成能力 | §5 |
| ④ 挂在流程上的看护定时项 | 看护作业被当成业务流程或步骤 | §3：拆成各自流程挂「系统看护」 |
| ⑤ 空壳价值流 / 空壳能力 | 只有名字没有内容 | §4 / §5 |
| ⑥ 只有 1 个 Activity 的流程 | **仅提醒** | 两条件：它和相邻流程是否其实该合并 |
| ⑦ 7 个及以上 Activity 的流程 | **仅提醒** | 两条件：有没有该断开的接缝（视频剪辑这种连着跑的就是对的） |
| ⑧ 名为「定时作业」的桶 | 各任务各自有触发、互相不串起来，按 §1 流程定义不成立 | 拆成各自的流程；看护类挂到「系统看护」 |
| ⑨ 口号式 Activity（没有输入、交不出可验收结果，只是一句承诺） | 不是 Activity | 判为「应改成承诺」，挂到对应 Activity 或能力上 |
| ⑩ 共享 Activity 合同变更失控 | (a) 被 ≥2 个流程引用的 Activity 合同变了，却没有影响表或版本号；(b) 同一个 Activity 被多个流程引用，各流程绑的版本不一致，且已超过过渡期 | §19：补影响表 / 版本号；过渡期超时的催切或分叉 |

⑩ 的机器部分：查 `workflow_activity_refs.activity_definition_version_id`（每条引用绑的合同版本），同一 Activity
下版本数 > 1 或有引用未绑版本即命中。**暂不支持、改为人工核对的部分**（需要的字段）：
- semver 版本号——现在版本只有 `activity_definition_versions.contract_sha256`，需要 `semver` 字段（或合同 payload 里的
  `contract.version`）；
- 影响表——需要一处存放（例如 `activity_contract_changes` 表：activity_id、from_version、to_version、change_kind、
  impact jsonb、approved_by），或至少一条 decisions 记录引用；
- 过渡期——需要 `sunset_at`（旧版本计划退役时间），否则「超过过渡期」只能人工判断。

**第二遍：逐项判定**——流程边界按 §6 **两条件**（① 能放下 且 ② 有分开跑的理由，默认同一流程），Activity
按问题二，再过 §3 判定链 / §5 能力边界（平台默认是走法）。筛中不等于错，判对的写「对」并给一句理由。

**输出**（每项一行）：

| 坐标 | 现在挂在哪 | 结论 | 建议挪到哪 | 理由（两条件 / 问题二 / 引用 §） |
|---|---|---|---|---|

**只提建议、不自动挪**，由主理人拍板；拍板后按 db-update 规范落库。

## 18. 设计模式：预先拆结构

设计新东西（一个新想法，或一份现有脚本）时，用同一把尺子**先拆好结构再动手**，按顺序输出：

1. **能力是什么**：客户买的结果（§5）；平台默认是走法，不单列能力。
2. **列段**：把整件事按时间顺序列成一串「段」。
3. **流程边界**：对每个接缝按 §6 两条件判——① 能不能放下、② 有没有分开跑的理由（节奏 / 资源 / 一对多·多对一 /
   等人）；两条都满足才断开，否则同一流程。断开处写明接住结果的表。流程名带平台前缀。
4. **问题二**：每个流程内对每段问「有没有明确输入、能验收的结果、后面失败能从这里重来」，得出 Activity 和 Step。
5. **共用**：先查树上已有的 Activity，列出哪些可以和已有流程共享（预检 / 收尾这类最常见）。复用已有 Activity 时，
   先核对合同（输入来源、输出去向）是否一致；不一致，就按 §19 判断是兼容、不兼容还是分叉。
6. **每个流程的运行面**：触发（定时 / 事件 / 从表里取待处理）、一次运行的时长预算、交接表（从哪张表取、
   写到哪张表）、逐个处理的循环、分支与失败策略。

产出格式见 /capability SKILL.md Mode E。现有脚本若把多个流程连着跑，照样按两条件划分，并注明
「现状：一个执行者顺序跑」。流程划分是运行设计，可以后续重新打包，Activity 不动。

## 19. 共享 Activity 的合同变更

Activity 是共享的（§7）：改了它的输入输出，可能把引用它的其他流程搞坏。所以 Activity 有合同、合同有版本，
改合同按类型走。

**合同** = 四项：
1. **承诺**：做完后业务上多了什么；
2. **输入**：字段 + 来源（从哪张表 / 哪个上游 Activity 来）；
3. **输出**：字段 + 去向（写到哪张表 / 交给谁）；
4. **读回**：验收探针。

合同有版本号，semver 口径（主版本.次版本.修订）。

**三类变更**

| 类型 | 例子 | 处理 |
|---|---|---|
| 兼容 | 只是多输出一个字段；输入多接受一种格式；读回探针加严，但现有运行仍能通过 | 升小版本，所有引用它的流程直接用新版本 |
| 不兼容 | 改字段名、删字段、改字段含义、换输入来源（比如从「刚打开的视频」换成「视频表里待判定的视频」）、读回口径变了 | ① 先列出所有引用它的流程（`/api/brain/activities/<id>/consumers`，或查 `workflow_activity_refs`）；② 发新的大版本；③ 每个流程逐个切到新版本，切完验证读回通过；④ 最后一个流程切完，旧版本才退役。过渡期新旧两版并存。运行记录绑定的是当时用的版本（`run_definition_bindings` / `activity_definition_versions`） |
| 只有一个流程有需要 | 某个流程要特别的判定口径 | 不改共享的那个 Activity，另建一个新 Activity（分叉），名字或说明里注明和原来的区别 |

**硬规矩：先出影响表，再改。** 改任何被两个及以上流程引用的 Activity 的合同，之前必须产出一张「影响表」；
**没有影响表就不能改**。

| 引用它的流程 | 兼容 / 不兼容 | 怎么切（直接用新版 / 切到大版本 x.0.0 / 分叉成新 Activity） | 谁验收（读回探针 + 验收人） |
|---|---|---|---|
| … | … | … | … |

实例见 §11（「判定」输入来源换了 → 不兼容 → 两个引用流程一起切）。接入点：巡逻筛子⑩（§17）、
capability-reviewer 打回项、设计模式第 5 步（§18）。

## 20. 铁律与例外

- **拍板前绝不写库**——树 / 裁决单 / 巡逻报告 / 设计稿是给主理人审的草案，不是既成事实。
- **止血例外**：生产事故可先斩后奏，但 24h 内补归位裁决单，钉红灯状态进账本。
- **账本写入必须是流水线自动副作用**——设计里出现「记得手动更新账本」= 该设计判死刑。
- **共享 Activity 改合同先出影响表**（§19）——没有影响表不许改。
- **一句话内核**：能力 = 客户买的结果（平台默认是走法）；Activity = 有输入、交出能验收结果、能从起点重来的
  一段业务工作；流程默认合在一起，只有「能放下 + 有分开跑的理由」才断开；其余是 Step。

## 附 A. 名词来历

- **Golden Path 为什么退役**：业界 Golden Path（Spotify 2020，平台工程）是给工程师铺的推荐建软件路线；
  我们家曾借这个词指「客户为一个完整价值结果而走的承诺序列」。借词不借义造成长期混淆，决策 a340f100 改称
  能力；v2.0（决策 0cee5452）拆成 能力 + 流程；v3.0（决策 c63688cf）引入两个问题；v3.1（决策 eb9f8f77）
  定稿 Activity / 流程定义，流程边界改为两条件、平台默认是走法。
- **Walking Skeleton / 贯穿**：一个流程第一次 thin 端到端跑通的动作。
- **Happy Path 与 smoke 的分工**：验收测试（建流程时）跑全场景八格，全绿才算通；smoke 守卫（通了之后）每天
  只走晴天剧本，回答「今天还通吗」。一个流程配**分段** smoke（按 Activity 独立坏，红灯要能指到断点）。
- **来源谱系**：流程两条件对应工作队列 / 持久化检查点边界（BPMN 的等待与消息事件、Temporal 的 workflow 边界）
  加运行设计取舍；问题二对应可重试的 Activity（Temporal）与 APQC PCF 的可度量工作单元；Story Mapping
  backbone（Patton）、Walking Skeleton（Cockburn）、Design by Contract、SRE、BDD + 混沌工程（场景牌组）、
  Team Topologies（四个家）。组装方式是自家的。
