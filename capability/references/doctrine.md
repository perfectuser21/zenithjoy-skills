## 0. 总原则

**层级按「做成了什么」判，不按「谁做、怎么做」判。**

- 「谁做」（人 / agent / 脚本 / 哪台机器）、「怎么做」（同步 / 异步 / 定时 / 捞池子 / 代码 /
  AI）都是**属性**，写在对应层的列上，**不决定它是哪一层**。
- 判层只看它交付出的结果：对外能说「我们能做到 X」的是能力；一条从触发走到客户可见结果的
  走法是流程；一段有承诺、能读回验收的工作是 Activity；单拿出来不构成交付的机械动作是 Step。

## 1. 六层与每层一句话定义

```
部门（含子部门）
 └─ 价值流   一条端到端为客户或业务创造价值的线
     └─ 能力   能对外说「我们能做到 X」，客户为它而来
         └─ 流程   兑现某个能力的一种走法：Activity 按业务顺序从触发走到客户可见的结果
             └─ Activity   流程里的一段工作，有承诺、能读回验收，可被多个流程共用
                 └─ Step   Activity 内部的机械动作，单拿出来不构成交付
```

| 层 | 一句话定义 | 落在哪（Brain 真表） |
|---|---|---|
| 部门 | 组织归属；价值流挂在部门（可以是子部门）下 | `areas`（`parent_area_id` = 上级部门） |
| 价值流 | 一条端到端为客户或业务创造价值的线，挂在部门（可以是子部门）下 | `value_streams`（`area_id` → 部门） |
| 能力 | 能对外说「我们能做到 X」，客户为它而来。三问法：独立触发、独立交付可见结果、独立验收（§5） | `capabilities`（`parent_journey_id` → 价值流） |
| 流程 | 把 Activity 按业务顺序排起来，从触发走到客户可见的结果，兑现某个能力的一种走法 | `workflows`（`capability_id` → 能力） |
| Activity | 流程里的一段工作，有承诺、能读回验收，可被多个流程共用 | `activities`；在流程里的位置只认 `workflow_activity_refs`（`sequence_no`），视图 `activity_placement` |
| Step | Activity 内部的机械动作，单拿出来不构成交付 | `steps`（`activity_id` → Activity；真身在仓库 step-dod.json） |

一次运行的账：`runs`（一次运行）+ `spans`（一次运行里每个 Activity / Step 的一次执行），见 §9。

**层与属性分开记**：「怎么启动」（跟着上一步 / 定时 / 捞池子 / 事件）是 Activity 的属性；
「谁来执行」（`activities.executor_kind`：code / agent / 混合 / 人）是 Activity 的属性；
「实现进度」（现在走代码 / AI / 混合，目标是什么）记在 Step 层（§10）。

## 2. 旧词 → 新词对照表

| 旧词 | 新词 / 处置 | 说明 |
|---|---|---|
| Line / 线 / 业务线（当层级用） | **价值流**（挂部门下） | 「一门生意」的意思由 部门 + 价值流 承接；Line 不再作为层级名 |
| 路 / Golden Path / GP / 大 Ability | **能力**（Capability） | 「一种触发 → 客户付钱的终点」的判法（三问法、两把尺子）原样保留在 §5 |
| 一条路的具体走法（渠道 / 形态） | **流程**（Workflow） | 旧体系没有这一层，常把它和路混在一起 |

| 挂片（价值件 / 使能件 / 小 ability / Feature） | **已退役**：工序细节 → **Step**；多流程共用的一段 → **共用 Activity**；多能力共用的底座 → **横切件** | 「挂片」一词不再使用 |
| 工序 / 动作 | **Step** | |
| 格子坐标 `line · 路 · 步 · 格` | `部门 · 价值流 · 能力 · 流程 · Activity（· Step）· 场景格` | |
| 承诺 | 承诺（不变），写在 Activity 的「承诺」列（`activities.promise`） | |
| journeys 表 | **已下线**为只读兼容视图；读 `value_streams` / `capabilities` | 迁移 520 拆表、529 下线父表 |
| `golden_paths` 表、`golden_path_proposal` task_type、`/golden-paths/*` 接口 | 保留为「能力提案管线」的机器名，**不改** | 机器名不随词汇改，避免断链；对人一律说「能力提案」 |
| 工序词黑名单（识别 / 判定 / 检测…不得当步名） | **已退役**，由 §7 三测试取代 | 「判定」能不能当 Activity 看三测试，不看它是不是动词（§11 判定就是 Activity） |
| 四测试 T1–T4（可观察终态 / 失败可辨 / 可独立验收 / 可停顿） | 并入 §7 三测试 | T1+T3 → 测试②结果；T4 → 测试①交接 + 测试③重试；T2 → 测试②的「可读回」 |

**硬规则**：Line（作层级）/ Golden Path / 路 / 骨干步 / 挂片 / ability 全面退役，只在解释历史时作括号注解。

## 3. 判定链（任何东西丢进来，从上往下问）

```
它是一条端到端为客户或业务创造价值的线吗（装得下多个能力，没有单一触发）？
 ──是→ 价值流（挂到哪个部门）
 └─否→ 能对外说「我们能做到 X」、三问法全过吗？
     ──是→ 能力（挂到哪条价值流）
     └─否→ 是「兑现某个能力的一种业务走法」（从触发走到客户可见结果）吗？
         ──是→ 流程（挂到哪个能力；先问 §6 是不是真的业务走法不同）
         └─否→ 过 §7 三测试（交接 / 结果 / 重试）任一吗？
             ──是→ Activity（排进哪个流程第几位；已存在就共用）
             └─否→ 塌了会让多个能力变红吗？
                 ──是→ 横切件
                 └─否→ 是看护作业（监工 / 巡检 / 日报 / 保活）吗？
                     ──是→ 归看护它的那一层的运维属性，或归「系统运行保障」自己的能力；
                           **不挂成被看护流程的步骤**
                     └─否→ Step（归到某个 Activity 里）
```

**先装地图铁律**：跑判定链之前必须先装载现有六层全树（/capability Step 0）。结论必须落成
**格子坐标**（§2），禁止在真空里判——已在树上的东西绝不重新发明（教训：14 条清洗曾把图上已有的
F5 指挥舱、F3 夜间体检重新发明成新的）。同时核验锚点健康：挂空 / 挂 deprecated / 悬空外键一律标失锚。

## 4. 价值流判定

**价值流 = 一条端到端为客户或业务创造价值的线，挂在部门（可以是子部门）下。** 回答
「我们在哪条线上创造价值」，不回答「事情怎么走」。

| 判据 | 过 = 价值流 | 不过 |
|---|---|---|
| 有自己的价值接收方 | 智能获客 = 要线索的老板；工厂 = 主理人 | 接收方与别的价值流完全重合 → 同一条 |
| 能独立考核 / 独立成交付 | 「智能获客」可单独卖 | 「看懂图片」不能 → 不是价值流 |
| 装得下一个或多个能力 | 获客装 关键词获客 / 对标获客 / 直播获客 | 只是某个能力的一段 → 下沉 |
| 没有单一触发器和终点 | 价值流是一组能力的家 | 说得出「X 发生 → 拿到 Y」→ 是能力不是价值流 |

关键区分：**能画出起点和终点的东西不是价值流，是能力。** 下面一个在用的能力都没有 = 空壳价值流（巡逻筛子⑤）。

## 5. 能力判定：三问法 + 两把尺子

**能力 = 能对外说「我们能做到 X」，客户为它而来。**

### 三问法（判断「是不是一个独立能力」）

1. **独立触发**：它有自己的起点（什么事发生了系统要动）吗？
2. **独立交付可见结果**：走完客户拿到一个看得见、愿意为之付钱 / 会出现在交付清单上的结果吗？
3. **独立验收**：不依赖别的能力跑完，就能对这个结果写断言验收吗？（拿掉它，别的旅程还走得通吗？）

三问全过 → 独立能力；任一不过 → 不是能力（是流程、Activity、共享前置或横切件）。

### 两把尺子

**尺子①「客户为什么而来」→ 定能力的边界。** 能不能对客户说「我们现在能做到 X 了」且客户因此点头？
- 「我们能做关键词获客了」→ 点头 ✅ → 能力
- 「我们能采集抖音评论了」→「那然后呢？」❌ → 只是某个流程里的一段（Activity）

**尺子②「走完拿到的结果是不是同一个」→ 定加厚 vs 分开。**
- 同一个结果、只是输入 / 覆盖面不同 → **加厚**，同一个能力（文字 / 图片 / 语音都是「顾客得到回复」）
- 结果本身不同 → 不同能力

**能力级的东西只有三样不住在 Activity 里**：① 能力 / 流程级端到端断言（「日 4 条、成功率 ≥90%」，
塞不进单个 Activity）② Gate 前置门（授权文书 / 技术可行性，第一个 Activity 之前，任一不过整条停）
③ 横切件（服务多个能力，塌了多个能力变红）。其余一切都住 Activity / Step 里。

**FR / NFR 归属**：FR = Activity 承诺 + 分支；Activity 级 NFR（并发 / 断网 / 恢复）= 该 Activity
场景格断言；流程级 NFR（端到端成功率 / SLO / 漏斗）= 流程终点断言；系统级 NFR = 横切件。

## 6. 流程判定与异步规则

**流程 = 把 Activity 按业务顺序排起来，从触发走到客户可见的结果，兑现某个能力的一种走法。**

1. **异步只是 Activity 的「怎么启动」属性**：跟着上一步、定时、捞池子、事件。它**不是拆流程的理由**。
2. **只有业务走法不同才拆成两个流程**，例如抖音关键词获客和对标获客（找视频的入口不同）；
   共同的 Activity（判定 / 采集 / 配送 / 评分 / 触达）**两边共用**，不复制。
3. **能力下只有 1 个流程属正常。** 别为了「看起来完整」硬造第二个。
4. **多个 agent 或脚本各自负责流程里的几段，不等于多个流程。** 执行体是「谁来执行」属性，
   不是层级（§0 总原则）。
5. 渠道 / 形态不同但 Activity 序列真不同（安卓真机发抖音 vs 发小红书）→ 可以是同一能力下的不同流程；
   序列一样只是参数不同 → 同一个流程，渠道是参数。
6. 没有 Activity 的流程 = 还没画完或根本不是流程（巡逻筛子①）。

## 7. Activity 判定：三测试

**Activity = 流程里的一段工作，有承诺、能读回验收，可被多个流程共用。**

依据：APQC PCF（Activity 是流程分类框架里「有输入输出、可度量」的工作单元）、BPMN（Task 的边界落在
交接与等待处）、Temporal（Activity 是可单独重试、有超时的持久执行单元）。

| # | 测试 | 问法 | 过 = Activity 边界 |
|---|---|---|---|
| ① | **交接** | 中间换执行者了吗？或者要等待（等池子、等定时、等事件）吗？ | 换人 / 要等的地方就是 Activity 边界 |
| ② | **结果** | 有业务上可见、可读回验收的结果吗（写进表、发出消息）？ | 有 → Activity；没有 → Step |
| ③ | **重试** | 能单独重跑、不用整条重来吗？ | 能 → Activity |

用法：
- 沿流程摊开候选片段，对每个相邻边界跑三测试；**测试①定边界、测试②定身份、测试③复核**。
  操作步骤与记录表模板见 `references/step-cutting.md`。
- 测试②的「可见」是**业务上可见**（写进一张业务表、发出一条消息、出现在中台），不要求终端客户
  亲眼看到；但只出现在日志 / 进程内存里的不算。
- 数量不设上下限：由三测试扫出来多少就是多少（获客样板是 7 个）。>10 个回头查有没有把 Step 当
  Activity；只有 1 个回头查是不是把整个流程当成了一个 Activity。
- **承诺式要求**（保留）：每个 Activity 必须有一句承诺（`activities.promise`）——「做完后业务上多了
  什么 / 谁拿到了什么」，配可执行读回（§13）。Activity 名可以是短动词（预检 / 判定 / 采集），
  但承诺句不许是「功能正常」式空话。
- 一个 Activity 被多个流程用到 → **共用同一行**（`workflow_activity_refs` 多条引用），禁复制。

## 8. Step 判定

**Step = Activity 内部的机械动作，单拿出来不构成交付。**

- 典型：打开页面、点击、输入、滑动、截图、等元素出现、调一次接口、写一条中间记录。
- 判据：三测试全不过——不换人不等待、没有独立的业务结果、单独重跑没意义（要从 Activity 头重来）。
- Step 照样要有读回（`steps.readback`：log 正则 / 截图 / 查表），那是 Activity 读回的分解，
  用来定位坏在哪一步，不是独立交付。
- **实现进度记在 Step 层**：每个 Step 现在走代码 / AI / 混合，目标是什么（§10）。
- 名字像机械动作的 Activity、只有 1 个 Step 的 Activity，多半是被抬错层的 Step（巡逻筛子②）。
  （0 个 Step 通常只是还没落 Step，不算层级信号。）

## 9. 一次运行怎么算

- **异步流程按「一批或一条线索走完全程」算一次运行**，用**交接物 id**（视频 id、线索 id）把各段串起来，
  看端到端漏斗（发现 N 个视频 → 判定通过 M 个 → 采集 K 条评论 → 落池 → 评分出 L 条线索 → 触达多少）。
- **runs 账里每个 Activity 的执行各记一条**（`runs` 记一次运行，`spans` 记其中每个 Activity / Step
  的一次执行），哪怕各段由不同执行体、在不同时间跑。
- 不要按「某个脚本跑了一轮」算一次运行——那是执行体视角，不是流程视角（§0）。

## 10. agent 换成代码

把某段从 agent 换成脚本（或反过来），**层级不动**：

1. **Activity 合同不变**：承诺、输入、输出、读回原样保留。
2. **同一套读回探针必须照样通过**——这就是换实现的验收（七动作里的「置换」，§16）。
3. **变的是「谁来执行」和 Step 粒度**：`executor_kind` 改；Step 可能变多变细（脚本比 agent 需要更多显式步骤）。
4. **实现进度记在 Step 层**：现在走代码 / AI / 混合，目标是什么。
5. **只有换实现时发现内部有交接或等待，才按测试①拆 Activity。** 单纯「代码写起来分了几个函数」不是拆的理由。

## 11. 样板：智能获客

**正确画法**

```
部门：增长获客部
 └─ 价值流：客户智能获客路径
     └─ 能力：关键词获客
         └─ 流程：抖音·关键词获客（只有这 1 个流程，正常）
             预检 → 发现 → 判定 → 采集 → 配送（落池）→ 评分 → 触达   （7 个 Activity）
             归位（关 App、放锁、回桌面、终态回执）= 运行收尾的 Step，不单独成 Activity
```

顺序以真实执行为准（2026-10-07 层级审计读 xian-m4 / MMV 脚本核实）：采集 → 配送（落池）→ 评分 → 触达。
生产库 `workflow_activity_refs` 里登记的「评分 → 配送」是反的，旧拍板文字里的「触达 → 配送」也不对。

执行者三类（执行者是属性，不是层级）：

| 执行者 | 负责的 Activity | 怎么被叫起来 |
|---|---|---|
| 采收脚本（xian-m4：harvest-keyword.sh / batch2.sh） | 预检 / 发现 / 采集 / 配送 | 定时：MMV 上 OpenClaw commander 定时发起 → wf-launch.sh → wf-run.sh（主触发）；xian 上 crontab harvest-cron 兜底，晚 15 分钟，pgrep 防重复 |
| 判定 AI、评分 AI（被同步调用，不是常驻 agent） | 判定：harvest-keyword.sh 逐个视频 `ssh mmv qualify-video.js judge` → judge-video.js；评分：batch2.sh 落池后立即 sort-comments.js → judge-comment.js | 跟上一步（同步调用） |
| 触达脚本（outreach-tick.sh） | 触达 | 捞池子：crontab 每 30 分钟从线索池捞（**全流程唯一真正异步的一段**） |

每个 Activity 的「怎么启动」：

| Activity | 怎么启动 | 执行者 |
|---|---|---|
| 预检 | 定时 | 采收脚本 |
| 发现 | 跟上一步 | 采收脚本 |
| 判定 | 跟上一步（逐个视频同步调 AI；判定接口故障留成 pending 的视频，等下次被搜到时重判） | 判定 AI |
| 采集 | 跟上一步（判为 matched 当场采评论，不等下一轮） | 采收脚本 |
| 配送（落池） | 跟上一步 | 采收脚本 |
| 评分 | 跟上一步（落池后立即调 AI） | 评分 AI |
| 触达 | 捞池子（每 30 分钟从线索池捞） | 触达脚本 |

一次运行 = 一批视频 / 一条线索走完全程，用视频 id、线索 id 串起来看漏斗（§9）；触达和前面不在同一轮，
靠线索 id 接上。对标获客是另一种业务走法（从对标账号找视频）→ 同一价值流下的另一个能力 / 流程，
判定 / 采集 / 配送 / 评分 / 触达**共用**同一批 Activity。

**判定为什么是 Activity（不是 Step、不是挂片）**：
- 换执行者：脚本 → AI（测试①）
- 有可验收结果：每个视频的 `judgment_status` 写回（如 matched、pending），能查表读回（测试②）
- 可单独重判：pending 或规则改了，可以只重判视频，不用重新搜索（测试③）

它是被同步调用的，不用等——但测试①只要换执行者就成立，「等待」不是必要条件。

**归位为什么是 Step**：关 App、放锁、回桌面、终态回执都是现场复原和运行外壳的动作，测试②没有业务上
可见的结果（不产生任何业务表的新记录、不对客户发出东西），单独拿出来不构成交付，所以记成运行收尾的
Step（也可以归到运行外壳），读回只用来确认现场干净。

**错误画法**

| 错误 | 为什么错 |
|---|---|
| 把执行体画成多个流程（「采收流程」「判定流程」「评分流程」「触达流程」） | 按「谁做」切了层（违反 §0）；多个执行体各负责几段 ≠ 多个流程（§6-4） |
| 因为触达是异步捞池子，就把它拆成独立流程 | 异步只是「怎么启动」属性（§6-1） |
| 把被同步调用的判定 AI / 评分 AI 当成独立 agent 流程 | 它们由采收脚本当场调用、跟着上一步跑，是流程里的 Activity 的执行者，不是流程，也不是常驻 agent |
| 把归位画成 Activity | 测试②无业务结果，是收尾 Step |
| 把监工、巡检、日报挂成流程里的步骤 | 看护作业不产出该流程的业务结果，它看的是流程本身；归运维属性或「系统运行保障」能力（§3） |
| 把「打开抖音搜索页」「输入关键词」「滑动加载」画成 Activity | 机械动作，三测试全不过 → 发现这个 Activity 里的 Step |
| 把判定并进发现（「客户看不到判定」） | 旧四测试按「客户可见」误并；新测试①②③全过，判定是 Activity |

## 12. 反模式（90% 误判栽在这）

1. **「难」≠「能力」**：读懂语音再难，客户也不为它单独买单。难度量工作量，不量层级。
2. **「平行的技能」≠「平行的能力」**：看懂文字 / 图片 / 语音平行对等，但走完同一个结果 → 加厚，不分能力。
3. **「阶段」≠「能力 / 流程」**：采集 → 判定 → 触达是一个流程里的几个 Activity，不是几个能力或几个流程。
4. **「执行体」≠「流程」**：几个 agent / 脚本分段负责 = 一个流程（§6-4）。
5. **「异步」≠「拆流程」**：定时、捞池子、事件触发都只是 Activity 的启动方式（§6-1）。
6. **「看护」≠「步骤」**：监工 / 巡检 / 日报 / 保活不挂成业务流程的 Activity。
7. **「调了 AI」≠「独立 agent 流程」**：脚本当场同步调用的 AI 是某个 Activity 的执行者，不是流程，也不是常驻 agent。

## 13. 承诺与验收断言

- 每个 Activity 承诺配**可执行验证**的读回锚点（psql / UIA 读回 / 截图 / API 查询 / log 正则），
  禁「功能正常」类空话。断言写在 **Activity 上**，不写在需求本身上。
- 流程终点配端到端断言（漏斗、成功率、SLO）。
- 接缝 Activity（碰真机 / 生产 env / 真实第三方）验证等级必须 **L3 真机真验**；纯前端交互可 L1 替身；
  真 DB 写入 L2 服务端真验。降级需证据。
- 「得体 / 像人 / 有分寸」类软承诺：eval 集 + LLM judge + 人工抽样，表上显式标**「软」**，
  不许用主观描述冒充硬断言。
- 读回是**换实现的验收**（§10）：读回写得好，agent 换代码时不用重新定义验收。

## 14. 场景牌组（承诺 × 场景矩阵，防「只想了晴天」）

每个 Activity 过固定八格：**首次使用 / 日常运行 / 重启恢复 / 断网弱网 / 并发洪峰 /
对抗输入 / 平台改版 / 凭据过期**。

每格二选一：一条具体断言，或 `N/A + 理由`。**空格 = 红灯**——没人想过这个 Activity 在这个
场景下会怎样，等于埋了未知故障模式。

## 15. 归位判定链（新东西该挂哪）

按序过五关，禁跳步：

1. **频率判据**：它发生的频率 = 目标流程的触发频率吗？一次性的事禁进高频流程（注册一生一次，
   不能当「被动接待」流程的第一个 Activity）。
2. **三问法**（§5）：全过 → 它自己是个能力，转划分 / 切分流程。
3. **三测试**（§7）：过 → 候选 Activity（已有同类 Activity → 共用）；全不过 → 某个 Activity 里的 Step。
4. **四问归家**：新能力 / 共享前置（一次性进场链归「客户首次成功路径」能力，业务流程用依赖标签引用，
   禁复制进各流程开头）/ 横切件（必须答出「塌了哪些承诺会变红」，答不出 = 不该做）/
   工厂件（不挂业务价值流，归工厂价值流自己的家，决策 2d28de45）。
5. **归位裁决单**：`部门 · 价值流 · 能力 · 流程 · Activity（· Step）· 场景格 ＋ 动作类型（七动作之一）
   ＋ 验收断言锚点`。拿不准的列「待拍板问题清单」，不硬填。

## 16. 七动作总表（动树的合法动作类型）

| 动作 | 定义 | 关键规则 |
|------|------|----------|
| 贯穿 | 新流程 thin 端到端走通 | 先通后厚（= Walking Skeleton） |
| 加厚 | Activity 覆盖更多场景格 / 读回从缺到有 / Step 从 AI 走到代码 | 四种材料：能力 / 体验 / NFR / 守卫 |
| 修复 | Activity 读回从绿掉回红，补回去 | hotfix + 复现断言永久进 CI，禁事后删 |
| 改流程结构 | 增删 / 重排流程里的 Activity | 唯一豁免 = 客户看到全新的结果；主理人拍板；稀有 |
| 退役 | 下线一个流程 / Activity / 能力 | 先减肥再增肌，不与新增混一次提交 |
| 探索 spike | 写不出承诺的试错调研 | timebox；产出 = 结论喂回切分；禁伪装成贯穿 |
| 置换 | 承诺零变化的底层换实现（含 agent 换代码，§10） | 验收 = 同一套读回 绿 → 短暂红 → 绿 + 迁移 SOP |

共用三规则：**首用即出生**（Activity 第一次被某流程用到时诞生，保持 thin）、**复用即引用**
（语义查重，第二个流程用到就加一条 `workflow_activity_refs`，禁重建）、**瓶颈才加厚**（多个流程同时
被它卡住才立加厚）。

## 17. 巡逻模式（同一把尺子定期审查全树）

进门判定管新东西，巡逻管存量。两者**同一套标准**，不另立口径。

**第一遍：规则筛**（机器跑，SQL 见 /capability SKILL.md Mode D）

| 筛子 | 疑点 | 常见真相 |
|---|---|---|
| ① 没有 Activity 的流程 | 流程画了个空壳 | 还没画完；或其实是看护作业 / 定时作业，不是流程 |
| ② 名字像机械动作的 Activity（或只有 1 个 Step） | Step 被抬成了 Activity | 降为某个 Activity 的 Step |
| ③ 同名跨层（去掉「X · 」前缀后同名出现在两层） | 同一个东西被画了两遍，或层级混用 | 合并，或改名区分 |
| ④ 挂在流程上的看护定时项（定时作业 / 监工 / 巡检 / 日报 / 看护 / 保活） | 看护作业被当成业务流程或流程步骤 | 挪到「系统运行保障」类能力，或改成被看护对象的运维属性 |
| ⑤ 空壳价值流（下面没有在用的能力）/ 空壳能力（下面没有流程） | 只有名字没有内容 | 补流程，或退役 |

**第二遍：逐项按标准判定**——对每个筛中项跑 §3 判定链 + §5 三问法 + §7 三测试，筛中不等于错
（例如「抖音·关键词获客」流程与「关键词获客」能力同名是渠道前缀造成的，判对）。

**输出**（每项一行）：

| 坐标 | 现在挂在哪 | 结论 | 建议挪到哪 | 理由（引用哪条标准） |
|---|---|---|---|---|
| … | 流程 / Activity / … | 对 / 疑似层级不对 | 能力 X 下的流程 / 某 Activity 的 Step / 退役 … | §7 测试②无结果 … |

**只提建议、不自动挪**，由主理人拍板；拍板后按 db-update 规范落库。

## 18. 铁律与例外

- **拍板前绝不写库**——树 / 裁决单 / 巡逻报告是给主理人审的草案，不是既成事实。
- **止血例外**：生产事故可先斩后奏，但 24h 内补归位裁决单，钉红灯状态进账本。
- **账本写入必须是流水线自动副作用**——设计里出现「记得手动更新账本」= 该设计判死刑。
- **一句话内核**：层级按「做成了什么」切。比结果细的（阶段 / 技能 / 模态 / 执行体 / 启动方式）
  一律往里装或记成属性；难不难、大不大、平不平行、同步还是异步、agent 还是代码，都不改变它在哪一层。

## 附 A. 名词来历

- **Golden Path 为什么退役**：业界 Golden Path（Spotify 2020，平台工程）是给工程师铺的推荐建软件
  路线；我们家曾借这个词指「客户为一个完整价值结果而走的承诺序列」（内核是 Story Mapping backbone
  + Walking Skeleton）。借词不借义造成长期混淆，决策 a340f100 改称能力，本版（决策 0cee5452）再把
  「路」拆成 能力 + 流程 两层，并把「骨干步」落实为 Activity、「挂片」拆回 Step / 共用 Activity / 横切件。
- **Walking Skeleton / 贯穿**：一个流程第一次 thin 端到端跑通的动作。
- **Happy Path 与 smoke 的分工**：验收测试（建流程时）跑全场景八格，全绿才算通；smoke 守卫
  （通了之后）每天只走晴天剧本，快而浅，回答「今天还通吗」。一个流程配**分段** smoke（按 Activity
  独立坏，红灯要能指到断点）。两个绿不是一回事。
- **来源谱系**：APQC PCF / BPMN / Temporal（Activity 三测试）、Story Mapping backbone（Patton）、
  Walking Skeleton（Cockburn）、Event Storming 触发器、Design by Contract、SRE（SLO / 对账）、
  BDD + 混沌工程（场景牌组）、Team Topologies（四个家）。组装方式是自家的。
