## 0. 总原则

**层级按「做成了什么」判，只看业务事实，不看「谁做、怎么做」。**

- 和用脚本还是 agent 无关；和「现在是不是被一个脚本连着跑完」也无关。
- **一个执行者把几个流程顺序跑完，它们仍然是几个流程。**
- 「谁做」（人 / agent / 脚本 / 哪台机器）、「怎么被叫起来」（定时 / 事件 / 从表里取待处理）是属性，
  写在对应层的列上，不决定它是哪一层。
- 流程边界只由问题一（§6）决定，Activity 边界只由问题二（§7）决定。

## 1. 六层与每层一句话定义

```
部门（含子部门）
 └─ 价值流   一条端到端为客户或业务创造价值的线
     └─ 能力   客户付钱买的那个结果
         └─ 流程   有触发、有一次运行，把多个 Activity 按顺序串起来；边界 = 结果能放进表里停下来的地方
             └─ Activity   流程里一段有可验收结果、下一段失败时能从这里重来的工作；从不单独运行，可被多个流程共用
                 └─ Step   Activity 里面的具体动作（点发送、往下翻一页）
```

| 层 | 一句话定义 | 落在哪（Brain 真表） |
|---|---|---|
| 部门 | 组织归属；价值流挂在部门（可以是子部门）下 | `areas`（`parent_area_id` = 上级部门） |
| 价值流 | 一条端到端为客户或业务创造价值的线，挂在部门（可以是子部门）下 | `value_streams`（`area_id` → 部门） |
| 能力 | 客户付钱买的那个结果（例：抖音智能获客）；三问法：独立触发、独立交付可见结果、独立验收（§5） | `capabilities`（`parent_journey_id` → 价值流） |
| 流程 | 有触发（定时 / 事件 / 从表里取待处理），有一次运行（开始、结束、时长预算），把**多个** Activity 按顺序串起来，可以有「逐个做」的循环和失败策略；边界由问题一定 | `workflows`（`capability_id` → 能力） |
| Activity | 流程里的一段工作，终点有能验收的结果、下一段失败时可以从这里重来；从不单独运行，只作为某个流程的一部分被执行；可被多个流程共用；边界由问题二定 | `activities`；在流程里的位置只认 `workflow_activity_refs`（`sequence_no`），视图 `activity_placement` |
| Step | Activity 里面的具体动作，比如点发送、往下翻一页 | `steps`（`activity_id` → Activity；真身在仓库 step-dod.json） |

**执行器与监工**：执行器（现在是 wf-run.sh、outreach-tick.sh 这类脚本）按流程定义去跑，Commander 盯
每一次运行。执行器是实现，不是层级。

一次运行的账：`runs`（一个流程的一次运行）+ `spans`（其中每个 Activity / Step 的一次执行），见 §9。

**层与属性分开记**：「谁来执行」（`activities.executor_kind`：code / agent / 混合 / 人）是 Activity 的属性；
「触发」「时长预算」「失败策略」是流程的属性；「实现进度」（现在走代码 / AI / 混合，目标是什么）记在 Step 层（§10）。

| 工序 / 动作 | **Step** | |

## 3. 判定链（任何东西丢进来，从上往下问）

```
它是一条端到端为客户或业务创造价值的线吗（装得下多个能力，没有单一触发）？
 ──是→ 价值流（挂到哪个部门）
 └─否→ 是客户付钱买的那个结果、三问法全过吗？
     ──是→ 能力（挂到哪条价值流）
     └─否→ 它有自己的触发、一次运行，前后的接缝都「能放下」（问题一）吗？
         ──是→ 流程（挂到哪个能力）
         └─否→ 它的终点有能验收的结果、下一段失败时能从这里重来（问题二）吗？
             ──是→ Activity（排进哪个流程第几位；已存在就共用）
             └─否→ 塌了会让多个能力变红吗？
                 ──是→ 横切件
                 └─否→ 是看护作业（监工 / 巡检 / 日报 / 保活）吗？
                     ──是→ 归看护它的那一层的运维属性，或归「系统运行保障」自己的能力；
                           **不挂成被看护流程的步骤**
                     └─否→ Step（归到某个 Activity 里）
```

**先装地图铁律**：跑判定链之前必须先装载现有六层全树（/capability Step 0）。结论必须落成
**格子坐标**（§2），禁止在真空里判——已在树上的东西绝不重新发明（教训：14 条清洗曾把图上已有的
F5 指挥舱、F3 夜间体检重新发明成新的）。同时核验锚点健康：挂空 / 挂 deprecated / 悬空外键一律标失锚。

## 4. 价值流判定

**价值流 = 一条端到端为客户或业务创造价值的线，挂在部门（可以是子部门）下。** 回答
「我们在哪条线上创造价值」，不回答「事情怎么走」。

| 判据 | 过 = 价值流 | 不过 |
|---|---|---|
| 有自己的价值接收方 | 智能获客 = 要线索的老板；工厂 = 主理人 | 接收方与别的价值流完全重合 → 同一条 |
| 能独立考核 / 独立成交付 | 「智能获客」可单独卖 | 「看懂图片」不能 → 不是价值流 |
| 装得下一个或多个能力 | 获客装 抖音智能获客 / 小红书智能获客 … | 只是某个能力的一段 → 下沉 |
| 没有单一触发器和终点 | 价值流是一组能力的家 | 说得出「X 发生 → 拿到 Y」→ 是能力不是价值流 |

关键区分：**能画出起点和终点的东西不是价值流，是能力。** 下面一个在用的能力都没有 = 空壳价值流（巡逻筛子⑤）。

## 5. 能力判定：客户买的结果 + 三问法 + 两把尺子

**能力 = 客户付钱买的那个结果。** 例：抖音智能获客（客户买的是「每天一批找到并私信过的意向客户」）。

- **找法不同不是能力**：关键词、对标只是「发现」阶段的不同找法，结果相同 → 同一个能力。
- **平台不同算不同能力**：抖音、小红书的账号、操作、风控、交付都各自独立 → 两个能力。

### 三问法（判断「是不是一个独立能力」）

1. **独立触发**：它有自己的起点（什么事发生了系统要动）吗？
2. **独立交付可见结果**：走完客户拿到一个看得见、愿意为之付钱 / 会出现在交付清单上的结果吗？
3. **独立验收**：不依赖别的能力跑完，就能对这个结果写断言验收吗？（拿掉它，别的旅程还走得通吗？）

三问全过 → 独立能力；任一不过 → 不是能力（是流程、Activity、共享前置或横切件）。

### 两把尺子

**尺子①「客户为什么而来」→ 定能力的边界。** 能不能对客户说「我们现在能做到 X 了」且客户因此点头？
- 「我们能在抖音上每天替你找到并私信一批意向客户了」→ 点头 ✅ → 能力
- 「我们能采集抖音评论了」→「那然后呢？」❌ → 只是某个流程里的一段

**尺子②「走完拿到的结果是不是同一个」→ 定加厚 vs 分开。**
- 同一个结果、只是输入 / 找法 / 覆盖面不同 → **加厚**，同一个能力（关键词找 / 对标找都是「拿到意向客户」）
- 结果本身不同，或交付链条各自独立（换平台）→ 不同能力

**能力级的东西只有三样不住在 Activity 里**：① 能力级端到端断言（「每天 N 条已私信线索、成功率 ≥90%」，
塞不进单个 Activity）② Gate 前置门（授权文书 / 技术可行性，任一不过整条停）③ 横切件（服务多个能力，
塌了多个能力变红）。其余一切都住流程 / Activity / Step 里。

**FR / NFR 归属**：FR = Activity 承诺 + 分支；Activity 级 NFR（并发 / 断网 / 恢复）= 该 Activity
场景格断言；流程级 NFR（一次运行的时长预算 / 成功率）= 流程断言；能力级 NFR（端到端漏斗 / SLO）=
能力终点断言；系统级 NFR = 横切件。

## 6. 问题一：定流程边界

> **做完这一段后，能不能把结果放进表里，停下来，过几个小时再做下一段，而且不用返工？**

- **能放下** → 在这里断开，后面的是另一个流程。
- **放不下**（一停就要返工，或者正占着手机、开着 App、持有设备锁）→ 仍在同一个流程里。

用法：
- 把整件事按时间顺序列成一串「段」，**对每个接缝问一次问题一**，标「放下 / 放不下」。
- 断开处必须有一张表接住结果（视频表、评论表、线索表），下一个流程从表里取「待处理」开始——这就是它的触发。
- 「交接」（换执行者、要等定时 / 事件）**本身不是理由**：换了执行者但结果放不下，仍是同一个流程；
  同一个执行者连着跑，但结果放得下，仍要断开。
- 流程的其他要件：有触发（定时 / 事件 / 从表里取待处理）、有一次运行（开始、结束、时长预算），
  把**多个** Activity 按顺序串起来，可以有「逐个做」的循环（逐个词、逐个视频、逐条评论）和失败策略。
  只有 1 个 Activity 的「流程」多半是画错了（巡逻筛子⑥）。
- 平台不同已经是不同能力（§5），不用在流程层再分；同一能力里找法不同（关键词版 / 对标版）可以是
  同一个流程的两个版本，共享预检 / 收尾，写同一张表。

## 7. 问题二：定 Activity

> **做到这里，有没有一个能验收的结果，并且下一段失败时可以从这里重来、不用从头？**

- **有** → 这里是一个 Activity 的终点。
- **没有** → 只是 Step。

解释（吸收 v2.0 的「结果 + 重试」）：
- **能验收的结果**：业务上可见、能读回（写进表、发出消息、拿到锁、确认了账号），不要求终端客户亲眼
  看到；只在日志 / 进程内存里的不算。
- **能从这里重来**：下一段坏了，从这个结果往后重做即可，不用退回流程开头。
- Activity **从不单独运行**，只作为某个流程的一部分被执行；可以被多个流程共用。
  例：预检 = 打开抖音、拿锁、确认账号；收尾 = 关抖音、放锁——发现、处理、触达三个流程都用。
- 一个 Activity 被多个流程用到 → **共用同一行**（`workflow_activity_refs` 多条引用），禁复制。
- **承诺式要求**（保留）：每个 Activity 一句承诺（`activities.promise`）——「做完后业务上多了什么 /
  谁拿到了什么」，配可执行读回（§13）。名字可以是短动词（预检 / 判定视频），承诺句不许是空话。
- 数量不设上下限：由问题二扫出来多少就是多少。

## 8. Step 判定

**Step = Activity 里面的具体动作**，比如点「发送」、往下翻一页、输入关键词、等元素出现。

- 判据：问题二不过——做到这里没有能验收的结果，或者下一段失败时不能从这里重来。
- Step 照样要有读回（`steps.readback`：log 正则 / 截图 / 查表），那是 Activity 读回的分解，
  用来定位坏在哪一步，不是独立交付。
- **实现进度记在 Step 层**：每个 Step 现在走代码 / AI / 混合，目标是什么（§10）。
- 名字像机械动作的 Activity、只有 1 个 Step 的 Activity，多半是被抬错层的 Step（巡逻筛子②）。
  （0 个 Step 通常只是还没落 Step，不算层级信号。）

## 9. 流程与一次运行

- **一次运行 = 一个流程从触发到结束跑一遍**：有开始、结束、时长预算；`runs` 记一条，其中每个 Activity
  的执行在 `spans` 各记一条。
- **跨流程的端到端漏斗**用交接物 id 串（视频 id → 评论 id → 线索 id）：发现 N 个视频 → 判定合格 M 个 →
  采集 K 条评论 → 评分出 L 条线索 → 私信送达多少。漏斗是能力级断言（§5），不是某个流程的运行。
- **执行器顺序跑多个流程时**（例如一个脚本把 ①②③ 连成一轮），账上仍按流程各记各的运行；
  不要按「某个脚本跑了一轮」算一次运行（§0）。

## 10. agent 换成代码

把某段从 agent 换成脚本（或反过来），**层级不动**：

1. **Activity 合同不变**：承诺、输入、输出、读回原样保留。
2. **同一套读回探针必须照样通过**——这就是换实现的验收（七动作里的「置换」，§16）。
3. **变的是「谁来执行」和 Step 粒度**：`executor_kind` 改；Step 可能变多变细。
4. **实现进度记在 Step 层**：现在走代码 / AI / 混合，目标是什么。
5. **只有换实现时发现某个接缝变得「能放下」或「放不下」了，才按问题一重划流程**；
   发现中间多了能验收、能重来的结果，才按问题二拆 Activity。「代码分了几个函数」不是拆的理由。

## 11. 样板：抖音智能获客（四个流程）

```
能力：抖音智能获客（客户买的结果：每天一批找到并私信过的意向客户）
 ├ 流程① 视频发现（关键词版 / 对标版）  每天 1~2 次
 │   预检 → 取关键词 → 搜索取视频（逐个词，按"最新"往下翻 20 个）→ 过滤去重 → 写视频表 → 收尾
 ├ 流程② 视频处理   一天多轮，从视频表取「待判定」
 │   预检 → 判定视频（逐个）→ 采集评论（只采合格的）→ 收尾
 ├ 流程③ 评论评分   有新评论就跑，不占手机
 │   取待评分评论 → 打分（逐条）→ 标记人 → 写线索表
 └ 流程④ 线索触达   全天，按每个号的额度
     预检 → 取线索 → 发私信（逐条，按额度）→ 回填 → 收尾
```

关键词版、对标版只是流程①的两种找法（§5），不是两个能力；它们共享预检 / 收尾，写同一张视频表。

**问题一：逐个接缝问「能不能放下」**

| 接缝 | 能放下吗 | 结论 |
|---|---|---|
| 打开抖音 → 发私信 → 关闭抖音 | 不能（开着 App、持有锁） | 同一流程 |
| 发现（写视频表）→ 判定 | 能 | 断开 |
| 判定 → 采集评论 | 不能（停了要重新打开视频，等于返工） | 同一流程 |
| 采集（写评论表）→ 评分 | 能（评分不用手机） | 断开 |
| 评分（写线索表）→ 触达 | 能（按额度慢慢发） | 断开 |

**问题二：哪些是 Activity、哪些是 Step**

| 段 | 能验收的结果 | 下一段失败能从这里重来吗 | 结论 |
|---|---|---|---|
| 预检 | 抖音已打开、拿到设备锁、确认了账号 | 能 | Activity（发现 / 处理 / 触达共用） |
| 判定视频 | 每个视频的判定结果写回视频表 | 能（采集失败不用重判） | Activity |
| 发私信 | 每条线索的发送结果（已发 / 受限 / 失败） | 能（回填失败不用重发） | Activity |
| 收尾 | 抖音已关闭、锁已释放 | 能 | Activity（三个流程共用） |
| 点「发送」 | 没有单独可验收的业务结果 | 不能（要从这条私信头上重来） | Step（属于「发私信」） |
| 往下翻一页 | 没有 | 不能 | Step（属于「搜索取视频」） |

**去重规则**
- **视频去重在发现阶段**：先按「标题 + 作者」过滤，取到链接后再按视频 id 确认，同时排除自家账号的视频。
- **人不删，只标记**：已触达过、多次出现（多次出现的可以调高意向等级）。

**现状**：目前 wf-run.sh 把 ①②③ 连成一轮顺序跑完，属于「一个执行者顺序跑多个流程」；树按 4 个流程登记，
实现以后再拆。生产库现在把「关键词获客」「对标获客」登记成两个能力、各一个 8 段流程，按本标准待改。

**错误画法**

| 错误 | 为什么错 |
|---|---|
| 一个流程、七八个 Activity 从预检串到触达 | 发现 → 判定、采集 → 评分、评分 → 触达三个接缝都「能放下」，必须断开（问题一） |
| 把关键词获客、对标获客画成两个能力 | 只是发现阶段的找法不同，客户买的结果一样（§5） |
| 因为 wf-run.sh 一口气跑完 ①②③，就画成一个流程 | 一个执行者顺序跑多个流程，仍是多个流程（§0） |
| 把判定视频和采集评论拆成两个流程 | 判定 → 采集放不下：停了要重新打开视频，等于返工（问题一） |
| 把点「发送」、往下翻一页画成 Activity | 没有能验收、能从这里重来的结果（问题二） |
| 把监工、巡检、日报挂成流程里的步骤 | 看护作业不产出该能力的业务结果；归运维属性或「系统运行保障」能力（§3） |
| 去重时把重复出现的人删掉 | 人不删只标记，多次出现是意向信号 |

## 12. 反模式（90% 误判栽在这）

1. **「难」≠「能力」**：读懂语音再难，客户也不为它单独买单。难度量工作量，不量层级。
2. **「找法 / 输入不同」≠「不同能力」**：关键词找、对标找，文字 / 图片 / 语音，结果相同 → 加厚。
3. **「一个脚本跑完」≠「一个流程」**：执行器怎么编排不改变接缝能不能放下（§0、§6）。
4. **「换了执行者」≠「新流程」**：脚本调 AI、agent 交给脚本，结果放不下就仍在同一个流程里（§6）。
5. **「动作」≠「Activity」**：点击、翻页、输入是 Step（§7、§8）。
6. **「看护」≠「步骤」**：监工 / 巡检 / 日报 / 保活不挂成业务流程的 Activity。

## 13. 承诺与验收断言

- 每个 Activity 承诺配**可执行验证**的读回锚点（psql / UIA 读回 / 截图 / API 查询 / log 正则），
  禁「功能正常」类空话。断言写在 **Activity 上**，不写在需求本身上。
- 每个流程配一次运行的断言（时长预算内结束、失败策略生效）；能力终点配端到端漏斗断言。
- 接缝 Activity（碰真机 / 生产 env / 真实第三方）验证等级必须 **L3 真机真验**；纯前端交互可 L1 替身；
  真 DB 写入 L2 服务端真验。降级需证据。
- 「得体 / 像人 / 有分寸」类软承诺：eval 集 + LLM judge + 人工抽样，表上显式标**「软」**，
  不许用主观描述冒充硬断言。
- 读回是**换实现的验收**（§10）：读回写得好，agent 换代码时不用重新定义验收。

## 14. 场景牌组（承诺 × 场景矩阵，防「只想了晴天」）

每个 Activity 过固定八格：**首次使用 / 日常运行 / 重启恢复 / 断网弱网 / 并发洪峰 /
对抗输入 / 平台改版 / 凭据过期**。

每格二选一：一条具体断言，或 `N/A + 理由`。**空格 = 红灯**——没人想过这个 Activity 在这个
场景下会怎样，等于埋了未知故障模式。

## 15. 归位判定链（新东西该挂哪）

按序过五关，禁跳步：

1. **频率判据**：它发生的频率 = 目标流程的触发频率吗？一次性的事禁进高频流程（注册一生一次，
   不能当「被动接待」流程的第一个 Activity）。
2. **三问法**（§5）：全过 → 它自己是个能力，转划分 / 设计。
3. **问题一 / 问题二**（§6 / §7）：前后接缝都能放下、有自己的触发 → 流程；有能验收、能重来的结果 →
   Activity（已有同类 Activity → 共用）；都不是 → 某个 Activity 里的 Step。
4. **四问归家**：新能力 / 共享前置（一次性进场链归「客户首次成功路径」能力，业务流程用依赖标签引用，
   禁复制进各流程开头）/ 横切件（必须答出「塌了哪些承诺会变红」，答不出 = 不该做）/
   工厂件（不挂业务价值流，归工厂价值流自己的家，决策 2d28de45）。
5. **归位裁决单**：`部门 · 价值流 · 能力 · 流程 · Activity（· Step）· 场景格 ＋ 动作类型（七动作之一）
   ＋ 验收断言锚点`。拿不准的列「待拍板问题清单」，不硬填。

## 16. 七动作总表（动树的合法动作类型）

| 动作 | 定义 | 关键规则 |
|------|------|----------|
| 贯穿 | 新流程 thin 端到端走通 | 先通后厚（= Walking Skeleton） |
| 加厚 | Activity 覆盖更多场景格 / 读回从缺到有 / Step 从 AI 走到代码 / 流程多一种找法 | 四种材料：能力 / 体验 / NFR / 守卫 |
| 修复 | Activity 读回从绿掉回红，补回去 | hotfix + 复现断言永久进 CI，禁事后删 |
| 改流程结构 | 按问题一重划流程，或增删 / 重排流程里的 Activity | 主理人拍板；稀有 |
| 退役 | 下线一个流程 / Activity / 能力 | 先减肥再增肌，不与新增混一次提交 |
| 探索 spike | 写不出承诺的试错调研 | timebox；产出 = 结论喂回切分；禁伪装成贯穿 |
| 置换 | 承诺零变化的底层换实现（含 agent 换代码、把连着跑的流程拆给不同执行器） | 验收 = 同一套读回 绿 → 短暂红 → 绿 + 迁移 SOP |

共用三规则：**首用即出生**（Activity 第一次被某流程用到时诞生，保持 thin）、**复用即引用**
（语义查重，第二个流程用到就加一条 `workflow_activity_refs`，禁重建）、**瓶颈才加厚**（多个流程同时
被它卡住才立加厚）。

## 17. 巡逻模式（同一把尺子定期审查全树）

进门判定管新东西，巡逻管存量。两者**同一套标准**，不另立口径。

**第一遍：规则筛**（机器跑，SQL 见 /capability SKILL.md Mode D）

| 筛子 | 疑点 | 用哪个问题判 |
|---|---|---|
| ① 没有 Activity 的流程 | 流程画了个空壳，或其实是看护 / 定时作业 | 问题一 + §3 看护 |
| ② 名字像机械动作的 Activity（或只有 1 个 Step） | Step 被抬成了 Activity | 问题二 |
| ③ 同名跨层（去掉「X · 」前缀后同名出现在两层） | 同一个东西画了两遍，或找法被画成能力 | §5 + 问题一 |
| ④ 挂在流程上的看护定时项（定时作业 / 监工 / 巡检 / 日报 / 看护 / 保活） | 看护作业被当成业务流程或步骤 | §3 |
| ⑤ 空壳价值流 / 空壳能力 | 只有名字没有内容 | §4 / §5 |
| ⑥ 只有 1 个 Activity 的流程 | 流程要串起多个 Activity | 问题一（它和前后能不能放下）+ 问题二 |
| ⑦ Activity 数很多的流程（≥ 7） | 很可能有「能放下」的接缝没断开 | 问题一逐个接缝 |

**第二遍：逐项判定**——筛中项逐个对它的接缝问问题一、对它的段问问题二，再过 §3 判定链 / §5 三问法。
筛中不等于错（例如渠道前缀造成的同名），判对的写「对」并给一句理由。

**输出**（每项一行）：

| 坐标 | 现在挂在哪 | 结论 | 建议挪到哪 | 理由（问题一 / 问题二 / 引用 §） |
|---|---|---|---|---|

**只提建议、不自动挪**，由主理人拍板；拍板后按 db-update 规范落库。

## 18. 设计模式：预先拆结构

设计新东西（一个新想法，或一份现有脚本）时，用同一把尺子**先拆好结构再动手**，按顺序输出：

1. **能力是什么**：客户买的结果（§5）；平台不同就是不同能力。
2. **列段**：把整件事按时间顺序列成一串「段」。
3. **问题一**：对每个接缝问「能不能放下」，标「放下 / 放不下」，得出流程划分（每个断开处写明接住结果的表）。
4. **问题二**：每个流程内对每段问「有没有能验收、能从这里重来的结果」，得出 Activity 和 Step。
5. **共用**：先查树上已有的 Activity，列出哪些可以和已有流程共享（预检 / 收尾这类最常见）。
6. **每个流程的运行面**：触发（定时 / 事件 / 从表里取待处理）、一次运行的时长预算、交接表（从哪张表取、
   写到哪张表）、逐个做的循环与失败策略。

产出格式见 /capability SKILL.md Mode E。现有脚本若把多个流程连着跑，照样按问题一划成多个流程，并注明
「现状：一个执行者顺序跑」。

## 19. 铁律与例外

- **拍板前绝不写库**——树 / 裁决单 / 巡逻报告 / 设计稿是给主理人审的草案，不是既成事实。
- **止血例外**：生产事故可先斩后奏，但 24h 内补归位裁决单，钉红灯状态进账本。
- **账本写入必须是流水线自动副作用**——设计里出现「记得手动更新账本」= 该设计判死刑。
- **一句话内核**：能力 = 客户买的结果；流程在「能放下」的地方断开；Activity 在「能验收、能从这里重来」
  的地方结束；其余是 Step。谁来做、用什么做、是不是一个脚本连着跑，都不改变它在哪一层。

## 附 A. 名词来历

- **Golden Path 为什么退役**：业界 Golden Path（Spotify 2020，平台工程）是给工程师铺的推荐建软件
  路线；我们家曾借这个词指「客户为一个完整价值结果而走的承诺序列」。借词不借义造成长期混淆，决策
  a340f100 改称能力，v2.0（决策 0cee5452）把「路」拆成 能力 + 流程 两层，v3.0（决策 c63688cf）把
  判据定为「能不能放下 / 能不能验收并从这里重来」两个问题。
- **Walking Skeleton / 贯穿**：一个流程第一次 thin 端到端跑通的动作。
- **Happy Path 与 smoke 的分工**：验收测试（建流程时）跑全场景八格，全绿才算通；smoke 守卫
  （通了之后）每天只走晴天剧本，快而浅，回答「今天还通吗」。一个流程配**分段** smoke（按 Activity
  独立坏，红灯要能指到断点）。两个绿不是一回事。
- **来源谱系**：问题一对应持久化检查点 / 工作队列边界（BPMN 的等待与消息事件、Temporal 的 workflow
  边界），问题二对应可重试的 Activity（Temporal）与 APQC PCF 的可度量工作单元；Story Mapping backbone
  （Patton）、Walking Skeleton（Cockburn）、Design by Contract、SRE（SLO / 对账）、BDD + 混沌工程
  （场景牌组）、Team Topologies（四个家）。组装方式是自家的。
