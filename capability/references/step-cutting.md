# 两个问题扫刀（一件事切几个流程、每个流程几个 Activity、哪些只是 Step）

> v3.0（主理人 2026-10-07 晚拍板，决策 c63688cf）：主判据换成两个问题——问题一「能不能放下」定流程边界，
> 问题二「有没有能验收、能从这里重来的结果」定 Activity。v2.0 的「Activity 三测试（交接 / 结果 / 重试）」
> 退役：「结果 + 重试」并入问题二，「交接」并入问题一。「数量不许拍脑袋，必须沿时间线扫出来」「切刀记录表」
> 两条纪律保留。本文件是 doctrine §6 / §7 / §18 的操作化补条，/capability A3 / Mode E、
> capability-proposer、capability-reviewer 统一引用。

## 0. 两个问题

**问题一（定流程边界）**：做完这一段后，能不能把结果放进表里，停下来，过几个小时再做下一段，而且不用返工？
- 能放下 → 在这里断开，后面是另一个流程。
- 放不下（一停就要返工，或者正占着手机、开着 App、持有设备锁）→ 仍在同一个流程里。

**问题二（定 Activity）**：做到这里，有没有一个能验收的结果，并且下一段失败时可以从这里重来、不用从头？
- 有 → 这里是一个 Activity 的终点。
- 没有 → 只是 Step。

只看业务事实：和用脚本还是 agent 无关，和「现在是不是被一个脚本连着跑完」无关（doctrine §0）。

## 1. 扫刀流程（机械执行，产出两张表）

1. 先定能力：客户买的结果是什么（doctrine §5）；平台不同就是不同能力，分开扫。
2. 把整件事按时间顺序列成一串「段」（有几个写几个，此时不限数量）。
3. **对每个接缝问问题一**，填「问题一表」：放下 → 断开（写明接住结果的表）；放不下 → 同一流程（写明为什么放不下）。
4. **每个流程内对每段问问题二**，填「问题二表」：有能验收、能重来的结果 → Activity；没有 → 并入相邻 Activity 成 Step。
5. 查共用：每个 Activity 先到现有树里语义查重（预检 / 收尾最常见），已有就共用，禁重建。
6. 给每个流程补运行面：触发、一次运行的时长预算、从哪张表取 / 写到哪张表、逐个做的循环与失败策略。
7. 看护作业（监工 / 巡检 / 日报 / 保活）不进流程，单列。
8. 两张表随设计稿一起呈拍板；GAN tech 镜头必须逐行攻击。

## 2. 表模板

**问题一表（流程边界）**

| 接缝（段 A → 段 B） | 能放下吗（理由） | 结论 | 接住结果的表 |
|---|---|---|---|
| … → … | 能 / 不能（开着 App、持有锁、停了要返工 …） | 断开 / 同一流程 | …表 / — |

**问题二表（Activity / Step）**

| 段 | 能验收的结果 | 下一段失败能从这里重来吗 | 结论 |
|---|---|---|---|
| … | … / 没有 | 能 / 不能 | Activity（共用？）/ Step（属于哪个 Activity） |

## 3. 已扫样例：抖音智能获客

段（按时间顺序）：打开抖音 / 拿锁 / 确认账号 → 取关键词 → 逐个词搜索、按「最新」往下翻 20 个 → 过滤去重
→ 写视频表 → 关抖音 / 放锁 →（过几小时）取待判定视频 → 打开抖音 → 逐个判定视频 → 合格的采评论 → 写评论表
→ 关抖音 →（随时）取待评分评论 → 逐条打分 → 标记人 → 写线索表 →（全天）打开抖音 → 取线索 → 逐条发私信
（按额度）→ 回填 → 关抖音

**问题一表**

| 接缝 | 能放下吗 | 结论 | 接住结果的表 |
|---|---|---|---|
| 打开抖音 → 发私信 → 关闭抖音 | 不能（开着 App、持有锁） | 同一流程 | — |
| 发现（写视频表）→ 判定 | 能 | 断开 | 视频表（待判定） |
| 判定 → 采集评论 | 不能（停了要重新打开视频，等于返工） | 同一流程 | — |
| 采集（写评论表）→ 评分 | 能（评分不用手机） | 断开 | 评论表（待评分） |
| 评分（写线索表）→ 触达 | 能（按额度慢慢发） | 断开 | 线索表（待触达） |

⇒ 四个流程：
- ① 视频发现（关键词版 / 对标版），每天 1~2 次：预检 → 取关键词 → 搜索取视频 → 过滤去重 → 写视频表 → 收尾
- ② 视频处理，一天多轮，从视频表取「待判定」：预检 → 判定视频（逐个）→ 采集评论（只采合格的）→ 收尾
- ③ 评论评分，有新评论就跑，不占手机：取待评分评论 → 打分（逐条）→ 标记人 → 写线索表
- ④ 线索触达，全天按每个号的额度：预检 → 取线索 → 发私信（逐条，按额度）→ 回填 → 收尾

**问题二表（节选）**

| 段 | 能验收的结果 | 下一段失败能从这里重来吗 | 结论 |
|---|---|---|---|
| 预检（打开抖音、拿锁、确认账号） | 锁在手、账号确认 | 能 | Activity（①②④ 共用） |
| 判定视频 | 判定结果写回视频表 | 能 | Activity |
| 发私信 | 每条线索的发送结果 | 能 | Activity |
| 收尾（关抖音、放锁） | App 已关、锁已释放 | 能 | Activity（①②④ 共用） |
| 点「发送」 | 没有 | 不能 | Step（属于「发私信」） |
| 往下翻一页 | 没有 | 不能 | Step（属于「搜索取视频」） |

去重：视频在发现阶段去重（先「标题 + 作者」过滤，取到链接后按视频 id 确认，排除自家账号视频）；
人不删只标记（已触达过、多次出现，多次出现可调高意向等级）。

现状：wf-run.sh 目前把 ①②③ 连成一轮顺序跑完 =「一个执行者顺序跑多个流程」，树仍按 4 个流程登记，实现以后再拆。

**和之前版本的差别**：v2.0 / v2.0.1 按「换执行者 / 异步」切，得出「一个流程 7~8 个 Activity」；
按问题一，发现 → 判定、采集 → 评分、评分 → 触达三处都能放下，必须断开，那种画法已作废。

## 4. 与账本的关系（别把颗粒度塞错地方）

- 流程 → `workflows`（触发 / 时长预算 / 失败策略）；断开处的交接表就是下一个流程的触发来源；
- Activity → `activities`（承诺 / 输入 / 输出 / 读回 / 执行体），在流程里的位置只认 `workflow_activity_refs`；
- Step → `steps`（真身在仓库 step-dod.json，`sync-steps-from-workspace.mjs` 灌入），每步带读回与实现进度；
- 一次运行 → `runs`（一个流程的一次运行）+ `spans`（每个 Activity 执行一条）；
- **禁止**为了「每一段都能单独管」把 Step 抬成 Activity——颗粒度该去 Step 层要。
