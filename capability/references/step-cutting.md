# 扫刀：流程边界两条件 + 问题二（一件事切几个流程、每个流程几个 Activity、哪些只是 Step）

> v3.1（主理人 2026-10-08 拍板定稿，决策 eb9f8f77，取代 c63688cf）：流程边界从 v3.0 的单条件「能不能放下」
> 改为**两条件**（① 能放下 且 ② 有分开跑的理由），默认同一流程；问题二（定 Activity / Step）不变。
> 「数量不许拍脑袋，必须沿时间线扫出来」「两张表随稿呈报」两条纪律保留。本文件是 doctrine §6 / §7 / §18
> 的操作化补条，/capability A3 / Mode E、capability-proposer、capability-reviewer 统一引用。

## 0. 判据

**流程边界（doctrine §6）**：默认放在同一个流程里。两条同时满足才断开：
- ① **能放下**：中间结果已经进表，停几个小时也不用返工。
- ② **有分开跑的理由**，至少一条：节奏不同 / 用的资源不同（占手机 vs 不占手机；不同机器、账号、App）/
  一对多或多对一 / 中间要等人（审核、拍板）。

① 不满足 → 必须同一流程。① 满足、② 不满足 → 仍同一流程。流程边界是运行设计，画错了重新打包即可，Activity 不动。

**问题二（doctrine §7）**：做到这里，有没有明确输入、交出能验收的结果，并且后面失败时可以从这里重来？
- 有 → 这里是一个 Activity 的终点。没有 → 只是 Step。没有输入、只是一句口号 → 改成承诺。

Activity 和能力只看业务事实；用脚本还是 agent、是不是被一个脚本连着跑完，都不影响判断（doctrine §0）。

## 1. 扫刀流程（机械执行，产出两张表）

1. 先定能力：客户买的结果是什么（doctrine §5）；平台默认是走法，不单列能力，流程名带平台前缀。
2. 把整件事按时间顺序列成一串「段」（有几个写几个，此时不限数量）。
3. **对每个接缝按两条件判**，填「流程边界表」：①✓ 且 ②✓ → 断开（写明接住结果的表和理由类型）；否则同一流程。
4. **每个流程内对每段问问题二**，填「问题二表」：有 → Activity；没有 → 并入相邻 Activity 成 Step。
5. 查共用：每个 Activity 先到现有树里语义查重（预检 / 收尾最常见），已有就共用，禁重建。
6. 给每个流程补运行面：触发、一次运行的时长预算、从哪张表取 / 写到哪张表、逐个处理的循环、分支与失败策略。
7. 看护作业（监工 / 巡检 / 日报 / 保活）拆成各自的流程，挂「系统看护」，不进业务流程。
8. 两张表随设计稿一起呈拍板；GAN tech 镜头必须逐行攻击。

## 3. 已扫样例：智能获客（抖音）

段（按时间顺序）：打开抖音 / 拿锁 / 确认账号 → 取关键词 → 逐个词搜索、按「最新」往下翻 20 个 → 过滤去重
→ 写视频表 → 关抖音 / 放锁 →（过几小时）取待判定视频 → 打开抖音 → 逐个判定视频 → 合格的采评论 → 写评论表
→ 关抖音 →（随时）取待评分评论 → 逐条打分 → 标记人 → 写线索表 →（全天）打开抖音 → 取线索 → 逐条发私信
（按额度）→ 回填 → 关抖音

**流程边界表**

| 接缝 | ① 能放下 | ② 分开跑的理由 | 结论 | 接住结果的表 |
|---|---|---|---|---|
| 打开抖音 → 发私信 → 关闭抖音 | ✗（开着 App、持有锁） | — | 同一流程 | — |
| 发现（写视频表）→ 处理 | ✓ | 节奏不同 | 断开 | 视频表（待判定） |
| 判定 → 采集评论 | ✗（要重新打开视频） | — | 同一流程 | — |
| 采集（写评论表）→ 评分 | ✓ | 资源不同（评分不占手机） | 断开 | 评论表（待评分） |
| 评分（写线索表）→ 触达 | ✓ | 一对多 + 按号的额度 | 断开 | 线索表（待触达） |

⇒ 能力「智能获客」下四个流程：
- 抖音·视频发现（关键词 / 对标两种找法），每天 1~2 次：预检 → 取关键词 → 搜索取视频 → 过滤去重 → 写视频表 → 收尾
- 抖音·视频处理，一天多轮，从视频表取「待判定」：预检 → 判定视频（逐个）→ 采集评论（只采合格的）→ 收尾
- 抖音·评论评分，有新评论就跑，不占手机：取待评分评论 → 打分（逐条）→ 标记人 → 写线索表
- 抖音·线索触达，全天按每个号的额度：预检 → 取线索 → 发私信（逐条，按额度）→ 回填 → 收尾

**问题二表（节选）**

| 段 | 输入 | 能验收的结果 | 后面失败能从这里重来吗 | 结论 |
|---|---|---|---|---|
| 预检（打开抖音、拿锁、确认账号） | 设备、账号 | 锁在手、账号确认 | 能 | Activity（发现 / 处理 / 触达共用） |
| 判定视频 | 视频表待判定行 | 判定结果写回视频表 | 能 | Activity |
| 发私信 | 线索表待触达行 | 每条线索的发送结果 | 能 | Activity |
| 收尾（关抖音、放锁） | 本次运行的设备 | App 已关、锁已释放 | 能 | Activity（三个流程共用） |
| 点「发送」 | — | 没有 | 不能 | Step（属于「发私信」） |
| 往下翻一页 | — | 没有 | 不能 | Step（属于「搜索取视频」） |

去重：视频在发现阶段去重（先「标题 + 作者」过滤，取到链接后按视频 id 确认，排除自家账号视频）；
人不删只标记（已触达过、多次出现，多次出现可调高意向等级）。

现状：wf-run.sh 目前把发现 / 处理 / 评分连成一轮顺序跑完 =「一个执行者顺序跑多个流程」，树按 4 个流程登记，实现以后再拆。

## 4. 对照样例

| 接缝 | ① 能放下 | ② 分开跑的理由 | 结论 |
|---|---|---|---|
| 视频剪辑：转录 → 场景 → 字幕 → BGM → 输出 | ✓ | ✗（总是连着跑，资源和节奏都一样） | 同一流程，6 个 Activity |
| 安卓发布：各平台之间 | ✓ | 资源不同（不同账号、不同 App） | 每个平台一个流程（预检 → 上传填写 → 发布 → 读回 → 收尾，预检和收尾共用） |

**和之前版本的差别**：v3.0 只问「能不能放下」，会把视频剪辑这种能放下但总是连着跑的流水线切碎；v3.1 加上
条件②，默认同一流程。v3.0 的「平台不同就是不同能力」也已作废——抖音、小红书是同一能力下带平台前缀的流程。

## 5. 与账本的关系（别把颗粒度塞错地方）

- 流程 → `workflows`（触发 / 时长预算 / 失败策略）；断开处的交接表就是下一个流程的触发来源；
- Activity → `activities`（输入 / 承诺 / 输出 / 读回 / 执行体），在流程里的位置只认 `workflow_activity_refs`；
- Step → `steps`（真身在仓库 step-dod.json，`sync-steps-from-workspace.mjs` 灌入），每步带读回与实现进度；
- 一次运行 → `runs`（一个流程的一次运行）+ `spans`（每个 Activity 执行一条）；
- **禁止**为了「每一段都能单独管」把 Step 抬成 Activity——颗粒度该去 Step 层要。
