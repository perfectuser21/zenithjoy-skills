# RPA 审计规则清单

> 条目数以本清单实际内容为准（规则会持续吸收新实战案例，标题不写死数字——写死条数本身就是 A2）。

每条含：判定标准、检查方法（grep 探针只是粗筛，判定靠通读）、真实案例出处、建议修法方向。
案例全部来自 2026-08~09 获客/发布线真机实战，不是假想。

## 目录

- A 定位与坐标（A1-A6）
- B 等待与重试（B1-B6）
- C 验证与证据（C1-C7）
- D 错误处理（D1-D2）
- E 状态与并发（E1-E3）
- F 工程卫生（F1-F7）

## A 定位与坐标

### A1 写死坐标 [P0]
**判定**：代码里出现具体像素/千分比坐标常量并被用于点击或验证。
换分辨率、UI 改版即全盘失效。
**探针**：`grep -nE 'input tap [0-9]+ [0-9]+|positions? ?= ?\{|\([0-9]{3}, ?[0-9]{3}\)' <脚本>`
注意：比例坐标（`cx/1000`）同样算写死——它写死的是**布局位置**，面板整体位移照样废。
**案例**：0911 筛选面板选中态验证表 `("time","one_day"):(374,369)`，抖音把排序砍一行后
全表错位 0.056，该步永远判失败。
**修法**：结构检测（扫 chip 色块自动找行列）或从无障碍树 bounds 取。

### A2 写死结构假设 [P0]
**判定**：行号/列号/序号/条数等结构量被硬编码（"第 2 行是发布时间""排序占 2 行"）。
比坐标更隐蔽——坐标看起来是算出来的，但行索引是数出来的。
**探针**：`grep -nE 'row_?index|第[0-9一二三四五]行|\[[0-9]\]' <脚本>` 后通读消费处。
**案例**：0911 抖音把排序从 5 项 2 行砍成 3 项 1 行，所有下游行整体上移一格，
`location` 被算到按钮行上。
**修法**：从**稳定锚点**推导（"位置距离永远是最后一个筛选行，往上依次是…"，即底部锚定），
并写明为什么该锚点稳定。

### A3 定位与验证两套机制 [P1]
**判定**：同一元素，点击侧和验证侧用不同的定位方法。一套修了另一套还错，必然漂移。
**检查**：找出每个"点击→验证"配对，确认两侧共享同一定位函数/算法。
**案例**：0911 同一文件里 `locate_filter_option` 是结构检测（对），
选中态验证却是写死千分比表（错）。
**修法**：验证复用定位的同一套检测，或直接对定位结果处取样。

### A4 空间数据（无障碍树）优先原则缺失 [P1]
**判定**：能从树取 bounds 的元素却直接上视觉/坐标。树优先→视觉降级是死规则。
**检查**：对每个视觉定位点问一句"树里真的没有吗"，要求代码或注释给出证据
（如 0909 实证：评论按钮 content-desc 在但 bounds 恒 [0,0][0,0]——这种才允许视觉）。
**案例**：0909 open-comments 曾靠视觉猜，后实测树里有真实 bounds+clickable=true。
**修法**：先读树；树确实不含该元素（要留证据）才降级视觉。

### A5 明知树不可用还在树上死磕 / 明知可用却不用 [P1]
**判定**：A4 的反面成对出现。综合 tab 的 feed 永不 idle（树结构上读不到），
在那儿重试是纯浪费；视频 tab 是静态网格（同秒 dump 出 182 节点），不读树是自找视觉坑。
**检查**：每个读树点要能回答"这个页面树是否可达"，且快慢路径匹配：
结构上不可能 → 单次快速失败立刻降级；已知存在 → 持久重试（见 B3）。
**案例**：0912 我把三波重试加进"机会性读树"路径，切 tab 前白烧 180 秒才肯退视觉兜底。
**修法**：区分「必须拿到树」（持久重试）与「机会性读树」（单波快速失败降级）两类调用。

### A6 缓存坐标无失效机制 [P1]
**判定**：`locate_cached` 类缓存没有版本/校验/清除路径，布局变了还在用旧坐标。
**探针**：`grep -n 'cache' <脚本>`，确认失败路径会 `cache_clear`。
**案例**：0911 筛选按钮缓存坐标在面板改版后点空，幸好失败分支里有 cache_clear 才自愈。
**修法**：使用缓存坐标的动作失败时必须清缓存重定位；缓存键里带布局特征更佳。

## B 等待与重试

### B1 单次尝试无重试 [P0]
**判定**：点击/读取一次失败就 die，且失败对象是"已知存在的东西"。
主理人原则（0912）：**已知存在的东西，不该一次读不到就放弃——连试几次、隔一会儿再试几次。**
**探针**：`grep -nE '\|\| die|\|\| return 1' <脚本>` 逐个看前面是不是单次操作。
**案例**：0911 「加载中，请稍后~」toast 挂着时点筛选被吞，单次点击+900ms 必然失败。
**修法**：有界重试；且重试前先验证目标状态是否已达成（防重复点击把已开的面板点关）。

### B2 背靠背重试（波内不等待） [P0]
**判定**：循环重试但迭代之间无 sleep。页面在动时 N 次瞬发全部同样失败，等于只试一次。
**探针**：重试循环内找不到 `sleep/wait_ms`。
**案例**：0912 读树旧实现 `for 1 2 3` 三次 dump 之间零间隔。
**修法**：波内短间隔（~1s）+ 波间长间隔（10s/20s 递增）分层。

### B3 重试预算与超时语义 [P1]
**判定**：(a) 多层重试嵌套没算过总账（控制器波 × stage 次数 × canvas 重问，最坏时长是乘积）；
(b) 把超时**下限**当**上限**用，为塞进预算削韧性。
**检查**：找出所有层的重试参数，算最坏总时长；核对 skill 里 timeout 字样写的是 ≥ 还是 ≤。
**案例**：0912 skill 写「timeout ≥ 120000ms」（下限），我误当上限把三波砍成两波；
纠正后下限抬到 300000ms 以容纳三波（~180s）。
**修法**：每层预算显式写在注释里，总最坏时长 ≤ 外层超时下限的 60%。

### B4 固定节奏（不拟人） [P1]
**判定**：面向平台的操作序列间隔恒定、零抖动（如每次精确 300ms）。风控视角就是机器人。
**探针**：`grep -nE 'wait_ms [0-9]+' <脚本>`，看面向业务操作（点赞/评论/私信/翻页）的
间隔是否全是同一常量。仅设备管理类操作（dump/pull）可以固定。
**案例**：dm 私信线 0821 定版随机间隔 120-180s，就是为了这条。
**修法**：业务操作间隔用区间随机；批量循环里加自然停顿。

### B5 等待无上界或无下界 [P2]
**判定**：`while true` 等待无退出条件；或依赖"等 X 秒页面一定就绪"的裸 sleep 而非条件等待。
**案例**：0818 NO_SEARCH_INPUT 修四次的根因就是裸 sleep 换不来条件成立，
最终 16 个调用点全迁两层条件等待。
**修法**：condition-based waiting：轮询目标条件 + 超时上界。

### B6 重试把非幂等操作重复执行 [P0]
**判定**：重试循环里包着会产生副作用的业务动作（发送/发布/评论），失败重试=重复发送。
**检查**：每个重试循环里列出副作用操作，确认它们幂等或在重试范围之外。
**案例**：skill 里 claim_then_send 模式（先领单占位再发送）就是为这条设计的。
**修法**：副作用动作放重试循环外，或用幂等键去重。

## C 验证与证据

### C1 只验证动作发生、不验证结果正确 [P0]
**判定**：判据是"命令返回 0 / 会话结束 / workflow 绿"，而不是产物本身
（线索条数、文件大小、DB 行数、帖子真实出现）。
**案例**：0911 四大病根——cron 报 ok 实际 0 线索、备份报 OK 但 db=4.0K、
n8n onError 吞错、n8n publish "Activated" 但内容一字没变。
**修法**：验收断言写到产物上（ffprobe 有流、DB 有行、表里条数增加）。

### C2 结构校验通过 ≠ 内容有效 [P0]
**判定**：只查外壳（XML 有 `<hierarchy>` 标签、JSON 能 parse）不查业务内容
（有没有卡片节点、字段是否非空）。
**案例**：0911 空壳树 9272 字节、仅 8 个文本节点，通过了结构校验被当成功，
下游"抽卡片 0 张"被误判为没有视频。
**修法**：校验加业务断言（节点数下限 / 必含关键元素），并区分
「内容为空的合法状态」（页面明说"搜索结果为空"→ 输出 empty_results=true）与「读取失败」。

### C3 前置条件不校验 [P0]
**判定**：宏命令不确定性校验自己"站在哪个页面"就开始点。
**案例**：0912 worker 在「我」个人主页上直接调筛选命令，点空 + 白烧 4 次重试，
报错还是含糊的"面板未打开"。修法是加"树里必须有搜索 tab 栏"前置校验后，
错误变成准确的"not on a search results page; call open-search first"。
**修法**：每个宏开头校验前置页面特征，失败立刻给出**准确**的错误与下一步指引。

### C4 关键操作后不回读 [P0]
**判定**：点击/关闭/释放后不验证状态真的变了。
**案例**：0821 私信案 `searchBtnFound=true` 点完后前台被 ROM 抢走，猜着改了三轮；
close-app 后必须回读前台非抖音、lock-release 后必须回读 lock=free（skill 已有此规则，
查脚本是否真做了）。
**修法**：动作后回读目标状态；前台包名是最便宜的回读。

### C5 失败路径不留三件套证据 [P2→P1]
**判定**：失败分支没有留下「前台包名 + 诊断行 + 截图」（真机死规则），下次排查还得重抓。
**探针**：每个 `die` 前面有没有 snapshot/evidence 落盘。
**案例**：0821 教训写进 CLAUDE.md：缺一件=你在猜。
**修法**：die 之前落一张截图 + 打一行前台包名。

### C6 UI 文案锚点散落无登记 [P2]
**判定**：判定逻辑依赖中文文案精确匹配（"搜索结果为空""加载中"），
散落在代码各处、无集中清单，平台改文案即静默失效。
**探针**：`grep -nE '"[\p{Han}]{2,}"' <脚本>`（或直接 grep 常见文案）。
**修法**：文案锚点集中成表（常量区/单文件），每条标注来源截图与验证日期。

### C7 证据文件覆盖 [P2]
**判定**：evidence_id 或输出路径可被复用覆盖，翻车现场被下一次运行冲掉。
**检查**：证据文件名是否含 run_id/时间戳等唯一成分。
**修法**：证据命名带唯一键；或写前检查已存在则报错。

## D 错误处理

### D1 吞错 [P0]
**判定**：`|| true`、`2>/dev/null` 后不检查、`onError: continueRegularOutput`、
catch 后继续——把失败包装成成功。
**探针**：`grep -nE '\|\| true|2>/dev/null' <脚本>` 逐个核对是否真的可忽略。
**案例**：0911 n8n 节点 onError 吞掉 131 秒 TCP 超时报 finished successfully，
真相被瞒 14 小时。
**修法**：错误要么处理要么上抛；确要忽略的写注释说明为什么安全。

### D2 含糊报错 [P1]
**判定**：错误信息不含现场（在哪个页面、期望什么、实际读到什么），排查者只能重现一遍。
**案例**："filter panel did not open" 掩盖了真相是"站在个人主页上"；
"panel signature missing (0.000, 1.000)" 带了实测值，就直接指向了区间不重叠。
**修法**：报错带关键测量值与页面特征；能区分的失败原因不要合并成一句话。

## E 状态与并发

### E1 幂等/锁标识不归一 [P0]
**判定**：同一逻辑轮次在不同阶段用不同标识形态（run_id / execution_id 带冒号 /
带阶段后缀 `-a1-preflight-1` / 下划线变体），锁与幂等键互不相认。
**案例**：0911-0912 锁 owner 出现过 4 种写法，preflight 拿的锁 discovery 认不出
直接 blocked；修法是 normalize 到 run 根（剥 `:` 与 `[-_]a<N>[-_]*` 后缀）。
**修法**：入口处统一归一化；校验器首字符必须字母数字（防 `--help` 这类选项串被当 id，
0911 实锤 `--help` 占锁）。

### E2 锁无 TTL / 无 stale 回收 [P0]
**判定**：裸 mkdir 锁，持有者死了锁永不释放，卡死后续所有轮次。
**案例**：0909 与 0911 各损失 2 轮；cron 旁路 20:30 抓锁后被网关重启杀死，孤儿锁 80 分钟。
**修法**：锁带时间戳，超龄 + 持有者不在（无对应会话/进程）才可回收，回收要留日志。

### E3 清理不闭环 [P1]
**判定**：cleanup 只发命令不回读（同 C4 但特指资源释放），或非 cleanup 阶段的 worker
擅自释放锁/关 App（越权清理会踩掉并行 run）。
**案例**：skill 已明文"只有 stage_id=cleanup 的 Worker 可以释放锁"，审计脚本是否有
非 cleanup 路径调 lock-release/close-app。
**修法**：释放动作集中在 cleanup；每个释放后回读。

## F 工程卫生

### F1 控制器脚本不在 git [P0]
**判定**：SKILL.md 引用的执行体（`~/.local/bin/*`、`/usr/local/bin/*`）在任何仓库都
找不到 source of truth。
**案例**：`douyin-phone-adb` 95KB 只在 M4 本机，0911 一夜 8 处修复全无版本管理，
机器一换全丢。
**修法**：脚本入仓 + 部署脚本分发；本机副本视为构建产物。

### F2 死代码 / 损坏代码残留 [P2]
**判定**：从未被调用的函数、被批量编辑改坏的代码块（变量名变空串、嵌入报错文本）。
**案例**：`ui_evidence_retry` 零调用，且内部 `"$ADB"` 全变 `""`、嵌着
`zsh:1: permission denied:` 字样——一次失败的批量编辑无人发现。
**探针**：对每个函数 grep 调用点；肉眼扫空字符串引用。
**修法**：删除；需要保留的写明保留原因。

### F3 让 LLM 转抄长标识符 [P1]
**判定**：流程要求 Worker（LLM）把 64 位 hash、长 URL、长 ID 从一处抄到另一处。
**案例**：0912 worker 抄 task_request_hash 多抄一个 `f`，整格 retry。
**修法**：长标识符走文件/参数/剪贴板传递；协议校验端明确报"多了尾部字符"这类差异。

### F4 高危控件无护栏 [P0]
**判定**：可能触达发布/发送/支付/输入框聚焦的点击没有护栏与禁区声明。
**案例**：零评论视频不点评论入口（点开就是带「发送」的发布框，风控高危）；
绝不留在已聚焦输入框状态退出。
**修法**：高危区域列显式禁区；点击前判定目标不在禁区内；异常退出路径先 back 脱离聚焦。
**补充判定（0912 对照组审计贡献）**：`locate-tap`/`tap` 这类"任意描述→点击"的万能入口
若不与禁区表联动，等于给了 Worker 绕过全部护栏的后门——万能点击入口必须强制过禁区检查。

### F5 修改流程无原子性 / 飞行中修改 [P1]
**判定**：脚本更新用非原子写（直接重写文件），或运维习惯允许 run 在飞时改控制器。
**案例**：0912 在飞行中改脚本打死 preflight 两次；后改为写临时文件 + `os.replace`。
**修法**：部署用原子替换；改前检查无 run 在飞（查锁/查执行表）。

### F6 单文件过大 [P2]
**判定**：控制器单文件 > 1500 行 / 80KB，改一处怕碰全身，批量编辑事故率高（见 F2）。
**修法**：按域拆分（锁/定位/证据/宏各一模块）；至少把纯函数抽出可单测的文件。

### F7 数据外发未披露 / 未计数 [P0]
**判定**：脚本把截图、UI 树、用户内容发给第三方服务（视觉 LLM / 云 OCR / 任何外部 API），
但 SKILL.md 未披露该外发行为，或协议计数（如 `external_interactions`）未把它计入。
**案例**：0912 对照组审计发现视觉定位把手机截图外发第三方视觉模型，
skill 协议里 `external_interactions` 恒报 0——外发既未披露也未计数。
**修法**：所有外发点在 SKILL.md 显式列出（发什么、发给谁、何时发）；协议计数如实累计；
能本地做的（如结构检测）不外发。

## 附：快速粗筛探针合集（只做线索，不做判定）

```bash
T=<脚本路径>
grep -nE 'input tap [0-9]+ [0-9]+' $T                 # A1
grep -nE 'positions? ?= ?\{|\([0-9]{3}, ?[0-9]{3}\)' $T  # A1/A2
grep -nE '\|\| true|2>/dev/null' $T                   # D1
grep -nE 'mkdir .*lock|LOCK_DIR' $T                   # E1/E2
grep -n  'cache' $T                                   # A6
grep -nE 'wait_ms [0-9]+|sleep [0-9]' $T              # B2/B4/B5
grep -cE '^\s*(function |[a-z_]+\(\))' $T             # F6 规模感
```
