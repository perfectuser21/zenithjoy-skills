# rpa-audit — Android RPA 反模式审计器

## 为什么有这个 skill

2026-09-11 通宵获客攻坚一夜修了 8 个独立缺陷，全部属于**可机械检查**的反模式：
写死的行索引被抖音改版打翻、单次点击无重试被"加载中"吞掉、`--help` 被当 run_id 占锁、
同一文件里定位用结构检测而验证用写死千分比……这些坑不该靠下一次真机翻车再发现一遍。
本 skill 把它们固化成一份规则清单（每条都有真实案例出处，持续吸收新案例），审计任何 RPA skill / 控制器脚本。

## 审计范围（两层都要查，缺一不可）

1. **SKILL.md 层**：规则写得对不对、给 Worker 的约束全不全。
2. **控制器/脚本层**（`*.sh` / `*-adb` / `scripts/*.mjs|py` 等实际执行体）：实现有没有违反。

> 0911 实证：skills 里的规则写得全是对的（5 处以上明令禁止猜坐标），
> **违规发生在适配器内部**。只查 SKILL.md 会漏掉真正的问题。

## 执行流程

1. 确认被审计对象：skill 目录 + 它声明的控制器/脚本路径（从 SKILL.md 里找
   `adb_controller`、`scripts/`、`~/.local/bin/` 等引用；找不到实际脚本本身就是 F1 违规）。
2. 读 `references/checklist.md`（规则全文 + 检查方法 + 真实案例）。
3. 先跑清单里给出的 grep 探针做粗筛，再**通读代码**核对每条——grep 只是线索，
   判定必须基于对上下文的理解（比如 `positions = {…}` 是不是写死坐标，要看它怎么被消费）。
4. 每条结论必须带证据（file:line + 原文摘录）。查不了的条目（如需要真机才能验证的）
   明确标注 SKIP 及原因，不许静默跳过。

## 输出格式（固定模板）

```markdown
# RPA 审计报告：<对象名>
审计时间：<UTC> ｜ 对象：<skill 路径> + <脚本路径列表>

## 违规（按严重级排序）
### [P0] A1 写死坐标 — <file>:<line>
证据：`<原文摘录>`
危害：<一句话，引用规则里的真实案例>
建议：<具体修法，不代改>

## 通过项
- A2 ✅ / B1 ✅ …（一行一条，清单里每条都要有着落）

## SKIP 项
- <规则号>：<为什么查不了>

## 总评
<P0 数 / P1 数 / P2 数；能不能上线的一句话判断>
```

严重级：**P0** = 会直接导致真机翻车或静默假成功；**P1** = 会在 UI 改版/机型更换时翻车；
**P2** = 工程卫生，短期不炸但埋雷。

## 铁律

- **只报不改。** RPA 脚本在有 run 在飞时被修改会打死 worker（0912 实锤两次），
  修改权在人和后续的 /dev 流程，不在审计器。
- 30 条每条都要有着落（违规/通过/SKIP 三选一），不许漏。
- 结论必须可复核：别人拿着报告里的 file:line 能立刻找到现场。
