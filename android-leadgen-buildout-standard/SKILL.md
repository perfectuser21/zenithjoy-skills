# 安卓关键词获客新平台搭建标准流程

> 本文档取代此前误用的"EXPLORE→VALIDATE(连续3次零新坑跨2台机)→HARDEN→FROZEN"模型
> （那是 `android-publish` 给"发布"类动作定的协议，被 0921 凌晨一次对话误套到"获客"上）。
> 真身协议是 `services/phone-adb-controller/COMMANDER.md` 的"熟化四态"，本文档是照抖音
> line02 0908-0921 真实历史提炼出的可复用标准，供快手/小红书/视频号（0919已完成EXPLORE，
> 见 `android-kuaishou-leadgen`/`android-xiaohongshu-leadgen`/`android-shipinhao-leadgen`）
> 接下来写ADB代码时直接抄。

## 核心结论：路径顺序，7月Kotlin先行是错误路线不要复制

抖音真实演进（有commit/handoff证据）：**07月Kotlin先探路(`services/agent-android/collect/
DouyinCollectService.kt`)→09月ADB shell脚本(`douyin-phone-adb`)后来居上直接抢跑上生产、
脱离git边跑边改→踩坑当场用uiautomator锚点修→09-14才回流git+反哺Kotlin经验→Kotlin正规军
固化被主理人当场拍板"过段时间再说"（主动推迟，不是走到的终态）**。

0921 主理人明确拍板：**7月Kotlin先行是错误路线，不用管；9月这条"脚本→ADB→(未来再考虑)
连Kotlin"才是走对的路，以这条为准**。

## 标准流程（新平台照这个走，不要走"先攒够验证再写代码"那套）

1. **EXPLORE**：真机走一次完整判定树，产出SKILL.md（快手/小红书/视频号0919已完成这步）
2. **直接写 `<平台>-phone-adb` 脚本**：命令对应判定树的每个动作原语（open-search/
   open-comments/collect-comments/tap-comment-avatar/open-dm等）。**uiautomator语义锚点
   从第一天就定为铁律**（树优先，坐标只是无障碍树不可用时的兜底）——这是本轮复盘明确指出的
   "应该更早引入"的优化点：抖音0908/0909两轮都在"坐标点不准"上反复试错，直到0909才确立
   "树优先"原则，多返工了至少两轮。新平台不用再交这个学费。
3. **脚本写完直接真机跑，不追求"先验证N次再写代码"**：按抖音实证，边跑边修比先攒够验证快。
   踩到的坑当场用uiautomator锚点修，不要停下来走额外的验证仪式。
4. **每个坑当场判断是否触发"熟化四态"**（见下方COMMANDER.md章节）：同一判例第2次出现标
   `[固化候选]`，第3次强制开dev单代码化，不是凭感觉判断"差不多该固化了"。
5. **编排层健康监控从第一天接入**：抖音的坑是09-09 n8n升级打死了整个编排层，到09-11才被
   主理人质问出来才发现——中间两天编排层完全没人管，cron旁路裸奔且看起来正常。新平台如果
   接了编排层（今晚为抖音验证的账本+Jev+schema那套），必须有"编排层本身是否存活"的独立信号，
   不能只看下游产物"看起来正常"就默认编排层活着。
6. **业务规则在设计阶段就想清楚，别指望运行中发现再补**：抖音的"评论数>0才开评论区"/
   "most_liked排序"/"按视频逐条结算"这几条规则，实际是09-13主理人当场拍板才补上，此前
   多轮"0线索"里相当比例是选中了评论数为0或冷门视频导致的空转。
7. **私信真发前必须留白到明确批准**——这条不变，三个平台的skill文档都已经这么写了。
8. **规则验证过之后，交给系统自动执行，别每次都停下来问**：0916主理人原话敲打过"触达该发就
   发呀，我不知道你为啥要听，谁让你听的"——0914触达链验证通过后AI把"要不要恢复"的判断权交
   还给主理人，导致产线空转了一整天。**这条跟"先VALIDATE再执行"的直觉正好相反**，规则一旦
   验证过就该自主推进，不是每次都请示。

## 预防清单（新平台从第一天抄，全部有真实事故支撑，不是理论推演）

| 规则 | 事故证据 |
|---|---|
| 任何"临时/热修"必须带复验日期，到期不复验报红 | 飞书写权限被热修换成只读账号，三周没人复验，表现为91403 Forbidden(0911) |
| 失败原因必须落进人会看的字段/表，不能只进日志 | 私信NO_SEARCH_INPUT同一个bug被"修复"四次都没修对，根因是`error_code`写进JSONB字段没人看 |
| 判据用"产物是否符合预期"，不用"命令返回码" | affine/cecelia备份脚本迁移后原地空转，`db=4.0K`空dump照样报OK |
| 服务迁移后必须同步排查原位置遗留cron/备份是否还在空转 | 同上 |
| 账号身份判定用三态(personal/organization/id_not_visible)，不要二态硬判 | 认证企业号无「抖音号」字段返回空被误判"不匹配"，整批已采客资被一票否决扔掉(0913,本轮坑里代价最高) |
| 字符串比较要normalize，不能裸`==` | 主页显示`Zenithjoyai`、搜索页显示`zenithjoyai`，大小写不一致判"不是同一人"静默拒发(0916) |
| 设备锁要有TTL，避免孤儿锁 | 裸`mkdir`占锁无过期机制，跑超预算的活锁卡住后续整批(0911/0913各损失2轮) |
| run_id/attempt_id不要混用同一变量占锁 | worker把attempt_id当run_id占锁，同一次run自己的错误锁挡死自己后续尝试(0913) |
| "只验证动作发生了，不验证结果对不对"是反复出现的根子 | 独立出现在4个事故里：cron报ok实际0线索、affine备份假绿、热修账号三周不复验、n8n onError吞错 |

## 复发多次的坑（Top3，系统性弱点，最值钱）

1. **私信NO_SEARCH_INPUT修了四次才修对**——前四次全部假设"等得不够久"，真凶是抖音冷启动
   闪屏整整10秒而等待只设了6秒。四次盲修的共同原因正是"失败原因没有落进人会看的地方"。
2. **"服务迁走、备份cron留在原地空转并假绿"复发三次**——判据只看命令返回码不看产物大小。
3. **n8n发布版本快照≠草稿**：编辑器改的内容不生效，实际执行三周前旧快照，指向已失效地址，
   TCP重试耗尽后被`onError:continueRegularOutput`吞掉判成功——编排层静默停摆一整天无人发现。

## COMMANDER.md「熟化四态」——实际在用的机制，不是android-publish那套

权威源：`services/phone-adb-controller/COMMANDER.md`（决策地基`7465d08f`/`dcdaa83e`/`9237202c`）。

**四态**：发现（FINDINGS/抽查）→蒸馏（进SOP，走PR留痕）→固化候选（同判例≥2次标
`[固化候选]`）→代码化（同判例≥3次强制开dev单写成守卫代码，SOP同步删掉该条）。

**运作载体**：
- 轮内记忆：custom session `escort-<机器>-<TAG>`，同批次内多次tick共享上下文
- 夜际记忆：`/root/.openclaw/escort-findings.md`，escort每次收工前写新发现，下次开工先读
- 升级史：`escalation-reports.log`，记录分身每次出勤的现场证据、采取的动作、剩余风险

**已真实运作起来的案例**：0914分拣规则闸(`ruleJudge()`)、`classify_failure`三态归因、瞬时
重试循环——都是从判例反复出现最终固化成代码守卫的真实样板。0916那次"55个smoke守卫假绿"的
大自查，某种意义上也是这套机制在自我纠错。

**驱动机制**：每次有头/分身救场收尾必须自答"这个判例能否固化进SOP/白名单/代码？"——这是
驱动四态往前走的唯一机制，不是定时任务或自动统计触发的，需要人/AI主动回答。
