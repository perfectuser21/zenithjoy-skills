# Eval V2.0 SOP：客观评测与 Baseline 对比流程

本文件用于 customer-chat-analyzer / 日报 Skill 的评测流程。V2.0 的目标是让 Eval 更全面、公正、客观、可复测，并避免把少量样本误用为正式验收结论。

## 一、适用场景

使用本 SOP 当用户要求：

1. 测试或演示 Skill 的效果。
2. 对 Skill 进行严格验收。
3. 与无 Skill 输出做 Baseline 对比。
4. 修改 Skill 后做回归测试。
5. 评估 Skill 是否可交给团队长期使用。

## 二、Eval 前置确认

当用户只说“测试一下”“跑 Eval”“做验收”“做回归”“对比一下”，但没有明确测试类型时，不得直接运行默认样例，必须先询问用户选择本次测试类型：

1. 快速冒烟测试：6 个固定核心样本，只验证核心流程是否跑通。
2. 小型回归测试：最低 12 个样本，推荐 15 个样本，验证修改后是否破坏主要规则。
3. 正式上线验收：最低 30 个样本，推荐 30-50 个样本，判断是否可交给团队使用。
4. 重大规则更新验收：最低 50 个样本，推荐 50+ 个样本，判断复杂场景下是否稳定。
5. 自定义测试：用户指定样本数量、资料包、评分重点或输出形式。

用户确认测试类型后，再按对应样本数量、覆盖规则、二值断言评测表和硬性失败项执行。若用户已经明确测试类型，则不重复询问。

## 三、Eval 组成

每次正式 Eval 至少包含 6 个文件或记录：

1. `eval_input.md`：测试输入。
2. `golden_answer.md`：标准答案。
3. `baseline0_output.md`：Baseline 0 输出。
4. `baseline1_output.md`：Baseline 1 输出。
5. `skillrun_output.md`：Skill Run 输出。
6. `eval_report.md`：二值断言评测、对比、典型客户证明和结论。

如果当前环境无法启动独立模型实例生成 Baseline 0 和 Baseline 1，必须在报告中明确说明“本次仅完成 Skill Run 回归评测，Baseline 0 和 Baseline 1 待团队在独立会话中补跑”，不得假装已经完成盲评 baseline，也不得输出 Skill 相对 baseline 的提升分差。

## 四、Baseline 与 Skill Run 定义

| 名称 | 含义 | 用途 |
| --- | --- | --- |
| Baseline 0 | 不使用 Skill、不使用专门日报模板，只给模型最基础提示词，让模型自由分析客户聊天记录。 | 用来观察普通模型在无结构约束下的自然表现。 |
| Baseline 1 | 不使用 Skill，但给模型一个普通分析模板，例如客户阶段、客户意向、主要顾虑、下一步动作、建议回复。 | 用来观察“普通模板提示词”能带来的提升。 |
| Skill Run | 使用本 Skill，按 Skill 内置规则、资料范围、A1-A4 阶段、四感模型、询价分级、风险识别、两层日报结构输出。 | 用来评估 Skill 本身相对于普通模型和普通模板的提升效果。 |

Eval 报告中的对比结论，必须基于同一批测试输入、同一份 Golden Answer、同一套二值断言评测表，分别评测 Baseline 0、Baseline 1 和 Skill Run 后得出。不得用不同样本、不同评测标准进行横向比较。

## 五、测试集设计

### 1. 样本规模

不得把 6 个样本作为所有 Eval 的默认测试量。用户选择哪个测试类型，就必须按该测试类型对应的最低样本数和推荐样本数执行。

| 测试类型 | 最低样本数 | 推荐样本数 | 作用 |
| --- | ---: | ---: | --- |
| 快速冒烟测试 | 6 | 6 | 只验证核心流程是否跑通 |
| 小型回归测试 | 12 | 15 | 验证修改后是否破坏主要规则 |
| 正式上线验收 | 30 | 30-50 | 判断是否可交给团队使用 |
| 重大规则更新验收 | 50 | 50+ | 判断复杂场景下是否稳定 |

样本不足时，必须说明：“当前样本不足，不能判定为该测试类型正式通过，只能作为样本不足测试或部分回归测试。”

### 2. 样本覆盖规则

Eval 当前采用整批样本通跑，不要求每个样本单独标注场景标签，但整批样本必须满足对应规模的覆盖要求。

#### 6 个快速冒烟样本

6 个样本必须固定覆盖 6 类核心边界，每类 1 个：

| 样本 | 必须覆盖的场景 | 测试目的 |
| --- | --- | --- |
| 1 | A1 初聊 / 防推销 / 不清楚需求 | 检查是否补确认感、安全感，而不是强推成交 |
| 2 | A2 已买低价入口 / 补资料 | 检查是否识别强推进，并收口到资料提交和体验复盘 |
| 3 | A3 中阶产品后升级正价 | 检查是否识别结果感、合同范围、付款方式等收口信号 |
| 4 | A4 签约付款 / 启动交付 | 检查是否处理启动清单、角色分工、资料权限和边界控制 |
| 5 | 调研型询价 / 预算收集 | 检查是否误判为购买型询价，是否强推付款 |
| 6 | 高风险 / 保成交 / 保退款 / 拒绝配合 | 检查是否识别暂不适配，而不是继续强推 |

6 个样本只能证明核心流程能否跑通，不能证明 Skill 已经稳定或可以正式上线。

15 个样本应采用轻量分层覆盖，建议结构如下：

| --- | ---: |
| A1 初聊 / 防御 / 不清楚需求 | 2 |
| A1 模糊询价 / 只问多少钱 | 2 |
| A2 已买低价入口 / 补资料 / 体验中 | 2 |
| A3 中阶产品后升级正价 | 2 |
| A4 签约付款 / 启动交付 | 1 |
| 调研型询价 / 比价 / 预算收集 | 2 |
| 高风险 / 保成交 / 保退款 / 拒绝配合 | 2 |
| 资料缺失 / 禁止编造 | 1 |
| 历史资料冲突 / 连续跟进变化 | 1 |
| 合计 | 15 |

15 个样本用于验证修改后是否破坏主要规则，不能替代正式上线验收。

## 六、测试资料包与事实边界

判断是否编造，不看测试资料是不是真实客户，而看这些信息是否在测试样本里预先提供。

Eval 中允许使用测试样本、测试资料包、数据库资料或用户提供内容中明确给出的模拟事实。测试样本里预先提供的模拟价格、合同范围、退款规则、客户案例、交付周期、付款节点或效果数据，可以作为本次测试事实使用。

如果测试样本没有提供具体价格、合同条款、退款规则、客户案例、交付周期、付款节点、效果数据，模型不得自行补充。模型输出了测试样本、测试资料包、数据库资料或用户提供内容之外的具体价格、客户案例、合同条款、退款规则、交付周期、付款节点或效果承诺，且未标注“未提供/待补充/暂无法判断”的，判定为事实越界编造，Eval 直接不通过。

以下两种情况即使没有写出具体数字，同样判定为事实越界编造：

1. 以既有资料口吻承诺发送测试样本未提供的材料，例如"我们正好有专门的案例/模型/报价单，一并发您""案例今天下午发您"。正确写法是标注"未提供/待核实后补充"，并给出可用已提供内容支撑的替代动作。
2. 输出模糊数字量级充当价格，例如"几千到几万""数万级投入"。量级也是价格信息，未提供即不得输出。


## 七、Baseline 设计

### Baseline 0：普通分析

提示词：

```text
请分析以下客户聊天记录，判断客户意向、主要顾虑，并给出下一步跟进建议。
```

### Baseline 1：普通模板分析

提示词：

```text
请按以下结构分析客户聊天记录：
1. 客户阶段
2. 客户意向
3. 主要顾虑
4. 下一步动作
5. 建议回复
```

### Skill Run：使用 Skill

提示词：

```text
请使用 customer-chat-analyzer / 日报 Skill，按本次分析资料范围、A1-A4 阶段、四感缺口、推进信号、询价分级、风险识别、下一步动作和两层日报结构生成客户日报。
```

## 八、Golden Answer 流程

1. 先写 Golden Answer，再跑 Baseline 和 Skill Run。
2. Golden Answer 必须写每个客户的正确阶段、推进信号、询价类型、主缺口、风险等级、下一步方向和禁止动作。
3. Golden Answer 必须标明已提供事实和未提供事实；模型不得越过事实边界。
4. 评测时允许不同表述，但核心判断不得偏离 Golden Answer。

## 九、二值断言评测流程

1. 确认测试类型、样本数量和覆盖规则是否匹配。
2. 固定 Golden Answer。
3. 分别运行 Baseline 0、Baseline 1 和 Skill Run；无法运行 baseline 时必须说明。
4. 先检查关键失败项。
5. 再按二值断言评测表逐项判定通过 / 不通过 / 需人工复核。
6. 选取 2-3 个典型客户，写“典型客户效果证明”。
7. 输出 Eval 报告。

## 十、二值断言评测表

| 评测项 | 核心断言 | 判定 | 证据要求 |
| --- | --- | --- | --- |
| 输入拆分与证据使用 | 是否正确识别所有客户，并能把判断对应到客户原话或资料证据？ | 通过 / 不通过 / 需人工复核 | 写明对应客户、原话或资料来源 |
| A1-A4 阶段判断 | 是否给出明确阶段，并且阶段判断与 Golden Answer 一致？ | 通过 / 不通过 / 需人工复核 | 对照 Golden Answer 和客户已完成动作 |
| 推进信号识别 | 是否正确识别无推进、弱推进、强推进，没有把弱信号误判为强推进？ | 通过 / 不通过 / 需人工复核 | 引用客户推进信号原话 |
| 询价分级 | 是否正确区分购买型询价、调研型询价、模糊询价？ | 通过 / 不通过 / 需人工复核 | 对照客户问价原话和 Golden Answer |
| 四感缺口判断 | 是否正确判断客户当前主缺口，并能对应客户真实顾虑？ | 通过 / 不通过 / 需人工复核 | 引用客户顾虑、犹豫、追问内容 |
| 高风险与不适配识别 | 是否识别高风险、不适配、保成交、保退款、拒绝配合等问题？ | 通过 / 不通过 / 需人工复核 | 引用高风险原话或行为 |
| 下一步动作可执行性 | 下一步动作是否具体到对象、动作、条件、资料或边界？ | 通过 / 不通过 / 需人工复核 | 检查是否不是“继续跟进、加强沟通”这类空话 |
| 建议回复话术 | 建议回复是否贴合客户阶段、顾虑和推进状态，可直接发送？ | 通过 / 不通过 / 需人工复核 | 对照客户当前状态和建议回复内容 |
| 连续跟进与变更记录 | 是否正确使用最近资料，并说明客户状态变化？ | 通过 / 不通过 / 需人工复核 | 对照历史资料、当日资料和今日变化 |
| 两层日报与汇总结构 | 是否先有单客户日报，再有所有客户汇总，且汇总来自单客户日报？ | 通过 / 不通过 / 需人工复核 | 检查输出结构和汇总依据 |
| 真实业务适配与不编造 | 是否没有输出测试样本外的价格、合同、退款、案例、交付周期、付款节点或效果承诺？ | 通过 / 不通过 / 需人工复核 | 对照测试样本、资料包、数据库资料或用户提供内容 |

## 十一、通过标准

| 结论 | 判定标准 |
| --- | --- |
| 通过 | 无关键失败项；核心项全部通过；整体大部分评测项通过；典型客户效果证明成立 |
| 部分通过 | 无关键失败项，但存在少量非核心项不通过，需要修改后回归 |
| 不通过 | 出现任一关键失败项，或核心能力项明显失败 |
| 需人工复核 | 涉及话术自然度、销售语气、业务适配等无法完全客观判断的内容 |

## 十三、输出 Eval 结果时的注意事项

1. 不得只输出评测汇总，必须说明典型客户差异。
2. 如果用户要求“公正、客观、全面”，必须使用 Golden Answer 和二值断言评测表。
3. 如果没有跑 baseline，不能写 Skill 比 baseline 高多少。
4. 如果没有独立评测者，不能写“盲评通过”。
5. 如果出现关键失败项，必须明确写“不通过”，不能用其他通过项掩盖。
6. 如果样本数量或样本覆盖不足，必须明确标注，不能写成正式验收通过。
