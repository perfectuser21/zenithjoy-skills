## 一、这是什么

一个给 AI Agent 用的销售「客户日报」生成 skill。核心能力：输入客户名称 → 抓取该客户资料（当天聊天记录、当日状态、周/月报、客户档案、企业/产品信息）→ 按 A1-A4 阶段框架 + 四感缺口模型 + 推进信号分级 + 询价分级 + 风险识别，输出「两层日报」（单客户日报 + 所有客户汇总日报）。附带一套 Eval 验收方法论（二值断言 + Golden Answer + Baseline 对比）。

包含 1 个 `SKILL.md`（约 384 行）、9 个 references 文件、1 个 `agents/openai.yaml`、1 个 icon。

---

## 二、做得好的地方（先讲优点，避免只挑刺）

1. **领域建模自洽且有「反作弊」设计**。A1-A4 明确「只看已完成动作，不看聊天热度」；弱推进信号不允许强收口；高风险客户（要求保成交/保退款 + 拒绝配合）允许「暂不承接」。这些正是销售场景 LLM 最容易翻车的点，skill 都做了硬约束。
2. **反编造红线写得很到位**（§14 / §16.4）。不仅禁止编造具体价格/案例/合同，连「几千到几万」「数万级」这类模糊量级都判定为编造，还禁止「案例今天下午发您」这类口吻承诺。这是本 skill 最有价值的部分。
3. **Eval 方法论方向正确**。用「通过/不通过/需人工复核」的二值断言替代「打 87 分」的伪科学；强制先写 Golden Answer 再跑；无法起 baseline 时要求诚实标注而非虚构分差；明确区分 6/15/30/50 样本档位，不把 6 样本冒烟包装成正式验收。
4. **输出结构规则清晰**：两层日报、单客户单文件、汇总日报只保留 4 部分并禁止逐客复制下一步动作，可扫读性有保证。

## 三、缺陷清单（共 11 项）

### 严重（会导致错误输出或红线被违反）

**D1｜Golden Answer 标准答案自相矛盾，且违反 skill 自己的核心红线。**
`references/eval-v2-golden-answer-template.md` §六「示例 Golden Answer」中，钱总（调研型询价）第 7 步下一步动作写「**给价格区间**、适用条件」，但同一份 skill 的 `SKILL.md` §11.2 / §14 明令：产品价格信息未提供时「一律写『报价区间待产品信息提供后输出』，不得自行给出任何数字或量级」。该示例第 10 步又补了「若未提供价格只能写待补充」——**同一个标准答案第 7 步和第 10 步互相打架**。后果最严重：Golden Answer 是评测的「标准答案」，评测者会据此把「给价格区间」当成合格动作，等于用一个违反红线的答案去评测，把评测方向带偏。

### 中（影响可用性 / 可执行性）

**D2｜「本月第 N 周」缺少计算定义，周报/月报读取规则无法稳定执行。**
`data-fetch-rules.md` §五和 `SKILL.md` §7 完全依赖「当前处于本月第几周」来决定抓哪些周报，但全包没有任何地方定义「第几周」如何界定（按自然周？按每月 1 号起算？跨月的那一周归属哪个月？）。日报的「周一驱动」有明确定义，周报的「第 N 周」却没有，实际运行必然产生歧义。

**D3｜除 6 样本冒烟外，所有更高档位的 Eval 实际不可执行。**
包里只有 `eval-simulation.md` 的 6 个冒烟样本 + 1 个钱总 Golden Answer 示例。12/15/30/50 档全是纸面 SOP：没有现成样本库、没有成套 Golden Answer、没有任何可运行脚本。要跑「正式上线验收」，评测者得自己现造 30-50 个样本、自己写每个 Golden Answer、自己开两个 baseline 会话。作为交付物，其 Eval 能力实质只停留在冒烟级。

**D4｜`eval-run-result.md` 名不副实。**
`SKILL.md` §2 承诺「查看最近 eval 记录：`references/eval-run-result.md`」，但该文件里没有任何实际运行记录，只有一句「旧版 100 分制作废，以 v2 文件为准」。是个空壳，与 SKILL 的引用承诺不符。

**D5｜两套评分体系并存，易误用。**
`capability-scorecard.md` 的 10 分制满分表以「旧版兼容」名义保留，而 `SKILL.md` §16.5 明令「正式 Eval 不按分值评分」。10 分制与二值断言两套标准同时存在，只靠「仅用户明确要求时用」这句话隔离，增加误用风险和认知负担。

### 轻（一致性 / 可维护性 / 规范）

**D6｜名称与版本号三处不一致。**
`SKILL.md` 的 `name: daily-report-v1-2`、`agents/openai.yaml` 的 `display_name: 日报skill-v1.1-7.6`、zip 包名 `日报skill-v1.2-7.7`——三个版本号/名字互不相同。对外展示名停留在 v1.1-7.6。

**D7｜遗留旧名 `customer-chat-analyzer` 散落多处未清理。**
`data-fetch-rules.md`、`eval-v2-sop.md`（3 处）、`eval-v2-scorecard.md` 共 5 处仍称本 skill 为 `customer-chat-analyzer`，与实际 name `daily-report-v1-2` 不符。说明是从旧 skill 改名而来、清理不彻底，全包同时存在两套名字。

**D8｜大段内容三重复制，违反自身「references 按需加载」原则。**
样本覆盖表（`SKILL.md` §16.3 与 `eval-v2-sop.md` §五）几乎逐字重复；二值断言评测表（`SKILL.md` §16.5、`eval-v2-sop.md` §十、`eval-v2-scorecard.md` §二）三处完全相同。SKILL.md §2 自己要求「按需加载 references，不要一次性加载」，正文却把 references 内容抄回来，导致主文件臃肿（384 行）、且一处修改要同步三处，极易漂移。

**D9｜`description` 写法不利于触发。**
description 是纯功能罗列 + 内部行话（A1-A4、四感、推进信号），缺少「何时用 / 触发词」。而 `openai.yaml` 开了 `allow_implicit_invocation: true`，隐式触发主要靠「客户日报/销售复盘」等词，但 description 没把这些用户口语触发场景讲清楚。

**D10｜跨模板字段集不统一。**
`output-template.md` 的单客户简版（11-13 字段，含「内部跟进记录」、无「次缺口」）、详细版（7 大节，字段名为「内部记录」、含「次缺口」）、Golden Answer 模板（11 点）三套字段名与集合不完全对应，沉淀到下游会对不齐。

**D11｜同一样本（钱总）在不同文件里结论口径未对齐。**
`example-input.md` 期望表里钱总只写「主缺口/风险：确认感/安全感」未给风险等级、跟进优先级写「观察培育或 24 小时内」；`golden-answer-template.md` 示例里钱总风险等级写「谨慎推进」。expected 与 golden 对同一样本的字段口径没有严格统一，会让评测判定产生分歧。

## 四、可用性判定

| 维度 | 评价 |
| --- | --- |
| 领域逻辑正确性 | 好——阶段/信号/风险模型自洽，反编造红线扎实 |
| 输出结构规范 | 好——两层日报、单客户单文件、汇总 4 部分定义清晰 |
| 可直接上手（冒烟级） | 可用——6 样本冒烟能跑通并自检 |
| 正式 Eval 可执行性 | 受限——高档位无样本库、无成套 Golden Answer（D3） |
| 内部一致性 | 偏弱——命名/版本/字段/样本口径多处不齐（D6/D7/D10/D11），且有 1 处标准答案违反红线（D1） |
| 可维护性 | 偏弱——三重复制导致改动易漂移（D8） |

**总判定：部分通过。核心能力可用于「快速冒烟 + 单客户/多客户日报生成」，但作为「可交给团队长期使用 + 支持正式上线验收」的交付物尚不达标。**

## 五、修订优先级建议

1. **必须先修（P0）**：D1——改掉 Golden Answer 钱总示例第 7 步，与 §14 红线对齐（未提供价格不得给区间）。这是评测正确性的地基。
2. **交付前应修（P1）**：D2 补「第 N 周」计算口径；D3 至少补一套 30 样本正式验收样本 + Golden Answer，否则「正式上线验收」名不副实；D4 让 `eval-run-result.md` 要么真记录、要么从 SKILL 引用里删掉。
3. **清理项（P2）**：D6/D7 统一名称与版本号；D8 消除三重复制（references 留一份、SKILL 只引用）；D5/D9/D10/D11 收口一致性。
