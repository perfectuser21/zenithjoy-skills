# 客户日报生成

## 1. 任务定位

根据用户输入的客户名称、客户昵称、客户编号或微信备注名，定位客户数据库资料，并结合企业信息、产品信息，生成中文客户日报。必须使用 A1-A4 阶段框架、四感缺口模型、推进信号判断、询价分级、适配风险和下一步动作设计，输出可用于销售日报、复盘和客户跟进的中文报告。

默认场景：用户不直接粘贴聊天记录，而是输入客户名称。客户当天聊天记录原文、当日状态、本周已生成日报、本月已完成周报、客户加微信以来的月报、客户档案、企业信息、产品信息由可用数据库、文档、连接器或用户提供的上下文中获取。若当前环境无法访问数据库或文档，必须请用户提供相应资料或明确标注“未提供/待补充”，不得编造客户身份、价格、案例、合同、退款、交付周期或产品细节。

原有日报模板保持不变：只在日报正文前新增“本次分析资料范围”模块，用于说明本次哪些资料已纳入分析、哪些资料未提供或待补充。

当日状态是独立数据库资料，指该客户当天在客户信息数据库中的状态记录、阶段标签、跟进状态、今日待办、负责人备注或系统状态字段；它不同于当天聊天记录原文，必须单独读取并单独列入“本次分析资料范围”。

## 2. 引用文件加载规则

按需加载 references 文件，不要一次性全部加载：

- 资料读取范围、日报/周报/月报调用规则、冲突处理：`references/data-fetch-rules.md`。
- 正式日报输出：`references/output-template.md`。
- 快速测试/演示/冒烟回归：`references/eval-simulation.md`，必要时配合 `references/example-input.md`。
- 查看最近 eval 记录：`references/eval-run-result.md`。
- 严格验收、baseline 对比、二值断言评测：优先使用 `references/eval-v2-sop.md`、`references/eval-v2-scorecard.md`、`references/eval-v2-golden-answer-template.md`。
- 旧版满分能力兼容：仅在用户明确要求时使用 `references/capability-scorecard.md`。
- 客户档案使用边界：客户档案视为客户基础信息资料，仅作为分析依据，不在日报中提示新建、更新或升级。

## 3. 默认输出：本次分析资料范围 + 两层日报

正式日报输出前必须先输出“本次分析资料范围”模块，列明当天聊天记录、当日状态、本周日报、本月周报、客户月报、客户档案、企业信息、产品信息是否已纳入分析；未提供的资料写“未提供/待补充”。随后保留原有两层日报：用户给多个客户时，默认必须先逐客户输出单客户当日日报，再输出所有客户当日总结日报。不得只给总结，不得只展开重点客户。

### 3.1 单客户当日日报

每个客户都必须保留以下字段：当前阶段、推进信号、询价类型、阶段判断依据、当日突出点、变更记录、主缺口/最大阻力、适配风险、下一步动作、建议回复、内部跟进记录。

如果客户很多，单客户日报可以简洁，但字段不能省略。用户只给 1 个客户时，只输出单客户当日日报，不需要所有客户总结日报。

### 3.2 所有客户当日总结日报

必须基于前面每个单客户日报汇总，默认只保留 4 部分：

1. 今日总览：客户总数、阶段分布、高优先级客户、可收口客户、高风险/暂不适配客户、主要成交阻力、明日最重要动作。
2. 当日突出点：3-5 条管理者最该关注的机会、风险、变化、卡点和动作，必须来自单客户日报。
3. 明日重点任务：按团队任务主题聚合，不逐客复制下一步动作。默认最多 3-5 项。
4. 团队话术/物料提醒：共性话术问题、明天需要补的物料、今日不要做的动作。

默认不输出“客户跟进清单/压缩管理看板”。只有用户明确要求总表或看板时，才作为附加表放在 4 部分之后。

### 3.3 用户指定输出范围

用户明确要求“只要汇总/只要总表/不要逐客日报”时，可以跳过单客户日报。用户要求“详细版/完整逐客分析/eval/验收”时，使用更详细模板或评分表。

## 4. 文件输出规则

当用户要求输出为 HTML、Word、PDF、Markdown 或其他可下载文件时，默认“单客户单文件”：

- 每个客户的单客户当日日报独立成文件。
- 所有客户当日总结日报单独成文件。
- 可额外生成 `index.html`、目录页或总目录文件，但目录页只做导航。
- 推荐命名：`01_客户名_单客户当日日报.html`、`02_客户名_单客户当日日报.html`、`99_所有客户当日总结日报.html`。
- 只有用户明确要求合并时，才合并；合并文件中也必须清晰分隔每个客户，并保留每个客户的“当日突出点”。

## 5. 输入处理、资料读取与证据规则

1. 首先识别用户输入的客户名称、客户昵称、客户编号或微信备注名；不要默认要求用户粘贴聊天记录原文。
2. 按 `references/data-fetch-rules.md` 读取或纳入该客户的全部必要资料：当天聊天记录、当日状态、本周一至昨日已生成日报、本月当前周之前已完成周报、客户加微信月份至最近已完成月份的月报、客户档案、企业信息、产品信息。
3. 若同一次请求包含多个客户名称，必须逐个客户独立读取资料并独立生成单客户日报；再基于单客户日报生成所有客户当日总结日报。
4. 每个客户独立分析。优先按客户名称、编号、昵称、微信备注名识别；没有名称则用“客户1、客户2……”并说明识别依据。
5. 阶段、推进信号、询价类型、四感缺口、风险和动作都必须有聊天记录、当日状态、日报、周报、月报、客户档案、企业信息或产品信息中的证据。能引用客户原话时优先引用。
6. 不把“愿意聊”“愿意试”“态度积极”直接等同于已购买、已签约或高阶段。
7. 资料之间不设置固定优先级；所有已纳入分析的资料均需结合使用。若资料内容冲突，以最近日期的资料为准；不得使用较早资料覆盖较新资料。若日期相同但内容冲突，标注为“待核实”。
8. 缺失资料必须在“本次分析资料范围”模块中标明“未提供/待补充”，并在相关字段写“未体现/暂无法判断”，不得用模型常识补齐。

## 6. 当天日报分析流程

读取客户当天聊天记录、当日状态和必要背景资料后，按以下顺序判断：

1. 识别推进信号及强弱。
2. 判断 A1-A4 阶段，并写依据和置信度。
3. 判断询价类型：购买型、调研型、模糊询价或未询价。
4. 提炼当日突出点：机会、风险、变化、卡点或关键动作。
5. 判断最大阻力、四感主缺口和次缺口。
6. 判断适配风险。
7. 设计下一步动作、辅助物料和建议回复。
8. 沉淀内部跟进记录。

若已出现明确强推进信号，优先收口，不要继续长篇补四感解释。

## 7. 连续跟进与历史资料使用规则

生成客户日报时，不使用“前 3 日日报”规则。必须按 `references/data-fetch-rules.md` 读取本周、本月和客户存续期内应调用的资料：

- 本周日报：读取本周一至昨日已经生成的日报。今天是周五时，抓取周一、周二、周三、周四日报；今天是周三时，只抓取周一、周二日报；今天是周一时，本周暂无历史日报。
- 本月周报：读取本月当前周之前已经完成的周报。今天是本月第 4 周周二时，抓取本月第 1 周、第 2 周、第 3 周周报；当前周尚未结束，不读取当前周周报。
- 客户月报：从客户加微信所在月份开始，读取至最近已完成月报的月份。客户 4 月份加微信且 6 月月报已完成时，抓取 4 月、5 月、6 月月报。
- 当日状态：读取该客户当天在数据库中的状态记录；未提供时必须标明“未提供/待补充”。
- 客户档案、企业信息、产品信息：均需读取或纳入分析；未提供时必须标明“未提供/待补充”。客户档案仅作为基础信息资料，不在日报中提示更新。

固定公式：

**客户日报 = 客户名称定位 + 本次分析资料范围说明 + 当天聊天记录 + 当日状态 + 本周日报 + 本月周报 + 客户月报 + 客户档案 + 企业信息 + 产品信息 + 当日判断 + 跟进动作。**

资料之间不设置固定优先级。所有资料都需要结合使用；如资料内容冲突，以最近日期的资料为准。若两个资料日期相同但内容冲突，标注为“待核实”。

### 7.1 上一有效客户状态

只提取状态包，不复制历史分析全文。状态包最多保留：上一有效阶段、最近推进状态、询价背景、历史主缺口、历史风险等级、未完成事项、决策链/禁忌话术、上一次下一步动作。

### 7.2 去重与校准

- 阶段默认沿用最近日期有效资料中的判断；只有今天或更近日期资料出现购买、预约、提交资料、签约、付款、启动、明确降级或证据修正时才更新。
- 历史推进信号只作为待核验事项；今天必须判断其已兑现、未兑现、增强、减弱、失效或出现新信号。
- 旧询价不重复分级；只有今天出现新的价格、预算、付款、费用或合同金额表达时，才判断今日询价类型。
- 四感、风险和下一步动作默认结合最近日期有效资料、当天聊天记录与当日状态；今天只记录新增、反复、转移、解除、加重或待核验事项。
- 如果今天无关键变化，写“无关键变化，沿用最近日期有效判断”，并说明是否仍有未完成事项。

### 7.3 变更记录

有历史材料时，单客户日报必须输出“变更记录”。默认 1-3 条，优先记录影响后续跟进的变化。每条包含：变更项、变更前、变更后、变更原因、证据、动作影响。没有历史基线时写“无历史基线/首次记录”。不得把旧日报、周报、月报或客户档案中的旧结论当作今日新增变化。

## 8. 客户档案使用规则

客户档案是客户基础信息资料，按本 Skill 视为相对恒定资料；用于补充客户身份、行业、需求、预算、决策链、偏好、历史风险或禁忌话术等分析背景。

日报不得输出“客户档案更新类字段”，不得提示新建、更新、升级客户档案。若客户档案未提供，必须在“本次分析资料范围”中标明“未提供/待补充”；若客户档案与当日聊天记录、当日状态或历史日报存在冲突，在相关字段标注“待核实”，并优先依据最近日期资料做当日判断。

## 9. A1-A4 阶段定义

| 阶段 | 判断依据 | 目标动作 |
| --- | --- | --- |
| A1 | 了解、初聊、收集信息；未完成最小结果 | 推动低价引流品、预约演示、提交资料、诊断、小交付等 A2 入口动作 |
| A2 | 已购买低价引流品、预约演示、提交资料或同意诊断，正在体验/使用 | 推进中阶产品或单板块方案 |
| A3 | 已购买中阶产品或单板块方案，正在使用 | 推进正价产品、全板块系统项目、合同/协议和付款 |
| A4 | 已签署正价产品合同/协议并完成付款 | 进入组织级落地、复制和持续运营 |

阶段看“客户已经完成什么动作”，不是看聊天热度。证据不足时写“阶段置信度：中/低”，并说明缺少的购买、预约、提交资料、签约或付款证据。

## 10. 四感模型

四感占比表示客户当前心理缺口权重，不是话术字数比例。

| 阶段 | 确认感 | 安全感 | 信任感 | 结果感 |
| --- | ---: | ---: | ---: | ---: |
| A1 | 35% | 30% | 25% | 10% |
| A2 | 25% | 30% | 20% | 25% |
| A3 | 15% | 25% | 20% | 40% |
| A4 | 10% | 30% | 25% | 35% |

含义与调整：

- 确认感：清楚你是谁、能做什么、下一步是什么。客户问流程、身份、适用范围、下一步时提高。
- 安全感：确信风险、成本、边界可控。客户问价格、退款、麻烦程度、最差损失时提高。
- 信任感：相信你真实、能做到、对客户有利。客户问案例、依据、凭什么、能不能做到时提高。
- 结果感：看见收益、变化、指标或验收方式。客户问回本、效果、收益、指标、验收时提高。
- 已经愿意推进时，不再补四感，直接收口。

## 11. 推进信号与询价分级

### 11.1 推进信号

客户出现以下表达时，说明心理条件基本足够，应优先收口：在问价格的同时问付款方式、怎么开始、需要准备什么、什么时候做、多久交付（购买型询价）；说“可以”“先试试”“你发我一下”；主动提供资料、预约时间、确认方案或交付细节。只问价格而无任何后续动作表达，不触发收口，按弱信号和 §11.2 模糊/调研型询价处理。

输出必须包含：是否有推进信号、信号强度、依据、是否应收口。收口必须明确下一步、降低行动成本、确认时间/资料/付款/交付边界，并推动客户完成当前阶段关键动作。

信号强度判档规则（无/弱/强三档，按客户表达归档，不凭语气推断）：

- 无推进信号：没有任何价格、开始、资料、时间相关表达；或只有防御性、对抗性表达。要求保成交、保退款、签对赌，属于风险信号，不是推进信号，不得计入任何强度档。
- 弱推进信号：只问价格或只表达兴趣，但没有任何后续动作表达。例如只问"多少钱""怎么收费"而未提怎么开始、什么时候做。纯价格试探一律判弱，不判无。
- 强推进信号：问怎么开始、付款方式、资料清单、交付周期，主动预约时间、确认方案，或已完成阶段动作（付定金、补资料、定演示时间）。

### 11.2 询价分级

- 购买型询价：问价格，同时问怎么开始、付款方式、资料清单、交付周期、合同范围、预约时间或能否先试。判断为明确推进信号，优先收口。
- 调研型询价：问价格，但说明只是调研、做预算、今年不一定做、暂不开始或收集供应商。只能弱推进，不强收款；给适用条件、判断标准和二次沟通节点。价格区间仅在产品价格信息已提供时给出；未提供时一律写“报价区间待产品信息提供后输出”，不得自行给出任何数字或量级（见 §14）。
- 模糊询价：只问“多少钱”且没有上下文。先补确认感/安全感，再用低阻力问题确认购买意图。
- 未询价：写“未体现”。

## 12. 阻力、风险和复杂场景

### 12.1 阻力映射

不清楚：补确认感；不放心：补安全感；不相信：补信任感；看不到收益：补结果感；已经愿意推进：直接收口。

### 12.2 阶段处理重点与物料

- A1：说明定位和低风险入口，不急成交。物料：企业简介、低价引流品介绍/演示、低风险说明、A1 FAQ。
- A2：让客户使用低价引流品并看到可验收小结果。物料：使用说明、小结果验收/复盘表、中阶产品价值对比、演示、A2 FAQ。
- A3：让客户看到中阶产品持续价值和正价产品更大范围价值。物料：中阶使用说明、正价价值对比、数据/前后对比、正价演示、合同/协议、数据安全说明、A3 FAQ。
- A4：把正价产品变成可控工程。物料：正价使用说明、角色分工、资料/权限清单、复盘迭代表、A4 FAQ。

### 12.3 复杂场景规则

- 多阶段信号混合：阶段仍看已完成动作；未购买/未预约通常仍是 A1，但若在问价的同时问开始、问资料（购买型倾向），要识别推进信号并收口到 A2 入口；只问价格无后续表达仍按弱信号处理，不收口。
- 价格异议强烈：不简单判低意向。优先看安全感，其次结果感；回应费用边界、时间成本、交付范围、退出条件和验收口径，不直接降价。
- 拖延考虑：不强行收款。给轻量动作、最短使用路径或约定复盘时间。
- 多人决策：识别老板、财务、运营、合伙人等角色关注点，下一步设计为内部汇报材料、决策会、合同范围确认或付款节点确认。
- 同行比较：主缺口通常是信任感，其次结果感。不贬低同行、不承诺保结果；给差异对比、交付边界、验收指标和阶段验证方式。
- 高风险/不适配：客户要求保证成交、保证回本、无条件退款，同时拒绝提供资料、拒绝复盘、拒绝边界，或要求超出能力范围时，判断为高风险或暂不适配；先明确合作边界和不承诺事项，不继续强推成交。

## 13. 建议回复话术

话术必须自然、克制、可信，按“回应当前顾虑 → 补主缺口 → 给低阻力下一步”组织。每段只处理一个主顾虑，最多两个；能一句话解决就不写大段解释。

- 无推进信号：聚焦补主缺口。
- 强推进信号：聚焦收口，明确时间、资料、付款、交付边界或预约。
- 调研型/模糊询价：先确认预算用途、启动时间和适用条件，不强推付款。
- 高风险/暂不适配：先明确合作边界、适用/不适用条件和验收口径。
- 禁止：夸大承诺、制造焦虑、攻击同行、承诺保成交/保回本/保效果、跨阶段强推。

## 14. 产品信息缺失处理

用户未提供真实产品名称、价格、交付物、资料清单、合同边界时，用通用层级替代，并标注“待用户补充/未体现”：

- 低价引流品：低风险入口、小范围诊断、体验课、演示、资料提交、一次诊断。
- 中阶产品：中阶产品、单板块方案、阶段性方案。
- 正价产品：正价产品、全板块系统项目、组织级落地项目。
- 辅助物料：优先用用户真实物料；没有时用阶段物料库通用物料。

用户未提供价格时，输出中不得出现任何具体数字或数字量级的价格表述，包括"几千""数万""几千到几万"这类模糊量级——量级也是编造。只能写"报价区间待产品信息提供后输出"，或先引导确认需求与预算用途。

分析质量按阶段、阻力、四感、风险和动作是否准确评价，不因用户尚未提供业务细节而直接扣分。

## 15. 满分自检

输出正式分析前隐性检查以下硬要求；只有用户要求 eval、验收或对比报告时，才显式输出评分表。

1. 多客户是否先逐客日报，再总览汇总；每个客户是否都有当日突出点。
2. 是否保留阶段、推进信号、询价类型、依据、变更记录、主缺口、风险、动作、话术和内部记录。
3. 是否先输出“本次分析资料范围”模块，且包含“当日状态”；资料缺失是否标明“未提供/待补充”；是否未输出“客户档案更新类字段”。
4. 阶段是否只看已完成动作；证据不足是否写明，不强行升级。
5. 推进信号是否写强度、依据和是否收口；询价是否区分购买型、调研型、模糊询价。
6. 四感是否写主缺口、次缺口、阶段默认权重和临时调整原因。
7. 下一步动作是否具备对象、动作、时间或条件、交付边界，避免“继续跟进、加强沟通、发资料”等空话。
8. 是否识别高风险/暂不适配，并避免对拒绝配合又要求保证结果的客户继续强推。
9. 建议回复是否克制可信，不编造价格、案例、合同、退款或效果承诺。
10. 所有客户总结日报是否只保留 4 个默认部分，明日任务是否按团队任务聚合。
11. 文件输出是否遵守“单客户单文件 + 汇总单文件”。
12. 有历史材料时，是否只提取上一有效状态，并输出变更记录；资料冲突时是否以最近日期资料为准。

## 16. Eval 与质量检查

用户要求测试、Eval、验收、回归或对比时，必须先判断用户是否已经明确测试类型。

### 16.1 Eval 前置确认

当用户只说“测试一下”“跑 Eval”“做验收”“做回归”“对比一下”，但没有明确测试类型时，不得直接运行默认样例，必须先询问用户选择本次测试类型：

1. 快速冒烟测试：6 个固定核心样本，只验证核心流程是否跑通。
2. 小型回归测试：最低 12 个样本，推荐 15 个样本，验证修改后是否破坏主要规则。
3. 正式上线验收：最低 30 个样本，推荐 30-50 个样本，判断是否可交给团队使用。
4. 重大规则更新验收：最低 50 个样本，推荐 50+ 个样本，判断复杂场景下是否稳定。
5. 自定义测试：由用户指定样本数量、资料包、评分重点或输出形式。

用户确认测试类型后，再按对应样本数量、覆盖规则、二值断言评测表和硬性失败项执行。若用户已经明确说“跑快速冒烟测试”“跑小型回归测试”“跑正式上线验收”“跑重大规则更新验收”或给出自定义样本集，则不重复询问，直接按对应类型执行。

### 16.2 样本数量规则

不得把 6 个样本作为所有 Eval 的默认测试量。用户选择哪个测试类型，就必须按该测试类型对应的最低样本数和推荐样本数执行。

| 测试类型 | 最低样本数 | 推荐样本数 |
| --- | ---: | ---: |
| 快速冒烟测试 | 6 | 6 |
| 小型回归测试 | 12 | 15 |
| 正式上线验收 | 30 | 30-50 |
| 重大规则更新验收 | 50 | 50+ |

如果当前样本数不足，必须说明：“当前样本不足，不能判定为该测试类型正式通过，只能作为样本不足测试或部分回归测试。”不得把样本不足测试包装成正式通过。

### 16.3 样本覆盖规则

Eval 当前采用整批样本通跑，不要求每个样本单独标注场景标签，但整批样本必须满足对应规模的覆盖要求。不能只规定人数，不规定样本结构。

### 16.4 事实边界与硬性失败项

判断是否编造，不看测试资料是不是真实客户，而看这些信息是否在测试样本里预先提供。

Eval 中允许使用测试样本、测试资料包、数据库资料或用户提供内容中明确给出的模拟事实。测试样本里预先提供的模拟价格、合同范围、退款规则、客户案例、交付周期、付款节点或效果数据，可以作为本次测试事实使用。

如果测试样本没有提供具体价格、合同条款、退款规则、客户案例、交付周期、付款节点、效果数据，模型不得自行补充。模型输出了测试样本、测试资料包、数据库资料或用户提供内容之外的具体价格、客户案例、合同条款、退款规则、交付周期、付款节点或效果承诺，且未标注“未提供/待补充/暂无法判断”的，判定为事实越界编造，Eval 直接不通过。

以下两种情况即使没有写出具体数字，同样判定为事实越界编造：

1. 以既有资料口吻承诺发送测试样本未提供的材料，例如"我们正好有专门的案例/模型/报价单，一并发您""案例今天下午发您"。正确写法是标注"未提供/待核实后补充"，并给出可用已提供内容支撑的替代动作。
2. 输出模糊数字量级充当价格，例如"几千到几万""数万级投入"。量级也是价格信息，未提供即不得输出。


### 16.5 二值断言评测表

正式 Eval 不按 8 分、14 分、87 分、100 分等分值评分。评分项保留，但每项只判定“通过 / 不通过 / 需人工复核”。

| 评测项 | 核心断言 | 判定 | 证据要求 |
| --- | --- | --- | --- |
| 输入拆分与证据使用 | 是否正确识别所有客户，并能把判断对应到客户原话或资料证据？ | 通过 / 不通过 / 需人工复核 | 写明对应客户、原话或资料来源 |
| A1-A4 阶段判断 | 是否给出明确阶段，并且阶段判断与 Golden Answer 一致？ | 通过 / 不通过 / 需人工复核 | 对照 Golden Answer 和客户已完成动作 |
| 推进信号识别 | 是否正确识别无推进、弱推进、强推进，没有把弱信号误判为强推进？ | 通过 / 不通过 / 需人工复核 | 引用客户推进信号原话 |
| 询价分级 | 是否正确区分购买型询价、调研型询价、模糊询价？ | 通过 / 不通过 / 需人工复核 | 对照客户问价原话和 Golden Answer |
| 四感缺口判断 | 是否正确判断客户当前主缺口，并能对应客户真实顾虑？ | 通过 / 不通过 / 需人工复核 | 引用客户顾虑、犹豫、追问内容 |
| 高风险与不适配识别 | 是否识别高风险、不适配、保成交、保退款、拒绝配合等问题？ | 通过 / 不通过 / 需人工复核 | 引用高风险原话或行为 |
| 下一步动作可执行性 | 下一步动作是否具体到对象、动作、条件、资料或边界？ | 通过 / 不通过 / 需人工复核 | 检查是否不是“继续跟进、加强沟通”这类空话 |
| 建议回复话术 | 建议回复是否贴合客户阶段、顾虑和推进状态，可直接发送？ | 通过 / 不通过 / 需人工复核 | 对照客户当前状态和建议回复内容 |
| 连续跟进与变更记录 | 是否正确使用最近资料，并说明客户状态变化？ | 通过 / 不通过 / 需人工复核 | 对照历史资料、当日资料和今日变化 |
| 两层日报与汇总结构 | 是否先有单客户日报，再有所有客户汇总，且汇总来自单客户日报？ | 通过 / 不通过 / 需人工复核 | 检查输出结构和汇总依据 |
| 真实业务适配与不编造 | 是否没有输出测试样本外的价格、合同、退款、案例、交付周期、付款节点或效果承诺？ | 通过 / 不通过 / 需人工复核 | 对照测试样本、资料包、数据库资料或用户提供内容 |

### 16.6 Eval 执行规则

- 快速冒烟测试：使用 `references/eval-simulation.md` 的 6 客户样例，并明确说明这不是正式上线验收。
- 严格客观 Eval / baseline 对比：先用 `references/eval-v2-golden-answer-template.md` 固定 Golden Answer，再按 `references/eval-v2-sop.md` 运行 Baseline 0、Baseline 1 和 Skill Run，最后用 `references/eval-v2-scorecard.md` 进行二值断言评测。
- 无法独立运行 baseline：必须说明“本次仅完成 Skill Run 回归评分，Baseline 0 和 Baseline 1 待独立会话补跑”，不得虚构 baseline、盲评或双人评分。
- 硬性失败项优先：事实越界编造、调研型询价强推付款、多客户无单客户日报、历史覆盖今日、高风险客户仍强推成交时，直接判定 Eval 不通过。
- Eval 报告必须选取 2-3 个典型客户，具体说明 Baseline 0、Baseline 1、Skill Run 的差异，不能只输出结论表。
