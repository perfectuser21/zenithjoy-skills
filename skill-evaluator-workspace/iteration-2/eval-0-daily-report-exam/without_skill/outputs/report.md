# 客户日报 Skill 验收报告（日报skill-v1.2-7.7）

- 被评估对象：`daily-report-v1-2`（zip 名 `日报skill-v1.2-7.7`）
- 包结构：`SKILL.md` + `agents/openai.yaml` + `assets/icon.svg` + 9 个 `references/*.md`，共 12 个文件、约 1694 行 / 100KB
- 评估方式：只读通读全部文件，从「Skill 工程质量 + 可执行性 + 内部一致性 + 可维护性」四个维度审查，不修改任何原文件
- 评估结论：**内容设计扎实，但作为"可交付上线的 Agent Skill"存在 1 个致命缺陷 + 多个中/轻度缺陷，当前状态为"设计稿"而非"可用件"**

---

## 一、总体判断

这个包在**销售方法论内容**层面做得相当好：A1-A4 阶段模型、四感缺口权重表、推进信号三档、询价四分类、硬性失败项、二值断言评测（不打虚假分值）等，规则清晰、边界明确、反编造纪律严格，看得出是有真实销售业务沉淀的人写的。四感权重表四行各自求和均为 100%，无算术错误。

但把它当成一个**要交给 AI Agent 自动执行的 Skill** 来验收，它有一个结构性硬伤：**核心卖点"用户只输入客户名，Skill 自动抓取 8 类资料"根本没有任何可执行的抓取机制**。加上版本/命名不一致、Eval 内容三处重复、交付物名不副实等问题，它现在更像一份**方法论规格说明书**，而不是一个能稳定跑起来、能维护的 Skill。

一句话结论：**方法论 A-，工程可用性 C-。建议退回补齐"数据接入契约 + 一致性 + 去重"后再上线。**

---

## 二、缺陷清单（共 12 项）

### 严重（阻断核心价值，必须修）

**D1. 核心卖点"按客户名自动抓取资料"没有任何可执行的数据获取机制**
- SKILL.md §1 把默认场景定义为：用户只输入客户名，"客户当天聊天记录、当日状态、本周日报、本月周报、客户月报、客户档案、企业信息、产品信息由可用数据库、文档、连接器或用户提供的上下文中获取"。§5、§7、`data-fetch-rules.md` 反复强调"必须读取/纳入"这 8 类资料。
- 但**整包没有任何一处说明"怎么读"**：没有数据库名/表结构/字段、没有连接器（MCP/API）名称、没有查询规范、没有文件命名约定、没有 `allowed-tools` 声明。
- 后果：真实调用时 Agent 必然命中 §1 的兜底分支"当前环境无法访问数据库 → 请用户提供资料或标注未提供/待补充"。也就是说，**这个 Skill 在实践中一定退化为"请把 8 类资料都贴给我"**，而这恰好等于它在 `eval-v2-sop.md` 里要对比、要超越的 Baseline。头号功能事实上不可用。
- 定性：这是"契约写满、机制为零"——规定了必须读什么，却没给任何读的手段。

### 中度（影响可用性/可维护性/可信度）

**D2. 声称支持 HTML/Word/PDF/Markdown 可下载文件，但无生成机制或工具声明**
- SKILL.md §4、`output-template.md`、`example-input.md` 都承诺"单客户单文件"输出为 HTML/Word/PDF 等，甚至给了压缩包命名规范；但没有任何一处说明用什么工具生成 Word/PDF（HTML/MD 尚可直接写文本，Word/PDF 需外部工具），也未在元数据里声明依赖。承诺的能力缺乏落地手段。

**D3. 版本号与命名三处互相矛盾**
- zip 名：`日报skill-v1.2-7.7`
- `SKILL.md` frontmatter `name`：`daily-report-v1-2`
- `agents/openai.yaml` `display_name`：`日报skill-v1.1-7.6`（且 `short_description` 为旧版措辞）
- 三个版本号（v1.2-7.7 / v1-2 / v1.1-7.6）无一对齐。对外展示名停留在上一版，说明打包时未同步刷新。

**D4. 残留旧 Skill 名 `customer-chat-analyzer`，且 Eval 提示词引用了不存在的 Skill**
- `data-fetch-rules.md` 第 3 行、`eval-v2-sop.md`、`eval-v2-scorecard.md` 多处把本 Skill 称作 `customer-chat-analyzer`，与 `SKILL.md` 的 `daily-report-v1-2` 不一致。
- 更实际的问题：`eval-v2-sop.md` 第 185 行 Skill Run 提示词写"请使用 customer-chat-analyzer / 日报 Skill …"。若执行者照此调用，会去找一个**不存在的 skill 名**，导致 Eval 无法按预期触发本 Skill。

**D5. Eval 框架大面积逐字重复，并被完整内联进 SKILL.md，违反渐进披露**
- 测试类型定义、样本数量表、6/15/30/30-50 覆盖分配表、事实边界与硬性失败项、11 项二值断言评测表——这些内容在 `SKILL.md §16`、`eval-v2-sop.md`、`eval-v2-scorecard.md` **三处几乎逐字重复**（11 项断言表全包出现 ≥4 次）。
- SKILL.md §2 明明要求"按需加载 references，不要一次性全部加载"，§16 却把本应只留在 references 的 Eval 全文整段抄进主文件，导致 `SKILL.md` 膨胀到 383 行 / 31KB。这既自相矛盾，又制造了 drift 风险——任何一处改规则都要同步改 3-4 份，极易漏改。

**D6. `description` 是功能罗列，缺少触发场景，不利于（尤其是隐式）调用命中**
- frontmatter `description` 是一长串逗号分隔的功能名（"本次分析资料范围、两层日报、A1-A4 阶段、四感缺口……"），没有写"什么时候该用它"（如"当销售/运营要为客户生成当日跟进日报或做销售复盘时"）。`openai.yaml` 又开了 `allow_implicit_invocation: true`，触发描述写不好会直接影响自动命中准确率。

**D7. 自称支持"严格 Eval / 正式上线验收（30-50 样本）"，但随包交付物远不足以支撑**
- 规则要求正式验收 ≥30 分层样本、重大更新 ≥50 样本，且必须先写 Golden Answer 再跑。但整包只提供了 `eval-simulation.md` 的 **6 个冒烟样本**，以及 `eval-v2-golden-answer-template.md` 里 **1 个填好的 Golden Answer 示例（钱总）**。30/50 样本集与对应 Golden Answer 全部缺失，需用户自建才能跑。"正式验收"能力名不副实——包里给的是模板和方法，不是可直接执行的验收套件。

**D8. Eval 前置人工追问与无头/隐式调用冲突**
- SKILL.md §16.1 与 `eval-v2-sop.md` 要求：用户只说"测试一下"时，"不得直接运行，必须先询问用户选择测试类型"。但 `openai.yaml` 设了 `allow_implicit_invocation: true`，在无人值守/自动化流水线里这个交互式 gate 无人应答，会导致流程卡死。缺少"无法交互时的默认降级策略"。

### 轻度（打磨项）

**D9. "本月第 N 周"周报读取口径未定义**
- `data-fetch-rules.md` 第五节按"本月第 1-5 周"决定抓哪些周报，但全包未定义周编号规则（按自然周？按含 1 号的周？周一起算？），"第 5 周"边界尤其模糊。不同执行者可能抓取不同周报，破坏可复现性。

**D10. §11.2 与 Golden Answer 示例存在表述张力**
- SKILL.md §11.2 对调研型询价规定"价格区间仅在产品价格信息已提供时给出；未提供时一律写'报价区间待…提供后输出'"；而 `eval-v2-golden-answer-template.md` 的钱总示例第 8 条写"给大概区间和适用条件"。虽第 10 条用"若未提供则待补充"做了兜底，但两处并列易让执行者困惑到底该不该给区间。

**D11. `customer-long-term-profile-template.md` 文件名含 template，内容却无任何模板**
- 该文件实为"本 Skill 不再更新客户档案"的说明（标题即"客户档案说明（已调整）"），文件名 `...-profile-template` 是上一版"客户档案模板"的残留，命名与内容不符，易误导按名索引的读者。

**D12. `SKILL.md` 描述与 `openai.yaml` 展示信息不同源、易脱节**
- 同一份能力有两处描述（frontmatter `description` 与 `openai.yaml short_description`），当前已不一致（见 D3）。缺少单一事实来源，后续每次改动都需人工双写，长期必然继续漂移。

## 三、可用性评级

| 维度 | 评级 | 说明 |
| --- | --- | --- |
| 方法论/内容质量 | A- | 阶段、四感、信号、询价、反编造、二值断言设计扎实，业务落地感强 |
| 核心功能可执行性 | D | 头号卖点"按客户名自动抓取"无机制，实际退化为手动贴料 |
| 内部一致性 | C | 版本号、Skill 名、价格区间口径多处不一致 |
| 可维护性 | C- | Eval 内容三处重复 + 内联进 SKILL.md，drift 风险已现实存在 |
| 交付完整度 | C | 缺正式验收样本集与 Golden Answer；文件名残留；展示信息过时 |
| 元数据/触发 | C+ | description 偏罗列缺触发场景；隐式调用与人工 gate 冲突 |

**综合：可作为"内容规格"验收通过，不建议直接作为"可上线 Skill"验收通过。**

## 四、修复优先级建议

1. **P0**：补"数据接入契约"——明确用哪个连接器/DB/文件约定读那 8 类资料，或诚实地把定位改为"用户贴料型 Skill"，让文档与现实一致（解 D1，连带 D2）。
2. **P1**：统一版本号与 Skill 名（zip/`name`/`openai.yaml` 对齐，全局替换 `customer-chat-analyzer`，修 Eval 提示词）（解 D3、D4、D12）。
3. **P1**：Eval 内容单一化——`SKILL.md §16` 只留触发条件与指针，全文收敛到 references 一处（解 D5）。
4. **P2**：补齐正式验收样本集 + Golden Answer，或把描述从"正式上线验收"下调为"提供验收方法与模板"（解 D7）；补无头调用降级策略（解 D8）。
5. **P3**：明确周编号规则、统一价格区间口径、重命名档案说明文件、给 description 加触发场景（解 D6、D9、D10、D11）。
