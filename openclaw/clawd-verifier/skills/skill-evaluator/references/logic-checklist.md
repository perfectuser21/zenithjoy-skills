# 逻辑校验 checklist（7 类，静态审查）

对被测 skill **全部文件**逐类过一遍。每类都附 0707 日报 skill 四轮实战的实证案例——这些不是理论风险，全是真实翻过的车。

## 1. 内部矛盾

新旧条款打架，模型会老实执行旧条款。
**实证**：§11.1"问价格→优先收口"清单 + §11.2"调研型给价格区间"与新加的 §14 价格禁令冲突，deepseek v4-pro 严格执行旧条款编出"几千到几十万"——修掉矛盾后编造清零。
**查法**：对每条"禁止/必须"，全文搜同主题的其他条款，看是否互斥。补丁式修改（只加新条不删旧条）是重灾区。

**样例也是条款（最隐蔽的矛盾）**：skill 内嵌的示例、golden 期望、演示输出如果和正文规则冲突，
杀伤力比条款互斥更大——模型会优先模仿样例而不是遵守规则。所以第 1 类必须包含一个独立动作：
**把每个示例/golden/期望表的行为逐条对照全部禁令扫一遍**。
**实证**：钱总 golden 期望"给价格区间"，与 §11.2/§14"未提供价格不得给量级"三处冲突——
补丁修掉了正文条款矛盾，样例里的旧期望没人动，照跑冒烟就会诱导编造。这类"补丁修文不修例"
的残留在多轮修补过的 skill 里几乎必现。

## 2. 输入无来源

主路径引用的接口/文件/数据在 skill 包和声明环境里都不存在。
**实证**：H3——"按客户名从数据库读资料"是核心前提，但全包没有任何数据接口定义，主流程实际不可执行。
**查法**：功能地图 Step 1 的依赖审计已覆盖，这里复核一遍"每个名词引用都有实体"。

## 3. 字段无填法

输出模板里的字段有名字没定义，不同模型各填各的。
**实证**："主缺口"字段没定义填法，GPT/DeepSeek 三遍都在收口客户上贴四感标签被判错。
**查法**：列出输出模板全部字段，逐个问"一个没看过例子的模型知道这里填什么吗"。没有 → 转向导题让作者定。

## 4. 规则重复

同一规则写在多处且不一致，改一处必漏两处。
**实证**：H1——eval 规则三处重复出处不一致，已有漂移证据；收敛到单一出处后 §16 从 135 行减到 30 行。
**查法**：找重复段落，diff 差异。修复建议永远是"唯一出处 + 其他处引用"。

## 5. 标准模糊

通过/质量标准依赖未定义概念，无法机械执行。
**实证**：H4——通过标准写"核心项大部分正确"，"核心项"和"大部分"都从未定义，二值评测没法跑。
**查法**：对每条验收标准问"两个评分员独立执行会得到同一结果吗"。

## 6. 只有禁令没有替代句式

光说"不许编"不给"资料缺失时该怎么说"，模型（尤其经济档）会"补偿性给东西"。
**实证**：v1.4 加了"资料缺失标准句式库"（可照抄的合规话术）后，gpt-5.5-mini 从 HF 1/3 → 0/3 被救活——这一刀对经济档最有效。
**查法**：每条禁令旁边有没有对应的"替代写法"。没有 → M 级缺陷 + 给出句式库建议。

## 7. 无版本 / CHANGELOG

改动无留痕，多轮修补后没人知道现在是哪版、改过什么。
**实证**：M3——三个补丁无留痕，排查矛盾时无法定位哪条是新哪条是旧（放大了第 1 类问题）。
**查法**：有没有版本号 + CHANGELOG。没有 → M 级，模板一并附上。

## 8. 全文件清扫（收尾必做，专治"抓大放小"）

前 7 类是带着问题找证据；第 8 类反过来：**逐个文件过一遍**，对包里每个文件问四个问题：

1. **是活的吗**——行数极少、只剩"已废止/待补充"说明、9 行空壳但仍被主文档当入口引用的，都是缺陷。
2. **名副其实吗**——文件名叫 template 内容是废止声明、display_name 和包版本对不上、skill 自我指称多套名字并存。
3. **引用一致吗**——主文档说它是什么，它实际是什么；说"字段 11-13 个"，模板里数一数是不是。
4. **每个名词有定义吗**——扫出所有被使用但从未定义的概念（"本月第几周"怎么算、"核心项"是哪几项、档位分界在哪）。

**为什么必须做**：实测发现只跑前 7 类会"抓大放小"——评估员把注意力全给了结构性 H 级问题，
M/L 级文档缺陷被下意识合并或略过，召回率掉到裸评审之下。清扫是机械动作，逐文件走完就不会漏。

## 单列纪律：求全不求并

**每个独立缺陷单独编号单独列出，禁止合并同类项。**"三处命名不一致"和"版本号 stale"是两条缺陷不是一条；
五个文件各有一个空壳问题就是五条。理由：报告的消费者是 skill 作者，他按清单逐条修——合并过的条目
会让他漏修；召回率是这份报告的生命线，简洁靠分组呈现（按严重度/按文件），不靠删条目。

## 严重度判定

- **H（高）**：会导致某条功能线输出错误或不可执行（矛盾、来源缺失、标准无法执行）。
- **M（中）**：会降低跨模型稳定性或可维护性（字段无填法、重复、缺替代句式、无版本）。
- **L（低）**：文档卫生问题（退化的模板文件、命名不一致）。

只有影响输出正确性的才配 H——文档洁癖不算。每条缺陷输出：编号 + 严重度 + 一句话描述 + 原文位置 + 一句话修复建议。
