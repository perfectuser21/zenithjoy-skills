# report_data 结构化输出模式（Form B 机器可读）

Form A（人看的 markdown 报告）走 `report-template.md`。
**Form B（网页服务）需要一份结构化 JSON**，喂给渲染器画「输入 → skill 内部逻辑 → 输出」的 n8n 式连线图。
当被要求「机器可读 / --json / Form B / report_data」时，**只输出一个 JSON 对象**（首字符 `{`、末字符 `}`，无解释文字、无 markdown、无代码围栏）。

## 为什么是这个结构

渲染器要把 skill 画成一张**执行流程连线图**：客户给一个输入 → skill 顺着一条 pipeline 一步步跑（有的步是去读数据、有的步是判断、有的步是硬闸）→ 产出几份输出。所以核心是 `anatomy.pipeline`——**skill 真实的执行序列**。把它排准，图才画得对。

## Schema

```json
{
  "skill": {"name":"字符串","version":"","source":"","type":"判断型/发布型/生成型/调研型/管道型 之一 + 一句定位","area":"ZenithJoy","line":"对应 Line","ability":"","submitter":"","evaluatedAt":"YYYY-MM-DD"},
  "verdict": {"level":"pass|partial|fail","text":"一句话裁决理由"},
  "stats": {"功能线":"N","依赖缺失":"N","红线":"✓ 或 ✗","成熟度":"thin|medium|thick","诚实度":"A+|A|B|C","耗时":"实测分钟"},
  "anatomy": {
    "input": "调用方给的输入，极短≤5字（如 客户名称）。就是发起 skill 时人给的那一个东西，不是 skill 自己去读的数据",
    "loadMode": "全部前置 | 穿插判定",
    "kernelName": "内核干嘛的≤12字（如 判客户阶段和风险）",
    "pipeline": ["按真实执行顺序排的字符串数组，见下方【pipeline 规则】"],
    "outputs": [{"name":"极短标签≤5字","kind":"文档|文本|数据库|数据|文件|修改动作","role":"这输出是啥，≤14字大白话"}]
  },
  "summary": "一句大白话≤35字：这 skill 现在什么状态、能不能上生产（像跟同事说话，别用术语）",
  "nextSteps": [{"issue":"发现了什么问题，大白话≤30字","fix":"员工该怎么改，大白话≤30字","severity":"high|mid|low"}],
  "health": [{"dim":"是什么","state":"ok|warn|bad|neutral"},{"dim":"输入","state":""},{"dim":"逻辑","state":""},{"dim":"输出","state":""},{"dim":"红线","state":""},{"dim":"成熟","state":""}]
}
```

## pipeline 规则（最关键）

`pipeline` 是**字符串数组**，10–16 个，按 skill **真实执行顺序**排。每个字符串是下面三种之一，**竖线 `|` 分字段，不写任何说明/箭头/注释**：

| 类型 | 格式 | 说明 |
|---|---|---|
| 读取 | `load\|数据名≤5字\|来源方式\|具体来源名≤7字\|已接或未接` | skill 去拿一份数据那一步 |
| 判定 | `judge\|判定动作≤10字` | skill 做一次判断那一步 |
| 硬闸 | `gate\|硬闸≤10字\|拦截或转人工或标注` | 命中就短路的硬规则 |

**【来源方式】只能填这 4 个之一**（按「数据从哪来、怎么拿」判，不要纠结数据库 vs 文档的存储细节）：

- `库` = 结构化数据库，要**查接口**才能拿（客户信息库、订单表）
- `文档` = 现成的**文字文件**，要**读文件**（产品手册、客户档案文档）
- `API` = **外部服务实时调**（订单查询接口、库存接口）
- `上下文` = **对话或输入当场就有**（用户输入、当前会话）

**【具体来源名】** 写真实来源名，如 `客户信息系统` / `产品手册` / `订单接口` / `用户输入`——让人一眼知道这数据要从哪个系统拿。

**【loadMode 判定】**——这决定图长什么样，务必判准：

- `全部前置` = skill 拿到输入后**先把所有 load 做完，再全是 judge/gate**（pipeline 开头一串 load，后面才判定）
- `穿插判定` = **边判边读**，load 夹在 judge 中间（后面读什么可能依赖前面判的结果）

pipeline 示例（全部前置）：

```json
["load|当日状态|库|客户信息系统|未接","load|客户档案|文档|客户档案库|未接","judge|判A1-A4阶段","judge|判推进信号","gate|事实越界编造|拦截","gate|高风险转人工|转人工"]
```

pipeline 示例（穿插判定）：

```json
["load|当前会话|库|会话状态库|已接","judge|判客户意图","load|客户档案|文档|客户档案文档|已接","judge|判所处阶段","load|历史订单|API|订单接口|未接","gate|高风险转人工|转人工","judge|生成回复话术"]
```

## 字段硬约束

- **所有 `name` / 标签务必极短（≤5 字）**，长了图上会截断出省略号，很难看。
- `nextSteps` **最多 3 条**，不同、不重复、不凑数；每条两句都 ≤30 字大白话。
- `summary` 一句话 ≤35 字。
- **字符串值内部禁止用英文双引号 `"`**，要强调用中文引号 `「」`，否则 JSON 会解析坏。
- 读取步里 skill 声称要读但没真实接通的（引用了不存在的接口/文件）→ 该 load 标 `未接`；真接通的标 `已接`。
- 只输出 JSON，第一个字符是 `{`，最后是 `}`。

## 生成前自检（避免 JSON 坏）

1. pipeline 每个字符串字段数对不对（load 5 段、judge 2 段、gate 3 段）？
2. 来源方式是不是只用了 库/文档/API/上下文？
3. 有没有 name 超过 5 字？有就压缩。
4. 字符串里有没有混入英文双引号？有就换成「」。
5. loadMode 和 pipeline 的排列一致吗（全部前置 → load 都在前面）？
