## 0. 名词一锤定音

**我们的 Golden Path ≠ 业界的 Golden Path。**

- 业界（Spotify 2020，平台工程）：给**工程师**铺的"有主见且有支持的"建软件推荐路线。
- 我们家：**客户为一个完整价值结果而走的承诺序列**——一种触发进来，3-5 步客户可感知的
  承诺，走到一个客户愿意付钱的终点。借词不借义，内核是 Story Mapping backbone（Patton）+
  Walking Skeleton（Cockburn）的自家组装。

相关概念各就各位（它们是一条路的不同侧面，不是路的别名）：

| 词 | 在体系里的位置 | 词性 |
|---|---|---|
| Golden Path / 路 | 路本身（层级名词） | 名词 |
| Walking Skeleton / 贯穿 | 这条路第一次 thin 端到端跑通的动作/阶段 | 动作 |
| Happy Path / 晴天剧本 | 这条路不出错时的剧本子集；验收必须超越它，smoke 守卫只巡它 | 剧本范围 |
| 加厚 | 通车后覆盖更多场景格的持续动作 | 动作 |

**Happy path 与 smoke 的分工**：验收测试（修路时）跑全场景八格，全绿才通车；
smoke 守卫（通车后）每天只走晴天剧本，快而浅，回答"今天还通吗"。一条路配**分段** smoke
（各阶段独立坏，红灯要能指到断点）。两个绿不是一回事。

## 1. 层级词汇表

```
Line（业务线/领域）＝ 智能客服、智能获客……＝ 一门生意
 └─ 路（Golden Path）×3~7条 ＝ 一种触发 → 一个客户愿意付钱的完整结果
     └─ 骨干 3~5 步 ＝ 每步一句客户/老板可感知的承诺
         └─ 挂片 / 分支 / 判定点 / 场景格 ＝ 工序细节全部住这层
```

一个领域切出 3-7 条属正常；超 7 条考虑拆领域；只有 1-2 条回头查漏了什么触发器。

**旧词对齐（Ability/Feature 轴 → GP 坐标，2026-07-24 拍板）**：旧词 "Ability" 跨了两个
粒度，是历史混乱的根源——大 Ability（可交付、上合同，"我们支持智能获客了"）= **一条
Golden Path**；小 ability（"看懂图片"，客户问"那然后呢"）= **挂片**。Feature/基础框架 =
挂片。Line 是生意，**不是** Ability。GP 词汇表取代旧轴，不做一一映射。

**FR/NFR 归属**：FR = 步骤承诺 + 分支；步骤级 NFR（并发/断网/恢复）= 该步场景格断言；
路级 NFR（端到端成功率/SLO）= 路的终点断言；系统级 NFR = 横切件。

**凌驾于 steps 之上的东西只有三样**（其余一切都住 steps 里）：
1. **路级断言**：整条路终点的端到端承诺（"日 4 条、成功率 ≥90%"），塞不进单步
2. **Gate 前置门**：授权文书/技术可行性，在 Step 1 之前，任一不过整条路停
3. **横切件**：服务多条路（"塌了多条路变红"），住横切件池，不住任何一条路

## 1.5 Line（业务线）判定

**Line = 一门生意 = 一类感知者 + 一个价值主题。** 回答"我们做哪门生意"，不回答"事情怎么走"。

| 判据 | 过 = Line | 不过 |
|---|---|---|
| 有自己的感知者群体 | 智能客服=商家老板；工厂=主理人 | 感知者与别的 line 完全重合 → 同一 line |
| 能独立成交付合同/独立考核 | "智能客服"可单独卖 | "看懂图片"不能 → 不是 line |
| 装得下 3~7 条路 | 智能客服切出 GP-A~F | 只装 1 条 → 它本身是别人家的一条路 |
| 没有单一触发器和终点 | Line 是一组路的家 | 说得出"X发生→拿到Y" → 是路不是 line |

关键区分：**能画出起点和终点的东西不是 line，是路。**

## 1.6 判定链（任何东西丢进来，从上往下问）

```
它是一门生意吗（有自己感知者+能独立卖）？ ──是→ Line（触发器计数法切出它的路）
 └─否→ 一种触发→一个付钱终点（三问法过）？ ──是→ Path（归进某条 line）
     └─否→ 塌了会让多条路变红吗？ ──是→ 横切件
         └─否→ 是造路/修路的工具吗？ ──是→ 工厂件（归工厂域）
             └─否→ 挂片/加厚/工作包（归到某条路的某一步）
```

**先装地图铁律（2026-07-24 实战教训）**：跑判定链之前必须先装载已拍板的 line→GP 地图
（Brain `journeys` 表：line 前缀命名如「智能客服 · GP-B」「工厂 · F4」）+ 现有
`golden_paths`。一切判定结论必须落成**格子坐标（line · 路 · 动作类型）**，禁止在真空里
判"是不是路"——已在图上的路绝不重新发明（教训现场：14 条清洗曾漏装地图，把 F5 指挥舱、
F3 夜间体检重新发明成"新路"）。同时核验锚点健康：journey_id 为空/挂 deprecated/悬空
外键的条目一律标失锚待修。

## 2. 三问法（判断"是不是一条独立的路"）

1. 客户会为它**单独付钱** / 它会出现在交付清单上吗？
2. 拿掉它，旅程还走得通吗？
3. 它有自己的**起点**和**客户可感知的终点**吗？

三问全过 → 独立的路；任一不过 → 不是路（是共享前置、挂片、或某条路的一步）。

## 3. 两把尺子（定边界、定分合）

**尺子① "客户为什么而来" → 定路的边界。**
判据一句话：能不能对客户说「我们现在支持 X 了」且客户因此点头？
- "我们支持智能获客了" → 点头 ✅ → 路级
- "我们支持采集抖音视频了" → "那然后呢？" ❌ → 只是路上的一段

**尺子② "走完拿到的结果是不是同一个" → 定加厚 vs 分路。**
- 同一个结果、只是输入/覆盖面不同 → **加厚**，同一条路（文字/图片/语音都是"顾客得到回复"）
- 结果本身不同 → 不同路，或同一条路的不同阶段

## 4. 三个反模式（90% 误判栽在这）

1. **"难" ≠ "路"**：读懂语音再难，客户也不为它单独买单。难度量工作量，不量路的边界。
2. **"平行的能力" ≠ "平行的路"**：看懂文字/图片/语音平行对等，但走完同一个结果 → 加厚不分路。
3. **"步骤/阶段" ≠ "路"**：采集→判定→触达→写 Lead 是一条路的四段，不是四条路。

## 5. 承诺式骨干（骨干步骤的硬规则）

- 每条路 **3-5 步**；步骤名必须能翻译成一句「客户/老板感知到什么」（承诺）。
- **工序词黑名单**：识别 / 判定 / 检测 / 解析 / 校验 / 生成 / 调用 等系统动词禁止直接当
  步骤名——出现即降级为挂片或分支，不得作为骨干步骤本身。
- 每步显式分两栏：**【挂片】**（现状：已落地/半成/缺失/规划）、**【分支/判定点】**
  （多路径分叉、系统需推断外部真实状态的接缝，注明误判后果）。

骨干步骤表模板：

| 步骤（承诺） | 【挂片】 | 【分支/判定点】 |
|------|---------|-----------------|
| 客户发出好友申请后立刻收到欢迎语 | 欢迎语模板(已落地)／触达渠道(半成) | 判定：新客户 vs 老客户回流（误判后果：老客户被当新客户重走欢迎流程） |

## 6. 验收断言（承诺必须可验收）

- 每步承诺配**可执行验证**的断言锚点（psql / UIA 读回 / 截图 / API 查询），禁"功能正常"类空话。
- 断言写在**路的步骤上**，不写在需求本身上。
- 接缝步骤（碰真机/生产 env/真实第三方）验证等级必须 **L3 真机真验**；纯前端交互可 L1 替身；
  真 DB 写入 L2 服务端真验。降级需证据。
- 「得体/像人/有分寸」类软承诺：eval 集 + LLM judge + 人工抽样，表上显式标**「软」**，
  不许用主观描述冒充硬断言。

## 7. 场景牌组（承诺 × 场景矩阵，防"只想了晴天"）

每个骨干步骤过固定八格：**首次使用 / 日常运行 / 重启恢复 / 断网弱网 / 并发洪峰 /
对抗输入 / 平台改版 / 凭据过期**。

每格二选一：一条具体断言，或 `N/A + 理由`。**空格 = 红灯**——没人想过这步在这个场景下
会怎样，等于埋了未知故障模式。

## 8. 归位判定链（新东西该挂哪，Mode 2 用）

按序过五关，禁跳步：

1. **频率判据**：它发生的频率 = 目标路的触发频率吗？一次性的事禁进高频路的骨干
   （注册一生一次，不能当"被动接待"的 S1）。
2. **三问法**：全过 → 它自己是条路，转切分流程。
3. **承诺翻译测试**：能翻译成客户感知 → 候选骨干步/场景格；翻出来是工序词 → 降级挂片。
4. **四问归家**：新路 / 共享前置（一次性进场链归「首次成功路径」Onboarding，业务路用依赖
   标签引用，禁复制进各路开头）/ 横切件（必须答出"塌了哪些承诺会变红"，答不出=不该做）/
   工厂件（不挂业务域的图，归工厂域自己的家，决策 2d28de45）。
5. **归位裁决单**：`家X · 路Y · 步Z · 格W ＋ 动作类型（七动作之一）＋ 验收断言锚点`。
   拿不准的列「待拍板问题清单」，不硬填。

## 9. 七动作总表（动路的合法动作类型）

| 动作 | 定义 | 关键规则 |
|------|------|----------|
| 贯穿 | 新路骨干 thin 端到端走通 | 先通后厚（= Walking Skeleton） |
| 加厚 | 挂片从半成/缺失点绿到已落地 | 四种材料：能力/体验/NFR/守卫 |
| 修复 | 挂片从绿掉回红，补回去 | hotfix + 复现断言永久进棋盘，禁事后删 |
| 动骨干 | 改骨干步骤本身 | 唯一豁免=客户看到全新的站；主理人拍板；季度级稀有 |
| 退役 | 下线一条路或一个挂片 | 先减肥再增肌，不与新增混一次提交 |
| 探索 spike | 写不出承诺的试错调研 | timebox；产出=结论喂回切分；禁伪装成贯穿 |
| 置换 | 承诺零变化的底层大手术 | 验收=引用断言 绿→短暂红→绿 + 迁移 SOP |

挂片三规则：**首用即出生**（保持 thin，断言写在步骤上）、**复用即引用**（语义查重，禁重建）、
**瓶颈才加厚**（多条路同时被卡才立加厚 sprint）。

## 10. 铁律与例外

- **拍板前绝不写库**——地图/裁决单是给主理人审的草案，不是既成事实。
- **止血例外**：生产事故可先斩后奏，但 24h 内补归位裁决单，钉红灯状态进账本。
- **账本写入必须是流水线自动副作用**——设计里出现"记得手动更新账本"= 该设计判死刑。
- **一句话内核**：路按"客户来买的那个完整结果"切；比结果细的（阶段/能力/模态/步骤）一律
  往里装。难不难、大不大、平不平行，都不改变它是路里的一块。
