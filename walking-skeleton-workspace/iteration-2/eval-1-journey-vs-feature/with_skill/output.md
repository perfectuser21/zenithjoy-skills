# 判断：这是一个 Feature，不是新 Journey

挂到现有的"独立咨询师管理客户合同"主 Journey 上，作为某一步的具体能力，不要新建 walking skeleton。

## 判断依据（来自 walking-skeleton skill 的边界规则）

走一遍核心决策树："用户走完 X 涉及的所有动作后，能不能拿到一个完整可感知的价值？"

- AI 自动生成合同条款本身**不构成完整价值闭环**——用户拿到一段 AI 生成的条款文本，不等于"管好了一份客户合同"。它必须嵌在"创建合同 → 填条款 → 发给客户 → 客户签 → 归档"这条已有路径里才有意义。
- **同一个角色（独立咨询师）、同一个价值闭环（管好合同）**。skill 明确：同角色、同闭环里的"某一步的另一种实现方式（如 AI 替代人工）"是 Feature，不是 Journey。
- 反例对照（concepts.md 案例）："AI 自动生成内容"在 ZenithJoy 里就是 Path 第 5 步的 Feature，不是新 Journey。你这个场景结构完全一样。
- 入口/出口没变——还是从合同列表进，签完归档出，没有产生独立的新入口。

判定 Journey 的三条标准（角色不同 / 闭环不同 / 入口出口完全不同），你这件事**一条都不满足**，所以 Feature。

## 下一步动作

1. **确认主 Journey 是否存在**：调 `status <你的 Area>` 看现有 Journey 列表。如果"咨询师合同管理首次成功路径"这条 Journey 还没建，先 `init journey` 把骨架定义出来（5-8 步：登录 → 新建合同 → 填条款 → 发送 → 签署 → 归档）。
2. **找到挂载点**：AI 生成条款挂在"填条款"那一步，作为该步的一个 Feature 实现。
3. **强制按 thin 起步**（铁律 #2）：第一版**不要**做 prompt 工程 / 模板库 / 多场景适配 / 风格控制。合格 thin 长这样：
   - 一个按钮"AI 生成"
   - 硬编码 prompt 拼用户输入的客户名 + 服务类型
   - 调一次 Claude API 返回一段文本，塞进编辑框
   - 丑 UI、零错误处理、只支持 1 种合同类型
   - 一条 smoke test 证明端到端能跑
4. **加厚靠真实反馈**（铁律 #5）：等真有咨询师用这个功能、提具体痛点（"生成的条款不够本地化" / "缺少违约金条款"），再按 thin → medium → thick 升级。不要一上来就做"完整版"。
5. 用 `add feature` 命令把它登记到 Notion，thickness=thin，挂到主 Journey 的对应 Step。

**核心提醒**：不要因为"AI 生成"听起来很大就误判成 Journey。一件事多技术含量 ≠ 它是端到端价值闭环。Journey 看的是用户视角的完整故事，不是工程视角的复杂度。
