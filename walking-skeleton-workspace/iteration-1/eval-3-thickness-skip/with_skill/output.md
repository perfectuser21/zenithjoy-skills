# 不能跳级 — 必须先升 medium，再考虑 thick

直接回答：**不行，不能从 thin 直接跳到 thick**。这是 walking skeleton 方法论里的硬纪律之一，不是建议，是规则。

## 为什么不能跳级

Thickness 4 阶段（thin → medium → thick → mature）的设计本意，就是**让每一次加厚都有真实反馈作为驱动力**，而不是工程师拍脑袋决定"现在该升级了"。每一级都有独立的升级标准，必须**全部满足**才能进下一级：

| 阶段 | 升级标准（必须全部满足） |
|---|---|
| `thin` | 端到端能跑（哪怕全是 mock/硬编码），smoke 通过 |
| `medium` | 真实数据替代 mock，有基本错误处理（不崩溃） |
| `thick` | 核心场景完整，UI 可面客户，常见错误已处理 |
| `mature` | 边界情况覆盖、监控告警、性能优化、回滚预案 |

跳级的危害很具体：你以为自己已经"production-ready"，但实际上**中间阶段该暴露的问题从来没暴露过**。10 个客户在用没出 bug，不代表你的错误处理完整、不代表常见错误已处理 —— 很可能只是这 10 个客户没踩到坑而已。直接升 thick 等于把"medium 层该解决的错误处理"和"thick 层该解决的核心场景完整 + 面客户 UI"两件事压到一次升级里做，这正是 walking skeleton 反对的"跳级幻觉"。

## 你现在的真实情况

"10 个客户在用、没出过 bug" 是一个**信号**，但它指向的是 **thin → medium 的升级时机已成熟**，不是 thin → thick。具体看：

- 你已经有真实用户了 → 说明可以替换 mock、接入真实数据 ✅
- 没出过 bug → 不代表错误处理完整，只代表用户没触发；medium 要求**主动**加上基本错误处理（输入校验、网络失败兜底、表单提交报错提示等）✅ 待补
- UI 是否面客户级、常见错误是否都覆盖、是否有空状态/加载态/失败重试 → 这些是 thick 的标准，**目前没有证据**

## 推荐路径

第一步：**先升 medium**。需要做两件事：

1. **真实数据替代 mock** —— 把表单里所有硬编码、占位符、临时配置换成真实 DB / API 数据流
2. **基本错误处理** —— 至少保证：输入非法不崩溃、提交失败有提示、网络异常能恢复

升级时调 `thicken` 动作，必填升级理由（写进 Notion 作为证据）：

```bash
node ~/.claude/skills/walking-skeleton/scripts/thicken.js \
  --feature-id "<画像表单 feature id>" \
  --to "medium" \
  --reason "10 个真实客户使用 1 周无 P0；已接入真实 DB 数据替代 mock；表单错误处理已覆盖输入校验+提交失败提示"
```

第二步：**等 medium 跑一段时间，收集真实反馈**。哪些场景常被触发？哪些错误用户实际遇到过？UI 哪里客户抱怨？**这些反馈才是你升 thick 的真正依据**，而不是"反正没 bug 那就升吧"。

记住铁律 5：**加厚要靠真实反馈，不靠时间表也不靠工程师直觉**。
