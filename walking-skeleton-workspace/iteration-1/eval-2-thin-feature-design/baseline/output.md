# 第 3 步「画像诊断」第一版怎么做

## 一句话原则

第一版只做一件事：**让用户填一份最少字段的画像表单，提交后系统真的把它写进数据库，并展示一个最简单的"诊断结果"页面给用户看**。链路打通比内容好坏重要 100 倍。

## 做什么（Do）

1. **一个表单页**，5–8 个字段就够：
   - 行业 / 角色（单选下拉）
   - 公司规模或个人/团队（单选）
   - 当前最大痛点（单选 + 一个 textarea 备用）
   - 想达成的目标（单选 + textarea）
   - 邮箱（已登录就预填）
2. **一次提交**：POST 到 `/api/profile/diagnosis`，写到 `user_profiles` 表，字段 1:1 对应表单。
3. **一页诊断结果**：根据用户选的"角色 × 痛点"在前端硬编码 3–5 条规则，匹配出一段 100–200 字的"诊断 + 推荐下一步"。**这一版不接 LLM**。
4. **一条状态流转**：在 user 表加一列 `onboarding_step`，提交后从 `step_2` 推进到 `step_3_done`，第 4 步才解锁。
5. **一条 smoke test**：curl 模拟整条链路（登录 → POST 表单 → GET 诊断页 → 确认 DB 落库 → 确认 onboarding_step 推进），跑在 CI 上。

## 不做什么（Don't）

- **不做 LLM 智能诊断**。第一版用规则引擎，能跑通端到端就行。LLM 是第二版的加厚动作。
- **不做多步骤分页表单 / 进度条 / 动画**。一页搞定，连 form validation 都只做必填校验。
- **不做画像编辑/历史版本/重新诊断**。第一版只支持"填一次"，后续要改？刷新重填，覆盖写。
- **不做 A/B 测试、埋点分析后台**。先埋一个 `profile_submitted` 事件就够，看板下个迭代再说。
- **不做精美的诊断结果设计**。卡片 + 一段文字 + 一个"下一步"按钮，纯文本就行。
- **不在这一步收集太多字段**（生日、地址、行业细分、团队成员名单……）。每多一个字段，转化率掉一截，且第一版用不上。
- **不做"跳过"按钮**。这一步是必经路径，跳过就破坏了 walking skeleton 第 4 步的输入假设。

## 验收标准（DoD）

- 真用户走完表单 → 看到诊断结果 → DB 里有完整记录 → onboarding 推进到第 4 步入口。
- smoke test 在 CI 上绿。
- 端到端 < 30 秒完成。

## 一句话总结

**先把"用户能填、能提交、能看到结果、状态能推进"这条线打通，不要在任何一个环节追求"做得好"。** 这是 thin feature，不是 MVP；MVP 是这条 journey 跑完三五次迭代之后的事。
