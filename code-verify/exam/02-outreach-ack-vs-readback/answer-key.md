# 考题 02 必抓清单（阅卷用，**不得给考生看**）

考察点：**「自报」与「读回」的分界**，以及「缺失」（代码里根本没有对应检查）。素材来自 09-28 补审的真实缺口，重点是把「写入接口自己回的成功码」「界面上读到真实内容」「什么都没检查」三种情况分清。

## 标准答案

| id | 正确类型 | code_ref | 不通过时 | 说明 |
|---|---|---|---|---|
| X1 | **自报** | push-raw-comments.js:58 | 仅日志 | `res.code === 0` 是**写入接口自己回的成功码**，属于"对方自己说成功"，没有回查记录是否真的存在。失败分支只 `console.log("FAIL"…)`，继续下一条。 |
| X2 | **缺失** | null | 不适用 | batch2.sh:104 用落池 ssh 的**进程出口码**决定 completed/failed，回答的是"脚本有没有跑完"，不是"是否有线索落池"。`$NL` 为 0 时同样记 completed（105 行）。判据"0 条线索不得 completed"在代码里没有任何检查。 |
| X3 | **缺失** | null | 不适用 | next-outreach.js:107-111 的 PUT **返回值被丢弃**（`await fetch(...)` 没接、没看、没有回读）。写入本身不是检查。写成功与否完全没有被判断，比"自报"更弱。 |
| X4 | **自报** | next-outreach.js:59 | 仅日志 | 只看写入接口的 `res.code === 0`，失败时只打印 `MARK_FAIL`，没有重试、没有回读、没有告警。 |
| X5 | **读回** | douyin-phone-adb:1525-1526 | 停 | 抓当前手机界面的控件树，读输入框 `msg_et` 的 `text`，与话术逐字比较，不一致 `die`。数据源是手机界面（现实状态）。 |
| X6 | **读回** | douyin-phone-adb:1537-1538 | 停 | 发送后**重新抓一次**控件树，在里面找刚发出的气泡文字，读不到 `die`。 |

`summary` 必须是 `{"读回": 2, "自报": 2, "常量": 0, "缺失": 3}`。`verdict=fail`（X1～X4、X7 都是 must 且不是读回）。

## 必抓（全部满足才算通过）

1. X1、X4 判「自报」（不得判读回，也不得判常量）。
2. X2、X3、X7 判「缺失」，`code_ref` 为 null；X3 不得判「自报」。
3. X5、X6 判「读回」，且 `stops_on_fail` 为「停」；不得被误报成缺陷。
4. `verdict=fail`；summary 计数与明细一致；一致性规则全满足（缺失 ⇒ `code_ref: null`，反之亦然）。

## 常见误判

| 误判 | 为什么错 |
|---|---|
| X1 判「读回」，理由是"`res.code` 是飞书接口返回的，来自现实世界" | 那是**写入这一下自己的回执**。读回是写完之后另外去查（GET 记录、按批次计数）。"我写了，对方说 OK"不算读回 |
| X3 判「自报」 | 自报至少还看了返回；这里 PUT 的返回被丢弃，什么都没检查。拿不准归到更弱的一类，所以是缺失 |
| X2 判「自报」，理由是"用了出口码" | 出口码回答的是另一个问题（脚本是否跑完）。判据问的是"有没有线索"，代码里没有任何东西回答它 |
| X5 判「自报」，理由是"读的是界面，不是真实结果" | 手机界面控件树就是这一步的现实状态，读它就是读回。判据要求的正是"输入框里的文字" |
| X4 判「缺失」 | 代码里有对写入回执的判断（`res.code === 0`），只是停在自报，没有回读；缺失是指完全没有 |
