# 考题 01 必抓清单（阅卷用，**不得给考生看**）

背景：zenithjoy-workspace PR#1937（2026-09-22）把 09-16 的 skill 判据转成账本代码。skill 要求预检核对账号、拿锁留证据，归位回读锁与前台；转成代码后这些判定全部变成写死的常量，验收只检查字段齐不齐，一直没人发现（补审 63 条判据：读回 28 / 自报 9 / 常量 7 / 缺失 19）。

## 标准答案

| id | 正确类型 | 关键行 | 说明 |
|---|---|---|---|
| J1 | 常量 | 84 | `device_verified:1` 是写死的字面量。**变量名叫 verified 不算证据**，写的时候没有任何东西去读设备 |
| J2 | 常量 | 84 | `call_state_idle:1` 写死。值恰好为真也是常量 |
| J3 | 常量 | 84 | `account_verified:0` 写死为 0。值为 0 也是常量（它不是"检查没通过"，而是"根本没查"） |
| J4 | 常量 | 84 | `lock_acquired:0` 写死；83 行只有 serial 与 hostkey，没有 owner 证据 |
| J5 | 常量 | 104 | `close_app_attempts:0` 写死 |
| J6 | 常量 | 104 | `lock_released:1` 写死为 1，没有回读锁状态。**这条最危险**：它看起来像"放锁成功"，实际什么都没查 |
| J7 | 常量 | 104 | `safe_desktop_visible:0` 写死 |
| J8 | 常量 | 85 | `candidates_judged:0` 写死，且阶段状态是 `blocked not_in_profile`，不与任何输入数比较 |
| J9 | 读回 | 105、108、116 | **这是对照题，不是缺陷**：`ls` 读工件目录数文件、`led show` 读账本项数，`n_items>0 && n_files>=n_items` 才判成功，不通过 `WFR_FINALIZE_OK=0`。数据来自文件系统与账本，追得到源头；不通过时会改变输出。注释里"判据用产物"的说法不是证据，但代码本身确实读了。 |

## 必抓（全部满足才算通过）

1. J1～J8 共 8 条，每条 `type` 必须是「常量」，`code_ref` 必须落在上表对应行（±1 行可接受）。
2. J9 必须判「读回」，`stops_on_fail` 判「停」（不通过时输出 `WFR_FINALIZE_OK=0`）。判成缺陷即误报，本次考试不通过。
3. 8 条常量对应的 `must` 判据使 `verdict=fail`；输出符合 SKILL.md 的一致性规则（summary 计数对得上，缺失/常量的 must 判据不得让 verdict=pass）。

## 加分项（不计入通过线，用于比较不同核验员）

`not_in_criteria` 应至少指出其中一项：
- 第 112～115 行的注释声称"判据用产物"，容易让人以为 cleanup 全面核对过；实际它只核对了工件文件数，没有核对锁或前台（考生不采信注释的证明）。
- 第 85、86 行 qualification、scoring 一开跑就以 `blocked not_in_profile` 写工件，会让这两个阶段在开跑时点就有了"已写"的记录。

## 常见误判

| 误判 | 为什么错 |
|---|---|
| 把 J1、J2、J6 判成读回，理由是"值为 1，看起来成功" | 判类型看数据来源，不看值；值恰好为真也是常量 |
| 把 J3 判成"缺失" | 代码里存在 `account_verified` 字段，是常量 0；缺失指代码里没有任何对应物。两者的整改方向不同（补检查 vs 加检查） |
| 把 J9 判成常量或自报 | 它读了文件系统与账本，是真的读回 |
| 判据 J4 判成读回，理由是"有 serial 和 hostkey 证据" | 那是登记信息，不是锁的 owner 证据 |
