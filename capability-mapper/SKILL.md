# /capability-mapper — 领域切分师

**判层标准唯一来源**：`tree/references/doctrine.md`（六层定义、三问法、两把尺子、Activity
流程边界两条件 / 问题二定 Activity、反模式、场景牌组、归位判定链、七动作、设计模式、铁律）；扫刀步骤在
`tree/references/step-cutting.md`。开工前先读这两份，本文件只写 mapper 的流程，不重复标准。

## 模式总览

- **Mode 1：切新领域**——主理人说一个新领域，产出该领域的六层地图。触发：/capability-mapper、
  帮我定义X领域的能力(Capability)、这个领域切几个能力、领域切分。
- **Mode 2：归位**——树已存在，判定主理人抛来的一个新东西该挂到哪一层哪个位置，不切新领域。
  触发：归位、这个加到哪、放哪个capability、XX算什么、帮我看看XX属于哪。

## GP 合同与格子账本的唯一引用纪律

> 机器名说明：`golden_paths` / `journey_step_links` 是能力提案管线的历史机器名，按 doctrine §2
> 保留不改；对人一律说「能力提案」。

地图拍板落账以及归位落账都必须遵守：

1. `golden_paths.journey_id` 必须指向该能力所属的价值流 / 能力行，不允许留下空锚点；
2. GP 级 7 项签字合同只通过
   `golden_path_id → golden_paths.journey_id → journey_step_links` 引用格子账本；
3. 7 项合同是每个能力提案的签字面；封版的 11 要素、场景与断言仍只落在
   `journey_step_links` 的既有结构中；
4. **禁止复制合同正文**到价值流 / 能力 / Activity 格，禁止把 11 要素复制进合同，禁止新建平行账本；
5. 禁止为合同层修改 `journey_step_links` 表结构。缺锚点时先补正确关联，不能绕过锚点闸。

mapper 只负责确定引用和归属，不起草、签署或修改 7 项合同正文；合同正文由
capability-proposer 起草、reviewer 攻击、Owner 按版本签字。

## Mode 1：切新领域

### 输入

```
DOMAIN        — 领域名（例：私域获客、微信客服、内容发布）
主理人补充口径（可选）— 已知的边界偏好、已知资产提示
```

### Step 1：探索现状

先按 `Skill(tree)` 的 **Step 0** 装载六层全树（生产只读 psql 查 value_streams / capabilities /
workflows / workflow_activity_refs / activities / steps，不可达走 `/api/brain/value-streams`、
`/api/brain/workflows`），筛出该领域已有的价值流 / 能力 / 流程 / Activity；再读相关代码目录，
逐项标 已有 / 半成 / 缺失，附证据（文件+行号或运行证据），禁凭记忆猜测。
`/api/brain/journeys`、`/api/brain/golden-paths` 不作地图源。

### Step 2：切分提案（四件产物）

#### ① 能力清单（触发器计数法）

**一种「什么事发生了系统要动」且三问法全过 = 一个能力**（doctrine §5）。每个能力给一行：

```
〔触发器〕→〔终点（客户/老板可感知）〕  挂在：部门 · 价值流
```

能力 = 客户买的结果：找法不同（关键词 / 对标）、平台不同（抖音 / 小红书）默认都是同一个能力，平台用带前缀的
流程区分；只有单独售卖、单独交付的平台才单列能力（doctrine §5）。
能力下按两条件列流程（doctrine §6）：默认同一流程，接缝「① 能放下 且 ② 有分开跑的理由（节奏 / 资源 /
一对多·多对一 / 等人）」才断开；一个执行者顺序跑多个流程，仍是多个流程。

#### ② 边界声明

与相邻价值流 / 能力的交界 Activity 归属**逐条定死**，不留模糊地带。

例：加好友归「获客」的终点；客服从「已是好友」这一状态起步，不重复覆盖加好友过程。

#### ③ 横切件池

多个能力共用的底座单列出来，标注：在哪个流程的哪个 Activity「首用出生」、被哪些其他能力引用、
塌了哪些承诺会变红。多个流程共用的 Activity 不进横切件池——它是**共用 Activity**，在树上加引用即可。

#### ④ 共享前置

进场门槛类动作（绑定账号、安装客户端等）标注「非独立能力」——归「客户首次成功路径」能力，
业务流程用依赖标签引用，不复制进各流程开头（doctrine §15-4）。

### Step 3：每个流程的 Activity

每个能力按 `step-cutting.md` 扫刀：段 × 两条件（流程边界）、流程内段 × 问题二（Activity / Step），产出
流程边界表 + 问题二表 + Activity 表，并给每个流程写触发、时长预算、交接表。每个 Activity 列：承诺、读回锚点、执行体、怎么启动、Step 概要、
【分支与判定点】、现状（已落地 / 半成 / 缺失 / 规划）。看护作业（监工 / 巡检 / 日报）单列，不进流程。

### Step 4：对抗切法

派 **3 个 fresh subagent** 复用 `Skill(capability-reviewer)`（LENS=product/tech/risk），
审查对象是**切法本身**，不是某个能力的提案细节：

- **触发器完备性**：漏了哪种起点事件？
- **边界归属正确性**：交界 Activity 归属是否站得住？
- **层级纯度**：断开的接缝两条件都满足吗（能放下 + 有分开跑的理由）、放不下的有没有被拆开、两条件都满足的
  有没有没断开？有没有把找法或平台画成能力、把 Step 或口号抬成 Activity、把看护作业挂进流程、把定时作业桶
  当流程（doctrine §6/§7/§12）？
- **共用识别**：同一段工作有没有在多个流程里各画一份、该共用没共用？共用的合同（输入来源、输出去向）一致吗，
  不一致的有没有按 doctrine §19 判兼容 / 不兼容 / 分叉并附影响表？
- **横切识别遗漏**：有没有被漏识别成横切件、实际却重复在多个能力里独立实现的东西？

P0/P1 打回修订；**真找不出实质漏洞时必须 APPROVED（禁凑数打回）**，同 capability-reviewer
收敛纪律。

### Step 5：收敛输出

产出领域地图 markdown（含待拍板问题清单）呈主理人：

```markdown
# <DOMAIN> 领域六层地图

## 能力清单（触发器计数法；每个能力挂在 部门 · 价值流）
## 边界声明
## 横切件池
## 共享前置
## 每个能力的流程与 Activity 表（含流程边界表 / 问题二表、每个流程的触发与交接表；共用 Activity 标注）
## 看护作业清单（不进流程，注明归属）
## 对抗结论（三镜头 verdict 摘要）
## 待拍板问题清单
```

**拍板后**（且仅拍板后）：调用 `Skill(db-update)` 规范写 Brain 六层真表（能力提案管线仍写
`golden_paths`）；写入时同时校验本文件的唯一引用纪律，并提示主理人可逐个点火 `capability-controller`
深化成正式提案。

**拍板前绝不写库**——地图是给主理人审的草案，不是既成事实。

## Mode 2：归位模式

> 场景：树已存在，主理人抛来一个新东西（一句话需求、一个已完成的功能、一个模糊的想法），
> 要判定它该挂到哪一层哪个位置——不是切一个新领域（那是 Mode 1 的事）。

### Step 1：读现状

同 Mode 1 Step 1 装载六层全树。库和接口都不可达 → **禁凭记忆猜测**，改为要求主理人给出领域名，
读该领域对应的地图文档 / PRD 作为替代现状源。

### Step 2：判定链（按序跑，禁跳步）

按 doctrine §15 五关：① 频率判据 → ② 三问法 → ③ 问题二 + 流程两条件 → ④ 四问归家（新能力 / 共享前置 /
横切件 / 工厂件，工厂件见下方「工厂域裁决」）→ ⑤ 归位裁决单：

```
部门 · 价值流 · 能力 · 流程 · Activity（· Step）· 场景格 ＋ 动作类型（七动作之一，doctrine §16）＋ 验收断言锚点
```

三问法全过 → 它本身是一个新能力，**转 Mode 1**。拿不准的不要硬填，列进「待拍板问题清单」。

### Step 3：呈报，拍板后落账

归位裁决单**不写库**——先呈主理人确认。确认后，按 `Skill(db-update)` 规范把裁决结果落进对应账本。

## 工厂域裁决（mapper 独有，2026-07-17 主理人拍板，决策 2d28de45）

**工厂件不挂业务价值流，但工厂自己是一条价值流**——同一套六层、同一套闸，感知者=主理人。

- 三问法对工厂照常适用：「主理人一句话 → 合格 PR → 部署 → 结果可查」是合格的可感知承诺。
- **结构性理由**：锚点闸要求任务带锚，而多数 dev 任务就是工厂活——工厂不上树 → 工厂任务永无合法锚 →
  只能全豁免 → 闸虚设。
- **禁「内部工程排期」平行系统**——工厂与业务共用一张账本（平行排期=平行表病）。
- 两条护栏：
  1. **产能配比政策线**：业务:工厂的开发配比是主理人拍板的政策旋钮，planner 按配比取格子，防工厂自嗨；
  2. **粒度地板**：工厂微件（单个 hook 小修等）不单独成 Activity——按七动作走 Step 级修复，不动树。

## 禁止事项

1. 禁拍板前写六层真表 / golden_paths
2. 禁在本 skill 里另写判层标准——一律引用 doctrine.md，发现冲突以 doctrine 为准并回报
3. 禁跳过 Step 1 探索直接切分——现状标注必须有代码 / Brain 数据证据
4. 禁三镜头对抗为凑轮次而打回无实质漏洞的切法
5. 禁越权写某个能力的提案文档细节——那是 capability-proposer 批准后的工作
