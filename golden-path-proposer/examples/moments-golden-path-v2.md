# Line04 朋友圈制作 Golden Path v2

提案人：Cecelia（AI）。v1 经三镜头对抗（技术 REJECTED / 产品 NEEDS_REVISION / 风险 NEEDS_REVISION，合计 27 findings，去重后 P0×9），本版逐条回应全部 P0/P1，P2 记账不阻塞。

## 0. v2 相对 v1 的结构性变化

1. **两道 Gate 前置**：写任何功能代码之前，先过 Gate 0（技术可行性探索）和 Gate 1（授权文书），任何一道不过整条 GP 停止或改道。
2. **现状标注全部重核**：v1 标"已有"的定时器（死代码，`startScheduler()` 零调用点 + SCHEDULER_TENANT_ID 未配）、草稿落库（NOT NULL 约束致静默失败）、"消费侧已在"（deprecated 文件，活路径是空 stub）全部改标**缺失/需修复**，工期按此重估。
3. **审核主体反转**：审核人从"运营在中台点批准"改为"**客户本人在微信里轻确认**"（详见 J1）。
4. **新增硬规则层**：红线词库闸（生成后、入审核队列前，fail-closed）。
5. **验收断言从 3 条扩到 7 条**，新增内容版本锁定、账号绑定、时间散布、互动度量。

## Gate 0 · 技术可行性探索（开工第一个任务，0.5-1 天）

**问题**：PC 微信 4.1.8 能否发朋友圈？（历史上 PC 端朋友圈长期只读；v1 完全未验证。）在 xian-rog 真机上探索：
- 4.1.8 UI 是否存在发圈入口；存在则 dump 朋友圈（SNS）窗口 UIA 树，验证离屏静默可达性；
- 探索结论三选一决定路线：**A** = UIA 后台静默（与客服回复同套铁律）；**B** = UIA 不可达但入口存在 → 桌面租约窗口内前台发（Desktop Arbiter，借用桌面后归还）；**C** = PC 无发圈入口 → 转手机端 RPA，成本结构变化，回到主理人重新拍板 scope。
- 预授权规则：结论为 A 或 B 直接按该路线继续；结论为 C 暂停并升级给主理人。

**回应**：技术#5（Gate 0 缺失）、J2 旧表述废弃。

## Gate 1 · 授权文书（没有它不碰任何真实客户号）

- 客户授权协议模板必须含：①自动化操作可能导致账号限制/封禁的显式风险告知与责任划分；②"AI 可以以你的口吻公开发布经你确认的内容"的代发权边界；③数据处理方清单（含 LLM 与中转商）。
- 首发客户强制灰度期：前 14 天隔天 1 条、随机时段；监测发布失败率/好友可见性抽检，异常自动熔断暂停全线。
- **回应**：风险#1（封号+授权+灰度+熔断）。

## Golden Path 六步（v2 修订版）

**① 触发（现状：缺失，需修复死代码）**
scheduler 接线启动 + SCHEDULER_TENANT_ID 进部署 env；cron 改北京时间；**生成时段按客户行业画像取默认值**（如餐饮=晚市前、教培=晚间），不是全体 09:00。DoD 含"生产进程真实 fire 一次 tick 且 generated>0"。
→ 回应 技术#1、#12；产品#6。

**② AI 生成 + 红线硬闸（现状：半成，落库需修）**
- 画像升级为**人设卡**：行业/人群/钩子 + 题材轮换表（按周内日轮换）+ 禁区 + 客户口头禅样例；画像缺失客户跳过并通知运营补齐（不 fallback 默认模板，见 J4 备选）。
- LLM 输出 → **红线词库硬闸**（绝对化用语 + 行业禁词，命中即拒，fail-closed，不打标放行）→ 才落库 pending_review。AI 生成失败写独立状态 `ai_failed`，永不进入可批准队列。
- 落库修复：migration 放开/统一 wechat_publish_task 老列 NOT NULL；INSERT 失败向上抛；写入 tenant_id 全链透传；当日去重加租户维度；新增 visible_group 列与 content_hash 列。
- 送入 LLM 的画像做字段白名单（剥离手机号/姓名/好友信息）；聊天记录与好友数据**永不**进入文案输入（放开须主理人重新拍板）。
→ 回应 技术#2、#8、#9；产品#4；风险#2、#3、#11。

**③ 审核：客户微信内轻确认（现状：缺失；主体反转）**
- 草稿经中台**预审**（运营抽查红线闸结果与人设符合度，可改稿——改稿留痕：原文/终稿/编辑人三元组）后，推送到**客户本人微信**（复用 Line04 已跑通的 IPC 主动发送）："今天准备发这条朋友圈：…… 回 1 发布 / 回 2 不发 / 直接回文字=改成你说的"。
- **确认消息协议（显式受限，防误匹配）**：推送消息带草稿短码（如 #P37）；仅在推送后 30 分钟确认窗口内、且回复以 `1`/`2` 单字或 `#P37 改：<文字>` 开头才被识别为审核动作；窗口内其他消息一律不动作（正常走客服会话），窗口结束草稿仍 pending 时晚间重推一次。改稿必须带短码前缀，改后重过红线闸并重新推送确认。新增断言 **A8**：确认窗口内发送任意无关消息，草稿状态与 content_hash 不得变化（回归用例含客户回"1"回应其他话题的场景）。
- **推送失败路径（不与"客户未回复"混同）**：IPC 推送失败（Line04 链路故障时常见）草稿标独立状态 `push_failed` 并触发运营告警（Bark），不静默滑向过期；台账区分 push_failed / expired / rejected 三类占比。
- 客户回复即批准/驳回/改稿。**批准动作固化 content_hash，批准后草稿只读。**
- 草稿有效期：当日 22:00 未确认自动过期作废，不顺延。
- 中台 Dashboard 保留一个**台账页**（非批准入口）：全客户草稿状态、过期率、驳回率，运营看盘用。
- 首版禁用任何批量批准。
→ 回应 产品#1、#5、#7；风险#5（版本锁定）、#8（审核主体/批量）；技术断言 A1 语义修正。

**④ 派发（现状：缺失——v1"消费侧已在"失实）**
批准 → enqueue `wechat_moments_send`（任务体含 tenant_id / account_id / content_hash / visible_group）。实现落在 **line04 模块包内**（modules/line04-wechat-cs 补 taskType 路由到 send_moment.py + 失败回执），不用 deprecated 的 core handler；模块未激活时任务失败留痕，不静默丢。
→ 回应 技术#3。

**⑤ 真机发布（现状：死路重写，路线由 Gate 0 定）**
- 发布前三重校验，任一不符 **fail-closed 拒发**：a) 当前登录微信号 == 任务 account_id；b) 文案 hash == 批准时 content_hash；c) 可见分组选择成功（失败拒发，绝不回落公开）。
- 频控修复：key 改 **wechat_id**（不是 visible_group）；占额改两段式（发成功后 confirm，失败不占额）；间隔为 24h±随机余量，非精确 24h；同机多号强制错峰；发布时刻在客户时段内 ±30min 随机抖动。
- send_moment.py 重写：REAL_PUBLISH=1 且依赖缺失必须 ok:false 硬失败（禁 MagicMock 静默降级）；修 stdin 合同与调用方一致。
- 发布后 UIA 读客户朋友圈首条做"已发检测"；回执缺失时先做已发检测再决定，重试一律**人工确认后**执行，防重复发布。
- 客户级 **kill switch**：pause 开关生效于派发前最后闸门，暂停时 in-flight 任务撤回；发错事故 SOP（删除时限 + 通知客户 + 事故记录）。
→ 回应 技术#4、#6；风险#4、#5、#6、#7。

**⑥ 回执 + 度量（现状：缺失）**
- sent_at + 真机截图回写；**回执不作为发布证据，A2 以截图+读回为准**。
- RPA 顺手采集该条互动快照（点赞/评论数）进日报；由此进线的私聊在 CRM 打来源标（哪怕 v1 先只采集不处理）。
- 评论回复/私聊承接显式声明为 **vNext GP「朋友圈互动承接」**（账本里已有 planned ability"客户朋友圈互动"，挂它名下），本 GP 不做但数据模型预留。
→ 回应 产品#2、#3。

## 验收断言 v2（Final E2E，冻结后 AI 不可改）

- **A1** 状态机以 `approval_status` 列为 SSOT（补 CHECK 约束：approved 必须 approved_by 非空且 approval_source≠'system'），完整走 pending_review→approved→sending→auto_sent；断言约束本身存在（psql 查 constraint）。
- **A2** 真机朋友圈出现该内容，**以截图 + UIA 读回为证据，回执字段不作为证据**；可见分组与批准版一致。
- **A3** 未批准/过期/ai_failed 草稿在发送队列恒为 0；同 wechat_id 24h 内第 2 条（**跨 visible_group**）被频控拒且留痕。
- **A4** 命中红线词库的草稿永不进入 pending_review，拦截留痕；词库空时闸 fail-closed 报错而非放行。
- **A5** content_hash 不符或登录号 ≠ account_id 时拒发路径触发且留痕（含"审后改稿发旧版"回归用例）。
- **A6** 同租户多号发布时刻散布：任意两号发布间隔 ≥ 10min，单号时刻含随机抖动（查 sent_at 分布）。
- **A7** 日报含每条已发朋友圈的互动快照字段（可为 0，但字段必须存在且被写入）。

## 判定点登记表 v2（需主理人拍板，批准即写 decisions 冻结）

- **J1 审核主体**：REC=客户本人微信内轻确认（回 1/2/改稿），中台只预审+台账。备选：运营代审（须协议明确代发权+人设卡为审核依据）。
- **J2 授权与准入**：REC=按 Gate 1 协议模板执行，且医疗/金融/教培行业客户首版**不接**。备选：接但红线词库按行业加严（法务成本自担）。
- **J3 路线预授权**：REC=Gate 0 结论 A/B 直接继续、C（PC 无发圈入口）暂停回来重拍。备选：C 时直接立项手机 RPA。
- **J4 画像缺失处置**：REC=跳过并通知运营补齐。备选：用行业默认模板硬发（人设失真风险自担）。
- **J5 红线词库归属**：REC=中台维护基础库+行业模板，运营可加客户级词条。备选：外采合规词库服务。
- **J6 成败线**：REC=上线 30 天复盘，客户驳回率 >40% 或互动率持续为 0 → 触发内容策略重做而非继续铺量。备选：主理人另定阈值。
- **J7 人机分工规则（参与递减）**：REC=AI 全自动跑，机器对抗管对错；主理人只在三种触发下参与——①新型判定点（无先例的分叉；有先例的 AI 引用 decisions 表自动选+事后报备）②不可逆动作首次放行（碰真实客户号/对外发布/花钱/签文书；同类放行过一次后走机器闸不再问）③异常铃响（GAN N 轮不收敛=隐藏判定点升级、熔断触发、成败线击穿）。日报常驻抽样若干条已放行事项供抽检（防三镜头共享盲区）。备选：每单人工终审（安全但不可规模化）。本条不只适用本 GP，批准后作为"AI 自提 Golden Path"模式的通用分工规则写入 decisions。
