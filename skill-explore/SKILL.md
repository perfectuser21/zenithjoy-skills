# 探路 skill-explore

目标只有一个：**把这件事真的做成，并把"怎么做成的"完整留下来**，交给下一步沉淀（skill-distill）。
做成 ≠ 你说做成了——是否成功由下一步独立核验（run-verify）判定，你只负责交证据。

## 第 1 步：读执行参数

任务正文最上面的【执行参数】块，逐项取值；缺失按默认：

| 字段 | 缺失时 |
|---|---|
| 设备 | 不碰手机的活可缺；要碰手机却没写 → 停下，报 blocked，不要自己挑手机 |
| 验收 | 用正文里描述的目标，自己写一句"成功长什么样"，并在交付物里标注「验收为自拟」 |
| 超时 | 30 分钟 |

## 第 2 步：先加载平台知识包，再动手

按顺序读，读到的就直接用，**不要从零摸索已有答案**：

1. 底座：`android-publish`（设备通道、设备锁、输入法、拟人纪律、定位三层）
2. 该平台已有的所有 skill（发布类、获客类都读，找能复用的步骤与已知的坑）
3. 手机控制器现成命令：`<controller> --profile <profile> --help` 与平台专用命令（如抖音的 open-search / open-comments）
4. 已知按钮锚点（控件文字 / content-desc），有锚点表就先查表
5. 新平台建设标准：`android-leadgen-buildout-standard` 的「预防清单」

## 第 3 步：预检与占用

- `preflight`：通话状态必须空闲，serial / 型号与执行参数一致，否则停止。
- **账号核对（动手前）**：打开目标 App 的「我」页截图，确认当前登录账号与执行参数一致；执行参数没写账号就把看到的账号记进交付物。不一致 → 在做任何对外动作之前停止，报 blocked。
- `lock-acquire <run_id>`：拿不到锁返回 blocked，**不抢占**。
- 结束时（成功或失败）必须 `lock-release <run_id>` 并回读 `lock-status` 为 free。释放失败或回读不是 free → 重试一次；仍失败则 `result=blocked`、`lock_released=false`，`fail_reason` 写明锁状态原文（锁有 30 分钟 TTL 兜底，但必须上报）。

## 第 4 步：执行——定位三层，别跳级

找"要点哪里"时按顺序：

1. **控件树优先**：`ui-evidence` / `uiautomator dump`，按 text / content-desc 精确匹配取中心点。不调任何模型。
2. **候选多个分不清** → 把候选列表（text / bounds / 面积）交 **Jev** 做选择题，只从已知候选里选。
3. **控件树里没有文字**（自绘界面、微信 dump 返回空树）→ 截图交 **UI-TARS** 直接给坐标。
4. 以上都不行 → 你自己看图判断，并在"发现的坑"里记一条，供以后固化。

坐标每次现场取，**禁止复用上一屏或历史坐标**。

**对外动作只点一次**：点赞、发送、发布、私信这类按钮，本次运行里**点过一次就不再点**。定位没把握时先截图确认再点；点完无论看起来成没成功，都先截图核对结果，绝不因为「好像没反应」再点第二次（再点一次可能等于取消或重复发送）。

拟人纪律照底座执行：步骤间随机 2–6 秒、点击坐标 ±5px 抖动、不秒点、启动 App 后先停 3–5 秒。

## 第 5 步：留证据（下一步沉淀全靠它）

- **每一次页面状态变化**都截图；关键页面同时保存控件树 XML。
- 证据 ID 格式：`<run_id>-<两位步号>-<一句英文短名>`，例 `likeprobe-03-wechat-home`。**禁止复用文件名覆盖旧证据**。
- 走错路、重试也要留证据并标注「绕路」——沉淀时要知道哪些该删。

## 第 6 步：什么时候必须停

| 情况 | 动作 |
|---|---|
| 来电、登录/验证码/人脸/风控挑战、账号与执行参数不符 | 立即停止，释放锁，报 blocked |
| **对外动作**（点赞、发送、发布、私信）失败或结果不确定 | **不重试**，截图后停止，报 failed |
| 同一步连续 3 次没到预期页面 | 停止，报 failed，写清卡在哪 |
| 快到超时 | 提前收尾：释放锁，交已有证据 |

判定成功一律看**产物**（页面上真的出现了什么），不看命令返回码。

以下情况的判定口径（避免临场发明规则）：
- 「预期页面」= 动手**之前**写进该步 `trajectory.expect` 的那一句目标状态（前台包名 / 页面标题 / 关键控件文字，至少一项）；没先写 expect 就动手的步骤一律记为未到达。
- 「连续 3 次没到」按同一个 expect 计数，中间绕路不清零。
- 证据 ID 重名 → 在 ID 末尾加 `-b`、`-c`，不覆盖。
- **每次对外动作之前**再核对一次当前账号（截图里的昵称 / 头像），与第 3 步记下的一致才动手；不一致立即停止。
- 对外动作后截图里看不出明确变化 → 记为「结果不确定」，按上表停止，不得记为成功。

## 第 7 步：交付物（最后只输出这一个 JSON）

```json
{
  "stage": "explore",
  "run_id": "本次运行 ID（与锁、证据 ID 一致）",
  "claimed_result": "success | failed | blocked",
  "goal": "一句话目标",
  "acceptance": "验收标准原文（自拟的标注「自拟」）",
  "device": {"profile": "...", "serial": "...", "host": "..."},
  "trajectory": [
    {"step": 1, "from": "起始页面", "expect": "动手前写下的目标状态", "action": "做了什么（写控件文字，不写坐标）", "to": "实际到达页面", "evidence": "证据ID", "detour": false}
  ],
  "final_evidence": ["证明结果的证据ID"],
  "side_effects": [{"action": "实际对外做了什么（例：给 某某 的动态点赞）", "evidence": "证据ID", "reversible": false}],
  "findings": ["这次发现的坑，一条一句，写清现象和怎么绕过的"],
  "lock_released": true,
  "fail_reason": null
}
```

`trajectory` 只记**页面状态变化**，不记每一次点击；绕路的步骤 `detour: true`。

- `claimed_result` 只是你的**声明**，下一步 run-verify 不采信它，只看证据重新判定。
- `side_effects` 必须列出**所有已经发生的对外动作**，失败的运行也要列（包括误触）；没有就写空数组。
- 验收是自拟的，`acceptance` 以「自拟：」开头；run-verify 会按更严的口径处理。
