# Golden Path 粒度判定

## 这个 skill 解决什么

反复出现的纠结：一堆功能/能力摆在面前——"看懂文字、看懂图片、读懂语音"或"采集、判定、触达、写 Lead"——**它们到底是一条 golden path 还是好几条？** 每个都又大又难，大到看着像独立的路,于是团队反复争论、拆错粒度、验收时对不齐。

本 skill 给两把**可复用的尺子**，把这堆东西判定成清晰的层级：哪些合成一条 path，哪些是路上的阶段/能力/加厚。目的是让"路"和"路上的东西"不再混为一谈——**这是团队对齐、拆 sprint、建守卫（smoke）的地基**。

判完之后的自然下一步通常是：给这条 path 配守卫（一条 path 可以有多个分段 smoke）、或走 `/plan` 判层级、或 `/dev` 路径C 开 sprint。

## 第零把尺子："Journey 还是 Ability"——五个测试（2026-08-06 拍板）

两把尺子管"一条路里怎么装"；**这把尺子管更上面一层：手里这东西到底是 journey（域/容器）还是 ability（一句承诺）**。五个测试按序过，两三个就能定：

| # | 测试 | 问法 | 判定 |
|---|---|---|---|
| ① | **主角测试** | 换主角/换核心需求了吗？ | 换了→journey；同主角同需求的不同招式→ability |
| ② | **出口测试** | 走完拿到"需求完成"还是"承诺兑现"？ | 需求终态（能独立当一条线汇报）→journey；一句承诺→ability |
| ③ | **孤儿测试** | 单独拎出去，答得出"挂哪条 journey"吗？ | 答不出（自成一体）→journey；答得出→ability（铁律1镜像） |
| ④ | **数数测试** | 底下还能列出几句"我们支持 X 了"？ | 能列多句→journey；只剩步骤和使能件→ability |
| ⑤ | **晨报测试** | 日报里想让它占一行还是一盏灯？ | 一行（线的生死）→journey；一盏灯→ability |

**漂移的两种症状**（发现分错了的信号）：
- **Ability 冒充 Journey**：描述只有一句承诺、数数测试列不出第二句——工厂 F0~F7 曾建档成 8 个 journey 即此症（实为工厂 journey 下 8 条 GP）。
- **Journey 冒充 Ability**：一条"ability"描述里出现多个主角或多个出口（如"客户端+管理端"混一条——harness 多角色检测拦的就是它）。

## 核心：两把尺子

判定 golden path 粒度，**只用这两把尺子**，按顺序量。

### 尺子① "客户为什么而来" → 定 path 的边界

一条 golden path 的边界 = **客户为了拿到什么完整结果而来**。

客户为之付钱、会主动说"我要 X"的那个**完整价值结果**，就是一条 path。比它更细的东西（单个能力、单个步骤、单个模态），客户不会单独为它买单——那些是路上的零件，不是路。

判据问一句：**"能不能对客户说『我们现在支持 [X] 了』，而且客户会因此点头？"**
- "我们支持智能获客了" → 客户点头 ✅ → **path 级**
- "我们支持采集抖音视频了" → 客户："那然后呢？"❌ → 只是 path 里的**一段**
- "我们支持看懂图片了" → 客户："看懂了要干嘛？"❌ → 只是某能力的**一个分支**

> **为什么用客户视角而不是技术视角**：因为 golden path 的存在意义是"交付客户价值的完整闭环"。技术上把系统切成模块是工程的事；但 path 的粒度必须锚在"客户拿到的完整结果"上，否则就会把一条路切成一堆客户根本感知不到的碎片。

### 尺子② "走完拿到的结果是不是同一个" → 定"加厚" vs "分路"

尺子①圈出候选 path 后，遇到"这几个东西是同一条 path 还是要分开"时，用尺子②：

**走完之后，客户拿到的结果是不是同一个？**
- **同一个结果、只是输入/覆盖面不同** → **加厚（thickness）**，同一条 path，不分。
- **结果本身不同** → 可能是**不同 path，或同一条 path 的不同阶段（Phase）**。

例：
- 顾客发**文字**→AI 回复 / 顾客发**图片**→AI 回复 / 顾客发**语音**→AI 回复
  → 三条走完结果**都是"顾客得到回复"**，只是入口模态不同 → **加厚，一条 path**。
- "AI 回复私聊" vs "AI 主动发朋友圈营销"
  → 一个是被动服务、一个是主动获客，客户拿到**两种不同结果** → **不同 path（或不同阶段）**。

> **为什么"同结果不同覆盖 = 加厚"**：加厚的本质是"同一条价值闭环覆盖更多情况"（thin 只覆盖文字 → medium 覆盖文字+图片+语音）。它让同一条路更结实，不产生新的客户价值类型，所以不是新路。

## 三个反模式（90% 的误判都栽在这）

### 反模式一：**"难" ≠ "path"**
"读懂语音"技术上很难、工作量巨大 —— 但**难度和工作量不改变它的层级**。它再难，客户也不为"读懂语音"单独买单。**难的东西可以是一个难的 Ability/Feature,挂在某条 path 上,不因为难就升格成一条路。**
> 别被"这个太大了，肯定是独立 path"骗了。大小量的是工作量，不是 path 边界。

### 反模式二：**"平行的能力" ≠ "平行的 path"**
"看懂文字/图片/语音"三个能力看起来平行、对等，容易让人以为是三条平行的 path。但它们走完是同一个结果（尺子②）→ 是同一个能力的三个分支/加厚，不是三条路。
> 平行、对等、都很重要 —— 都不是"分路"的理由。只有"结果不同"才分。

### 反模式三：**"步骤/阶段" ≠ "path"**
"采集→判定→触达→写 Lead"是四个先后步骤，容易被当成四条 path。但客户为"拿到 Lead"这**一个结果**而来（尺子①），这四步是通向那个结果的**四个阶段（Phase）**,是一条 path 内部的分段。
> 一条路上的四段路，不是四条路。

## 层级词汇（判定结果往这几层里装）

```
Journey（域）            ← 某主角的【一个完整需求】的闭环容器（智能客服 / 工厂）
  └─ Phase（阶段）        ← journey 内按主角视角分的分组（交付 / 观察 / 守护…）
       └─ Golden Path = Ability ← 一句可独立交付的承诺（"我们支持 X 了"），一条 GP 就是一个 ability
            └─ Step（步骤）      ← GP 内部的有序步（golden_path 表，L4）
                 └─ Feature / 加厚 ← 使能件或覆盖面（看懂图片=覆盖面加厚）
```

- **Journey（域）**：主角的完整需求闭环，是**容器**——底下装得下多句"我们支持 X 了"（智能客服装 GP-A~F，工厂装 F0~F7）。⚠️ v1.0 曾把 Journey 与 Golden Path 写成同层，2026-08-06 拍板对齐 13013a49：**一条 Golden Path = 一个 Ability**，Journey 在其上。
- **Phase**：journey 内的视图分组，不改变 ability 边界（晨报与驾驶舱同属"观察"Phase，仍是两条 ability）。
- **Golden Path / Ability**：一句能独立说出口、独立坏、独立验收的承诺。
- **Step / Feature / 加厚**：GP 内部的步骤、使能件、覆盖面。共享使能件（告警、健康探测）在 Feature 层复用，**器官共享不等于 GP 重叠**。

## 判定流程

拿到一组功能/能力后，按这个顺序走：

1. **找客户价值结果**（尺子①）：这堆东西最终让客户拿到**什么完整结果**？把这个结果命名出来 —— 那就是这条 golden path 的名字和边界。
2. **归位每个东西**：逐个问"它是那个完整结果本身，还是通向它的一段/一块/一个覆盖面？"
   - 是完整结果 → 它就是 path（通常只有一个）
   - 是流程段 → Phase
   - 是客户会写进清单的能力 → Ability
   - 是使能件 / 同能力的更多覆盖 → Feature / 加厚
3. **遇到"要不要分成两条 path"用尺子②**：走完结果是否同一个？同 → 合（加厚）；不同 → 分。
4. **过一遍三个反模式**：有没有因为"难/大/平行/是步骤"而误判？纠正。
5. **输出结构化判定**（见下）。

  │    ├─ <子项>  ← 加厚/分支（尺子②：与 XX 同结果，只是覆盖面不同）

## 真实案例（判定示范）

### 案例 A：智能客服多模态
输入："智能客服能看懂文字、看懂图片、读懂语音"

```
## 判定结论
Journey「智能客服」下 1 条 Golden Path —— 接管对话（即后来的 GP-B 被动接待）

## 层级树
Journey「智能客服」← 主角测试：私域运营者的"客服被接住"需求（域，另有 GP-A/C~F 兄弟路）
  └─ Golden Path「接管对话」        ← 尺子①：客户为「AI 替我回复顾客」而来
  └─ Ability「理解顾客消息」
       ├─ 看懂文字   ← 加厚（尺子②：走完都是"顾客得到回复"，只是模态不同）
       ├─ 看懂图片   ← 加厚（同上）
       └─ 读懂语音   ← 加厚（同上；反模式一：它虽难，仍是加厚不是新 path）

## 关键判定说明
- 三个模态不是三条 path：撞反模式二（平行能力≠平行 path），且尺子②三者同结果。
- "读懂语音"虽工作量大，不升格为 path：反模式一（难≠path）。
```

### 案例 B：客户智能获客闭环
输入："采集对标视频、判定内容是否对标、评论区触达、写 Lead 表"

```
## 判定结论
Golden Path：1 条 —— 客户智能获客

## 层级树
Golden Path「客户智能获客」          ← 尺子①：客户为「拿到精准客户线索(Lead)」而来
  ├─ 阶段 采集      ← 通向 Lead 的第 1 段（反模式三：步骤≠path）
  ├─ 阶段 判定      ← 第 2 段
  ├─ 阶段 触达      ← 第 3 段
  └─ 阶段 写 Lead   ← 第 4 段（终点=客户拿到的结果）

## 关键判定说明
- 四个环节不是四条 path：撞反模式三（步骤/阶段≠path）；客户为"拿到 Lead"一个结果而来。
- 但它们该各配一个分段 smoke 守卫（一条 path 可以有多趟检测车），因为四段会各自独立坏。
```

### 案例 C：工厂域 F0~F7（Journey↔Ability 误判实录，2026-08-06）
输入：晨报（F3）和驾驶舱（F5）"看起来都是看系统状态"，它们是两个 journey 还是一个 journey 下两个 ability？

```
## 判定结论
Journey：1 个 —— 工厂（主理人的"想法变成上线且知情"需求）
Golden Path：8 条 —— F0 提案拍板 / F1 开发 / F2 部署 / F3 晨报 / F4 自愈 / F5 驾驶舱 / F6 收件箱 / F7 记忆

## 层级树（Phase 仅视图分组）
Journey「工厂」
  ├─ Phase 交付：F0 → F1 → F2
  ├─ Phase 观察：F3 晨报（推给你）、F5 驾驶舱（你来拉）
  ├─ Phase 守护：F4 故障自愈
  └─ Phase 输入与记忆：F6、F7

## 关键判定说明
- F3/F5 不合并：出口测试——"我们支持晨报了"和"我们支持驾驶舱了"是两句各自成立、可独立交付/独立坏/独立验收的承诺（push vs pull）。
- 八条不升格为 8 个 journey：数数测试——每条底下只剩步骤与使能件，列不出第二句"我们支持"；孤儿测试——每条都答得出"挂工厂"。
- F3/F4 共用告警、F4/F5 共用健康探测：器官共享是 Feature 层复用（同智能客服共享"绑定/安装前置"），不是 GP 重叠，不构成合并理由。
```

## 一句话内核

> **Path 按"客户来买的那个完整结果"切；比结果更细的（阶段、能力、模态、步骤）一律往里装，不另开 path。难不难、大不大、平不平行，都不改变它是路里的一块,不是一条新路。**
